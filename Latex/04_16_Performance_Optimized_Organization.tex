In Chapter \ref{chap:perf_opt_logic}, we examined component-level digital logic optimizations---such as carry-lookahead adders, Kogge-Stone parallel prefix networks, and Wallace tree multipliers---designed to minimize combinational propagation delay along critical paths within individual functional blocks. In this chapter, we move from circuit-level logic to \textbf{system- and microarchitectural-level organization}. 

Instruction-Level Parallelism (ILP) represents the family of architectural techniques that enable multiple machine operations to be executed simultaneously. We focus on the foundational organizational mechanisms that govern modern processor throughput: pipelining, pipeline hazard management (structural, data, and control), dynamic branch prediction, and superscalar dispatch with dynamic scheduling. As we will discover, every performance gain realized through spatial or temporal overlap introduces architectural dependencies that demand rigorous hardware solutions.

\section{Pipelining}

Combinational logic circuits (CLCs) that have a very high depth cause the system clock frequency to be reduced. The solution that allows for an increase in clock frequency is the introduction of pipeline registers.


\subsection{Pipeline Acceleration\index{pipeline acceleration}}

In Figure \ref{fig47} the pipeline technique is illustrated. In Figure \ref{fig47}a, the frequency at which the system clock can work is given by the propagation time through the $CLC_{f \circ g}$ to which is added the time associated with the propagation through the registers.

\placedrawing[htbp]{figures/05b_01_pipelining.lp}{Pipelining. {\bf a.} The initial circuit, without pipeline register.  {\bf b.} The pipelined version of the circuit.}{fig47}

\begin{equation}
    T_{clock} = t_{regProp} + t_{CLC_{f \circ g}} + t_{set-up} \simeq t_{CLC_{f \circ g}}
\end{equation}

In Figure \ref{fig47}b, the frequency at which the system clock can work will be increased because the period of the clock is given by:
\begin{equation}
    T_{clock} = t_{regProp} + \max(t_{CLC_{f}}, t_{CLC_{g}}) + t_{set-up}
\end{equation}

The resulting acceleration (speedup) is:
\begin{equation}
    \alpha \simeq \frac{t_{CLC_{f \circ g}}}{\max(t_{CLC_{f}}, t_{CLC_{g}})}
\end{equation}

The maximum efficiency, $\alpha \simeq 2$, is obtained when the combinational delay is perfectly balanced across stages:
\begin{equation}
    t_{CLC_{f}} \simeq t_{CLC_{g}}
\end{equation}

If the resulting frequency is not high enough, the technique is applied recursively to the deepest circuit or both. The process can continue until the requested speed is reached or until register setup and propagation overheads dominate the stage delay.

\subsection{Pipeline Latency}

Increasing the clock frequency is accompanied, in a pipeline structure, by the introduction of additional latency. By latency, we mean the number of clock cycles that occur in the sequential processing of a data string.

For example, in the structure from Figure \ref{fig47}a the latency is 2, due to the two synchronization registers, on the input and output. By introducing a pipeline register in the structure in Figure \ref{fig47}b the latency increases by one unit.

If we process a sufficiently long string of data, \texttt{X(1), X(2), ..., X(n)}, then the additional latency introduces an insignificant effect: the processing of the string will be performed in $n+3$ cycles instead of $n+2$ but at a frequency $\alpha$ times higher.

In other words, the introduction of the pipeline register in Figure \ref{fig47}b triggers a temporal parallel process wherein the system concurrently operates on two successive components of the data sequence.

\subsection{Pipeline Throughput and Performance Metrics}
\index{CPI (Cycles Per Instruction)!pipeline performance}\index{pipeline speedup}\index{performance equation}

The performance of an instruction pipeline is formally evaluated using the fundamental processor performance equation:
\begin{equation}
    \text{Execution Time} = \text{IC} \times \text{CPI} \times T_{clock}
\end{equation}
where $\text{IC}$ is the total instruction count of the program, $\text{CPI}$ is the average number of clock cycles per instruction, and $T_{clock} = 1/f_{clock}$ is the clock period.

In an ideal $k$-stage pipeline operating under steady-state conditions without hazards or stalls, exactly one instruction completes on every clock cycle:
\begin{equation}
    \text{CPI}_{\text{ideal}} = 1
\end{equation}
However, real hardware pipelines deviate from this theoretical optimum due to pipeline stalls introduced by architectural dependencies:
\begin{equation}
    \text{CPI} = \text{CPI}_{\text{ideal}} + \text{Stalls}_{\text{structural}} + \text{Stalls}_{\text{data}} + \text{Stalls}_{\text{control}}
\end{equation}

The effective speedup $S_k$ of a $k$-stage pipeline over an unpipelined single-cycle implementation is given by:
\begin{equation}
    S_k = \frac{\text{Execution Time}_{\text{unpipelined}}}{\text{Execution Time}_{\text{pipelined}}} = \frac{\text{CPI}_{\text{unpipelined}} \times T_{\text{unpipelined}}}{\text{CPI}_{\text{pipelined}} \times T_{\text{pipelined}}} \simeq \frac{k}{1 + \text{Stalls}}
\end{equation}
Minimizing these pipeline stall penalties through performance-optimized organization is the central engineering objective of high-performance processor design.

A version, adapted to be accelerated, is shown in Figure \ref{fig46} where the two memories, for data and programs, are also represented. The data memory is a synchronous pipelined memory (see \ref{sybcPipeMem}) which responds with one cycle latency to the read command.

The micro-architecture is the same as the one presented in Listing \ref{lst:toyRISCdefines} from Chapter \ref{toyRiscDesign}. The same for the Instruction Set Architecture which is in Table \ref{tab:riscISA}.

\placedrawing[htbp]{figures/05b_02_pipelined_toyRISC.lp}{The pipelined version of toyRISC.}{fig46}

The three pipeline registers introduced in design divide the execution of an instruction in four stages:
\begin{description}
    \item[INSTRUCTION FETCH (IF)]: the content of the register {\tt pc} (program counter) addresses in the program memory the binary code of an instruction; in the same time the module {\tt next} computes the value for the next {\tt pc}. The execution time for this stage is:
        $$t_{IF} = t_{pc} + max(t_{next}, t_{ACCto Program Memory}) + t_{suPipeReg1}$$
        In the pipeline register {\bf PipeReg\_1} is loaded the information requested to finish the execution of the fetched instruction
        
    \item[OPERANDS FETCH (OF)]: from the register are fetched the two operands of the instruction using the fields {\tt leftAddr} and {\tt rightAddr} fetched in the previous cycle from the program memory. In {\bf pipeReg\_2} are loaded the two fetched operands and the information needed in the next cycles to end the execution of the instruction. The execution time for this stage is:
        $$t_{OF} = t_{PipeReg1} + t_{regFile} + t_{suPipeReg2}$$


        
    \item[EXECUTION (EX)]: ALU performs the operation according to the code {\tt opCode}, propagated to this stage through the two previous  pipeline registers,  generate {\tt result} and the predicate {\tt zero = (result == 0)}; the {\tt add} module adds to the program counter the signed value of {\tt value} to perform the branch operation.  The execution time for this stage is:
        $$t_{EX} = t_{PipeReg2} + max((t_{mux}+t_{alu}),  (t_{add}+t_{mux}), t_{dataMemPipeReg}) + t_{suPipeReg3}$$
    \item[WRITE BACK (WB)]: acts on the first two levels in the pipeline: it allows the modification of the {\tt pc} to perform jumps and writes the result of the current operation in the register file. The execution time for this stage is:
        $$t_{WB} = t_{PipeReg3} +  max(t_{suRegFile}, (t_{next} + t_{suPC}))$$
\end{description}
The maximum clock frequency is limited by:
$$T_{clock} = max(t_{IF}, t_{OF}, t_{EX}, t_{WB})$$

\section{Hazards Generated by Dependencies}

There are three fundamental types of dependencies that create pipeline hazards\index{pipeline dependencies: structural, data, and control hazards}:
\begin{enumerate}
\item \textbf{Structural Hazard}: Hardware resource conflicts where multiple instructions attempt to use the same physical unit concurrently.
\item \textbf{Data Hazard}: Dependencies where an instruction requires the result of an earlier instruction that has not yet completed write-back.
\item \textbf{Control Hazard}: Dependencies where the next instruction address depends on the evaluation of a branch or jump in a subsequent stage.
\end{enumerate}

These dependencies generate hazardous behaviors in the pipelined processor due to the temporal overlap of partially completed instructions.

\subsection{Structural Hazards and Hardware Replication}\label{sec:structural_hazards}
\index{structural hazards!resource conflicts}\index{hardware replication!structural hazard mitigation}

A \textbf{structural hazard} occurs when two or more overlapping instructions in the pipeline attempt to access the same physical hardware resource simultaneously. When a required hardware block cannot support all concurrent requests, one or more instructions must stall until the resource is freed, degrading processor throughput.

In a non-pipelined, single-cycle computing system (such as the Harvard 5-OS core discussed in Chapter \ref{lect6a}), execution is strictly sequential. Consequently, a single arithmetic logic unit (ALU) can theoretically be time-multiplexed to perform both arithmetic computations and sequential program counter incrementing ($\text{pc} \leftarrow \text{pc} + 4$).

In a pipelined processor, however, this time-multiplexing is impossible. On \textbf{every single clock cycle}, the Instruction Fetch (\texttt{IF}) stage must calculate the sequential next address ($\text{pc} + 4$) concurrently while the Execution (\texttt{EX}) stage evaluates an arithmetic instruction or computes a branch target ($\text{pc} + \text{offset}$). If the processor attempted to share a single ALU between \texttt{IF} and \texttt{EX}, a structural hazard would occur on every cycle, stalling instruction fetch whenever arithmetic was performed and halving throughput.

To eliminate this structural hazard, pipelined organization mandates \textbf{hardware replication}:
\begin{itemize}
    \item \textbf{Dedicated Program Counter Adder}: The \texttt{IF} stage incorporates its own autonomous $+4$ incrementer (or $+1$ in word-addressed architectures) exclusively dedicated to sequential instruction pointer calculation.
    \item \textbf{Dedicated Branch Target Adder}: A separate adder is provided in the \texttt{EX} (or \texttt{OF}) stage to compute relative branch offsets without contending with the primary integer ALU.
    \item \textbf{Separate Instruction and Data Memories}: In von Neumann architectures with a single shared memory bus, a structural hazard arises whenever an instruction in \texttt{MEM} attempts to read/write data while \texttt{IF} attempts to fetch the next instruction. By utilizing the Harvard architecture with separate instruction and data memories (or dual-ported L1 caches), memory access conflicts are eliminated.
    \item \textbf{Multi-Ported Register Files}: The register file must provide multiple independent read ports (at least two for binary operations in \texttt{OF}) and a concurrent write port in \texttt{WB} so that operand reading and result write-back do not create structural contention.
\end{itemize}

\subsubsection{Reordering\index{reordering: solution for pipelined processor dependency}}

Sometimes, {\bf but only sometimes}, there is a very simple and efficient solution for data dependency: reordering the instructions in the sequence of instructions. In Example \ref{dataDep}, the instruction {\tt XOR(5,0,0)} can be moved, without affecting the result of running the sequence of instructions, between the instructions {\tt SUB} and {\tt ADD}. as follows:
\begin{verbatim}
    VAL(1,12)   ;
    SUB(2,3,4)  ;
    XOR(5,0,0)  ;
    ADD(0,2,1)  ;
    AND(1,1,2)  ;
\end{verbatim}
Thus, the {\tt XOR} instruction is used for stalling instead of the {\tt NOP} instruction, but now the execution time is not affected.

\subsubsection{Forwarding\index{forwarding: solution for pipelined processor dependency}}

By adding hardware, the data dependency can be resolved, {\bf in all cases}, with no time penalty. The solution is to connect {\tt result} not only to the register file input, but also directly to the ALU input when the value just computed is needed for the next instruction. The mechanism is called {\em forwarding} and requires the addition of one input to the  ALU input as left operand or as right operand. But, because there are binary operations (operations with two operands) sometimes both operands arrive to late in the register file to be fetched for the current instruction.

Thus, forwarding control is done by a circuit which analyses the binary code of three successive instructions. Three situations can occur:

\begin{verbatim}
    xxxxxx_00001_xxx...x                // identified in PipeReg_3
    xxxxxx_yyyyy_00001_xxx...x          // identified in PipeReg_2
\end{verbatim}
or
\begin{verbatim}
    xxxxxx_00001_xxx...x                // identified in PipeReg_3
    xxxxxx_yyyyy_zzzzz_00001_xxx...x    // identified in PipeReg_2
\end{verbatim}
or
\begin{verbatim}
    xxxxxx_00001_xxx...x                // identified in PipeReg_3
    xxxxxx_yyyyy_00001_00001_xxx...x    // identified in PipeReg_2
\end{verbatim}

\begin{verbatim}
    xxxxxx_00001_xxx...x                // identified in PipeReg_4
    xxxxxx_00011_xxx...x                // identified in PipeReg_3
    xxxxxx_yyyyy_00011_00001_xxx...x    // identified in PipeReg_2
\end{verbatim}

\begin{verbatim}
    xxxxxx_00001_xxx...x                // identified in PipeReg_4
    xxxxxx_00011_xxx...x                // identified in PipeReg_3
    xxxxxx_yyyyy_00001_00011_xxx...x    // identified in PipeReg_2
\end{verbatim}

\placedrawing[htbp]{figures/05b_03_forwarding.lp}{The change used to reduce hazards imposed by data dependencies.}{brDelRed}

The structure of the processor is modified as shown in Figure \ref{brDelRed}, where a new level in the pipeline is added and the operands at the ALU inputs are selected using multiplexers with additional inputs. The selection for the augmented multiplexers is computed combinationally as {\tt opSel[3:0]} in {\tt DECODE} and synchronized in {\bf PipeReg2} as {\tt opSel2[3:0]} to avoid an additional delay in selecting ALU operands. Thus, {\tt result} is used as an operand in the EXECUTE stage of the pipeline, if the forwarding mechanism decides, as {\tt result3} connected to inputs 1 or as {\tt result4} to inputs 2 of the selection multiplexers at the ALU operand inputs. The value of {\tt result3} is forwarded when the dependency is identified with the result of the instruction issued one clock cycle before the current one (EX hazard). The value of {\tt result4} is forwarded when the dependency is identified with the result of the instruction issued two clock cycles before the current one (MEM hazard).

Formally, the Boolean equations for generating the forwarding multiplexer controls for the left operand ($rs1$) are:
\begin{align}
\text{ForwardA}_{1} &= \texttt{RegWrite\_3} \land (\texttt{rd\_3 == rs1\_2}) \\
\text{ForwardA}_{2} &= \texttt{RegWrite\_4} \land (\texttt{rd\_4 == rs1\_2}) \land \neg \text{ForwardA}_{1}
\end{align}
and symmetrically for the right operand ($rs2$):
\begin{align}
\text{ForwardB}_{1} &= \texttt{RegWrite\_3} \land (\texttt{rd\_3 == rs2\_2}) \\
\text{ForwardB}_{2} &= \texttt{RegWrite\_4} \land (\texttt{rd\_4 == rs2\_2}) \land \neg \text{ForwardB}_{1}
\end{align}
In architectures where register 0 is hardwired to zero (such as RISC-V or MIPS), each hazard condition additionally verifies that $\texttt{rd} \neq 0$ so that writes targeting the constant zero register do not trigger spurious forwarding.

\subsubsection{Branch Prediction}\label{sec:branch_prediction_origins}
\index{branch prediction!historical origins}
\index{IBM 7030 Stretch}
\index{Blosk, Richard T.}
\index{Cocke, John}
\index{Kolsky, Harwood G.}
\index{Ballance, Richard S.}
\index{McWilliams, Thomas M.}
\index{Widdoes, L. Curtis}
\index{Smith, James E.}
\index{S-1 supercomputer}
\index{speculative execution!historical origins}

In early, sequential computers (such as ENIAC, EDVAC, UNIVAC, and the IBM 704), instructions were fetched and executed one after another. In a sequential microarchitecture, the processor simply waits for the conditional evaluation of an instruction to complete before fetching the next target; guessing or predicting the branch outcome is neither necessary nor beneficial.

The architectural necessity of branch prediction arose the exact moment computer architects decoupled instruction fetching from arithmetic execution through instruction prefetching, pipelining, and lookahead. When instruction fetching runs several clock cycles ahead of the execution stage, the instruction unit encounters conditional branches whose outcomes depend on arithmetic or logical flags that have not yet been evaluated. The architect is confronted with a fundamental dilemma: stall instruction fetching until the condition resolves (wasting precious pipeline throughput), or make an educated guess and proceed \emph{speculatively} down the anticipated instruction path.

\paragraph{The Earliest Implementation: IBM 7030 Stretch (1956--1961)}
Hardware branch prediction and speculative execution were first conceived and implemented in the late 1950s for the IBM 7030 (known as ``Stretch'') supercomputer project \cite{buchholz1962}. Stretch was managed by Stephen Dunwell, with system architecture developed by Gene Amdahl, John Cocke, and Frederick Brooks. Stretch decoupled instruction processing across specialized hardware units, integrating an advanced Instruction Unit (I-Unit) and a speculative Look-Ahead Unit \cite{blosk1960, ballance1962lookahead}:
\begin{itemize}
    \item \textit{Index-Dependent and Unconditional Branches:} Unconditional jumps and branches conditioned on index registers were resolved and executed directly within the I-Unit with zero branch penalty.
    
    \item \textit{Static Prediction (Predict Untaken):} For conditional branches depending on pending arithmetic results, the initial Stretch machines implemented the first hardware branch predictor: they statically predicted the branch as untaken and speculatively prefetched instructions along the sequential fall-through path. Subsequent revisions refined this heuristic to predict based on the current state of indicator bits (condition codes).
    
    \item \textit{Hardware Speculative Recovery:} The Look-Ahead Unit introduced the world's first hardware mechanism for speculative recovery: if an arithmetic branch was subsequently resolved as taken (a misprediction), the Look-Ahead Unit initiated a ``housecleaning'' recovery sequence that flushed the speculative instructions, restored the register state, and redirected instruction fetch along the taken path.
\end{itemize}

\paragraph{Static Heuristics (1960s--1970s)}
Following Stretch, pipelined machines in the 1960s and 1970s relied primarily on static heuristics, most notably the \textit{BTFNT (Backward Taken, Forward Not Taken)} convention: backward branches typically close iterative loops and are taken with high probability, whereas forward branches often guard exceptional conditions or conditional skips and are predominantly not taken. Compilers also began embedding static branch hints into instruction opcodes.

\paragraph{Dynamic Branch Prediction (Late 1970s)}
Static heuristics cannot adapt to data-dependent branch behaviors that vary across program phases. The  transition to \textit{dynamic branch prediction}---where specialized hardware monitors runtime branch outcomes to dynamically learn and predict future behavior---emerged independently in the late 1970s:
\begin{itemize}
    \item \textbf{Tom McWilliams and Curt Widdoes (1977):} Working on the \textbf{S-1 supercomputer} project at Lawrence Livermore National Laboratory (LLNL), McWilliams and Widdoes invented the \textit{2-bit saturating counter branch predictor}. To maintain high throughput in their deeply pipelined processor without stalling on conditional branches, their design used a ``reverse bit'' mechanism that required two consecutive mispredictions before reversing the predicted branch direction \cite{s1project1979}.
    
    \item \textbf{James E. Smith (1979--1981):} Concurrently, James E. Smith at Control Data Corporation (CDC) and the University of Wisconsin formalized table-based dynamic branch prediction, patenting random-access memory branch predictor tables and evaluating 1-bit and 2-bit saturating counters and Branch Target Buffers (BTBs) \cite{smith1981study, smith1983patent}. This empirical analysis was subsequently expanded into a comprehensive evaluation of branch target cache designs by Johnny K. F. Lee and Alan Jay Smith \cite{lee1984branch}.
\end{itemize}

\paragraph{Modern Adaptive Predictors (1990s)}
While 2-bit bimodal counters served early pipelined microprocessors effectively, deep superscalar pipelines (where a misprediction penalty wastes dozens of in-flight instructions) demanded accuracy well beyond the bimodal ceiling of $\sim 85\text{--}90\%$. As detailed later in Section \ref{sec:yeh_patt}, \textbf{Tse-Yu Yeh and Yale N. Patt} revolutionized the field by inventing \textit{Two-Level Adaptive Branch Prediction}, tracking correlated branch histories to achieve over $97\%$ accuracy \cite{yeh1991twolevel, yeh1992alternative}. This breakthrough established the foundation for subsequent innovations, including \textbf{Scott McFarling's} \textit{gshare} and tournament combining predictors \cite{mcfarling1993combining}.


\subsubsection{Static Branch Prediction\index{branch prediction!static branch prediction}}

Let us see now how the conditioned jumps, the branches, are managed to be performed efficiently. There are two cases: backward branches or forward branches. Static prediction\index{branch prediction!static branch prediction} presumes that backward branches will be taken and that forward branches will not.

In this case, most of the predictions will be correct. Indeed, if we have a jump back to execute a loop that repeats $n$ times, then once in $n+1$ situations the prediction will have to be corrected.

\begin{exemplu}
A backward branch is one that has a target address that is lower than its own address. For example,
it  refers to the following type of loop:
\begin{verbatim}
    i:          VAL(1,23)   ;
    i+1:        VAL(2,1)    ;
    i+2:  LB(3) SUB(1,1,2)  ;
    i+3:        NZJMP(1,3)  ;
    i+4:        NOP         ;
    i+5:        NOP         ;
    i+6:        ...
\end{verbatim}
This technique can help with prediction accuracy of loops, which are usually backward-pointing branches, and are taken more often than not taken.

$\diamond$
\end{exemplu}

\begin{exemplu}
A forward branch is one that has a target address that is higher than its own address. For example,
it  refers to the following type of loop:
\begin{verbatim}
    i:          VAL(1,23)   ;
    i+1:        VAL(2,1)    ;
    i+2:        SUB(1,1,2)  ;
    i+3:        ZJMP(1,2)   ;
    i+4:        XXX         ;
                ...
    i+j: LB(2)  YYY         ;
\end{verbatim}


$\diamond$
\end{exemplu}

In static prediction, all decisions are made at compile time, before the execution of the program

{\bf Note}: In order to reduce the branch penalty, in the case of unconditional jumps, certain changes can be made in the hardware. For example, the calculation of unconditional jump addresses can be moved to the OP FETCH (OF) level. The execution latency of unconditional jumps is thus reduced by one unit.

\subsubsection{Dynamic Branch Prediction}

Dynamic branch prediction\index{branch prediction!dynamic branch prediction} predicts branch directions and targets based on execution history collected at run-time using dedicated hardware structures. Foundational studies established the empirical framework for runtime branch history tracking, saturating up/down counters, and Branch Target Buffers (BTBs)\index{branch target buffer (BTB)} \cite{smith1981study, lee1984branch}. We first examine the two classic bimodal counter mechanisms before discussing modern two-level adaptive predictors.

\paragraph{Last-time, one-bit predictor}
is the simplest solution  which uses a two state automaton whose behavior is described in Figure \ref{bp1}. We will code the state {\tt prediction not taken} with 0, and the state {\tt prediction taken} with 1. The automaton is a {\em saturated} 1-bit counter. If is incremented from 0 goes to 1, if is decremented from 1 goes to 0. But if it is incremented from 1, stays in 1, while decremented from 0 stays in 0. This 2-state automaton says whether the branch was recently taken or not. Based on this, the processor fetches the next instruction from the target address or sequential address. If the prediction is wrong, flushes the pipeline and also flips prediction. So, every time a wrong prediction is made, the prediction bit is flipped.

\placedrawing[H]{figures/05b_04_1bit_branch_predictor.lp}{The saturated one-bit up/down counter as last-time branch predictor.}{bp1}


This mechanism always mispredicts the last iteration and the first iteration of a loop branch, thus the accuracy for a loop with $N$ iterations is $(100 \times (N-2)/N)\%$. For large values of $N$ the accuracy of the prediction increases, while for small values this mechanism is not very efficient.


\paragraph{Two-Bit Counter Based Predictor} is a four-state finite automaton. Its behavior is described in Figure \ref{2bp}. The advantage of the two-bit predictor over a one-bit predictor is that a conditional jump has to deviate twice from what it has done most in the past before the prediction changes. For example, a loop-closing conditional jump is mispredicted once rather than twice.

Each state of the automaton is interpreted as follows:
\begin{itemize}
    \item 00: strongly not taken
    \item 01: weakly not taken
    \item 10: weakly taken
    \item 11: strongly taken
\end{itemize}

\placedrawing[H]{figures/05b_05_2bit_branch_predictor.lp}{Two-bit saturated counter based predictor.}{2bp}

The automaton is a {\em saturated} 2-bit counter. It increments for {\tt actually taken} and decrements for {\tt actually not taken}. This predictor changes prediction only on two successive mispredictions.

    \end{tabular}
  \end{center}
\end{table}

As shown in Table \ref{tab:branch_trace}, the 1-bit predictor incurs \textbf{two mispredictions} per loop invocation:
\begin{enumerate}
    \item When the loop terminates on Iteration 4 (predicts T, actually NT), causing the state bit to flip from 1 to 0.
    \item When the loop is re-entered on Pass 2, Iteration 1 (predicts NT based on the previous loop exit, but the branch is actually T), causing the state bit to flip back to 1.
\end{enumerate}
Consequently, for an $N$-iteration loop, the 1-bit predictor correctly predicts only $N-2$ branch occurrences, giving an accuracy of $(N-2)/N$. For $N = 4$, its steady-state accuracy is only $2/4 = 50\%$.

In contrast, the 2-bit counter predictor incurs only \textbf{a single misprediction} upon loop exit. When the loop terminates on Iteration 4, the counter decrements from Strongly Taken (11) to Weakly Taken (10). Because the most significant bit remains 1, the predictor continues to predict Taken! When the loop re-executes on Pass 2, Iteration 1 is correctly predicted as Taken, and the counter immediately increments back to Strongly Taken (11). Its accuracy is $(N-1)/N$, which is $3/4 = 75\%$ for $N = 4$, and rises to $90\%$ for $N = 10$.

\paragraph{Two-Level Adaptive Predictors and Correlated Branches (Yeh and Patt)}
\label{sec:yeh_patt}
\index{branch prediction!two-level adaptive}
\index{Patt, Yale N.}
\index{Yeh, Tse-Yu}
\index{branch history register (BHR)}
\index{pattern history table (PHT)}
\index{branch correlation}
\index{gshare predictor}
\index{tournament predictor}

While 1-bit and 2-bit bimodal counters track the history of individual branches in isolation, real programs contain branches whose outcomes strongly correlate either with their own recent past outcomes or with the outcomes of other preceding branches (known as \emph{branch correlation}\index{branch correlation}). For example, consider an alternating loop condition or a sequence of dependent conditional statements such as:
\begin{verbatim}
    if (aa == 2)
        aa = 0;
    if (bb == 2)
        bb = 0;
    if (aa != bb) { ... }
\end{verbatim}
If both preceding conditions are true, the third branch is guaranteed not to be taken. An isolated 2-bit counter indexed solely by the branch address cannot capture this inter-branch correlation because it does not record which path led to the branch.

In landmark research, Tse-Yu Yeh and Yale N.~Patt solved this limitation by introducing \textit{Two-Level Adaptive Branch Prediction} \cite{yeh1991twolevel, yeh1992alternative}. Aggressive out-of-order execution and wide superscalar dispatch cannot succeed without near-perfect branch prediction, because branch misprediction penalties flush large instruction windows, as demonstrated in Yale Patt's High Performance Substrate (HPS) architecture \cite{patt1985hps}.

The key insight of Yeh and Patt was to decouple dynamic branch prediction into two distinct levels of history:
\begin{enumerate}
    \item \textbf{First Level: Branch History Register (BHR / GHR)}: A $k$-bit shift register that records the actual outcomes of the last $k$ branches (shifting in a 1 for Taken and a 0 for Not Taken). This history can be tracked globally across all branches in a Global History Register (GHR) to capture inter-branch correlation, or locally per branch instruction (BHR) to capture recurring loop patterns.
    \item \textbf{Second Level: Pattern History Table (PHT)}: An array of $2^k$ 2-bit saturating counters. Instead of indexing counters directly by the branch address, the predictor uses the $k$-bit branch history pattern as an index (or combines the branch address with the history pattern) to select a dedicated 2-bit saturating counter.
\end{enumerate}

Yeh and Patt classified two-level adaptive predictors into nine variations based on whether the history register is Global ($G$), Per-branch ($P$), or Set-associative ($S$), and whether the pattern table is Global ($g$), Per-branch ($p$), or Set-associative ($s$)---yielding configurations such as \emph{GAg}, \emph{GAp}, \emph{PAg}, and \emph{PAp} \cite{yeh1992alternative}. By maintaining separate saturating counters for each specific sequence of recent branch outcomes (e.g., distinguishing the behavior after pattern \texttt{1010} from pattern \texttt{1111}), Yeh and Patt demonstrated that two-level adaptive predictors shattered the accuracy ceiling of isolated 2-bit counters, elevating prediction accuracy from $\sim 85\text{--}90\%$ to over $97\%$.

Building upon Yeh and Patt's two-level framework, \textbf{Scott McFarling} introduced the \textit{gshare predictor}, which computes a bitwise XOR of the global branch history register with the branch instruction address (PC) to index the PHT, significantly reducing aliasing (conflict interference) between different branches \cite{mcfarling1993combining}. McFarling also pioneered \textit{combining (tournament) predictors}, which use a secondary array of 2-bit counters to dynamically select between two different prediction strategies (such as a local bimodal predictor and a global two-level predictor) based on which predictor has historically demonstrated greater accuracy for that specific branch. Yeh and Patt's two-level adaptive techniques and their derivatives (including gshare, tournament predictors, and modern neural perceptron predictors) formed the core branch prediction engine in virtually all high-performance microprocessors, including the Intel Pentium Pro/II/III/4/Core, AMD K6/Athlon/Zen, and DEC Alpha 21264.

\section{Superscalar Processor\index{superscallar processor: a processor  designed with several execution units}}

If the processor is designed with several execution units (for example: one integer ALU, two floating-point units, two load/store units), the potential parallelism thus obtained should be activated at the highest possible level. This means that in each clock cycle a maximum number of resources should be active, if possible all of them.

In this case, the processor, called  {\em superscalar}, can execute instructions in an order imposed by the availability of data and execution units, rather than by their initial sequence in the  program. For example, the {\em PowerPC 970} processor (derived from the IBM POWER4 architecture \cite{tendler2002power4}) fetches and decodes up to eight instructions, dispatches up to five to reservation stations, issues up to eight to the execution units, and retires up to five per cycle.

\subsection{Structural Hazards and Execution Unit Replication}\label{sec:superscalar_structural_hazards}
\index{structural hazards!superscalar execution}\index{hardware replication!execution units}

When the microarchitecture is expanded from a scalar pipeline (issuing 1 instruction per cycle) to a \textbf{superscalar} organization (issuing $N$ instructions per cycle), structural hazards multiply:
\begin{itemize}
    \item If two independent arithmetic instructions are issued simultaneously in the same cycle, a core with only one integer ALU suffers a structural stall.
    \item If two memory operations (e.g., two loads, or a load and a store) are issued in parallel, they conflict unless the data cache provides multiple independent read/write ports.
\end{itemize}
To sustain high issue rates without structural stalls, superscalar processors replicate functional execution units:
\begin{itemize}
    \item Multiple symmetric integer ALUs (e.g., 2 to 4 ALUs operating in parallel).
    \item Multiple Address Generation Units (AGUs) and dual-ported load/store queues.
    \item Dedicated floating-point adders and multipliers separate from the integer datapath.
    \item Highly multi-ported register files (requiring $2N$ read ports and $N$ write ports for an $N$-way superscalar core).
\end{itemize}
Where physical silicon area or routing complexity prevents full replication (e.g., hardware dividers or complex transcendental units), instructions targeting the shared unit must arbitrate, and subsequent instructions that require the busy unit experience a structural stall.

\subsection{Register renaming\index{renaming register: technique applied when sequential execution is no longer mandatory}}

The sequence in which the instructions are executed must be strictly respected when there are data dependencies. But when certain independent sequences can be identified, strictly sequential execution is no longer mandatory, especially in the case of a superscalar processor that allows parallelism at the level of instructions. We can apply in such cases the {\em register renaming} technique.

\begin{exemplu}
Consider this sequence of code running on an out-of-order processor:
\begin{verbatim}
    READ(0,4)   ;   // read in rf[0] from the address in rf[4]
    ADD(0,0,12) ;   // rf[0] <= rf[0] + rf[12]
    STORE(0,7)  ;   // dataMemory[rf[7]] <= rf[0]
    READ(0,5)   ;
    ADD(0,0,6)  ;
    STORE(0,21) ;
\end{verbatim}
The instructions in the last three lines are {\bf independent} of the first three lines. The processor cannot execute {\tt STORE(0,21)} until  {\tt STORE(0,7)} is done.
We can eliminate this restriction involving in our code a supplementary register, as follows:
\begin{verbatim}
    READ(0,4)   ;   // read in rf[0] from the address in rf[4]
    ADD(0,0,12) ;   // rf[0] <= rf[0] + rf[12]
    STORE(0,7)  ;   // dataMemory[rf[7]] <= rf[0]
    READ(2,5)   ;
    ADD(2,2,6)  ;
    STORE(2,21) ;
\end{verbatim}
The first three instructions involves {\tt rf[0]}, while the last three instructions work on the register {\tt rf[2]}, allowing the last three instructions to be executed in parallel with the first three.

$\diamond$
\end{exemplu}


\subsection{Out-of-Order Execution\index{out-of-order execution: instruction execution in an order governed by the data availability}}

Out-of-order execution  is a mechanism used in  high-performance  processing units to make use efficiently  of instruction cycles. Using this mechanism, a processor executes instructions in an order governed by the availability of input data and execution units, rather than by their original order in a program. Thus the processor  avoids being idle while waiting for the preceding instruction to complete and can, in the meantime, proceed to execution of the next instructions that are able to run immediately and independently.
The mechanism is efficient for a processor with multiple execution units {\bf with speed difference between instructions}. It is the case of superscalar processor with ISA performing integer and floating-point arithmetic operations. There are also speed difference between arithmetic and logic instructions and memory access instructions.

While in a pipelined scalar processor an instruction is executed in the following steps:
\begin{enumerate}
\item Instruction fetch.
\item Operands fetch, if input operands are available in processor's register file, else the processor stalls until they are available.
\item The instruction is executed.
\item The results is write back to the register file.
\end{enumerate}
in a superscalar processor the out-of-order execution is requested. It consists of the following steps:
\begin{enumerate}
\item Instruction fetch.
\item Instruction dispatch to an instruction queue (also called instruction buffer or reservation stations).
\item The instruction waits in the queue until its input operands are available. The instruction can leave the queue before older instructions.
\item The instruction is issued to the appropriate idle functional unit.
\item The results are queued.
\item Only after all older instructions have their results written back to the register file, then this result is written back to the register file.
\end{enumerate}

The benefit of out-of-order execution processing grows as the instruction pipeline deepens and the speed difference between main memory or cache memory and the processor widens. On modern machines, the processor runs few times faster than the cache memory and many times faster then system memory, so during the time an in-order processor  waits for data, a large number of instructions could be executed.

\begin{exemplu}\label{warwaw}
Consider the following sequence of instructions \cite[p.~185]{Patterson05}:
\begin{verbatim}
    DIV(0,2,4)  ;
    ADD(6,0,8)  ;
    STR(6,1)    ;   // store
    SUB(8,9,7)  ;
    MUL(6,9,8)  ;
\end{verbatim}
here are the following dependencies:
\begin{enumerate}
    \item between ADD and SUB if SUB finishes before ADD starts (a WAR hazard) is an antidependence
    \item between ADD and MUL if ADD finishes later than MUL (WAW hazard) is an output dependence
    \item between DIV and ADD a true data dependency (a RAW hazard)
    \item between SUB and MUL a true data dependency (a RAW hazard)
    \item between ADD and STORE a true data dependency (a RAW hazard)
\end{enumerate}
First, let us apply register renaming technique involving two additional registers, {\tt rf(10)} and {\tt rf(11)}:
\begin{verbatim}
    DIV(0, 2, 4)    ;
    ADD(10,0, 8)    ;
    STR(10,1)       ;
    SUB(11,9, 7)    ;
    MUL(6, 9, 11)   ;
\end{verbatim}
Any WAR and WAW dependencies are now removed statically by the compiler. For RAW dependency the forwarding mechanism works but only in a processor with one integer ALU. What can be done for a superscalar processor with floating point arithmetic?

$\diamond$
\end{exemplu}

The hardware added for out-of-order execution is big sized and complex. With the increase in the number of pipeline levels, the costs (area plus complexity in use) increase. Multiprocessing and multithreading will allow more efficient alternative solutions.

\subsubsection{Dynamic Scheduling with the Scoreboard (CDC 6600)}\label{sec:scoreboard}\index{Scoreboard!CDC 6600 dynamic scheduling}\index{Cray, Seymour (1925-1996)}\index{Thornton, James E. (1925-2005)}

The earliest dynamic scheduling technique for out-of-order execution was the \emph{Scoreboard}, developed by Seymour Cray and James E. Thornton for the Control Data Corporation (CDC) 6600 supercomputer in 1964 \cite{thornton1964, thornton1970}. The CDC 6600 incorporated multiple independent functional units (floating-point adders, multipliers, a divider, shift units, and integer ALUs) operating in parallel. 

The scoreboard is a centralized hardware control unit that maintains the status of all active instructions, functional units, and registers. It dynamically steers instruction progress through four execution stages:
\begin{enumerate}
    \item \textbf{Issue}: Decodes the instruction and checks for \textit{structural hazards} and \textit{WAW hazards} (output dependencies). If the required functional unit is busy, or if another previously issued instruction has the same destination register ($rd$), the instruction issue stage stalls. No subsequent instructions can issue until the hazard resolves.
    
    \item \textbf{Read Operands}: Monitors \textit{RAW hazards} (true data dependencies). An instruction remains in this stage until all of its source operands are available in the register file---meaning no currently active functional unit is computing a value destined for those registers. Once the operands are valid, the functional unit reads them directly from the register file.
    
    \item \textbf{Execution}: The functional unit performs the requested operation over its required latency (e.g., 1 cycle for integer addition, 4 cycles for floating-point addition, 10 cycles for floating-point multiplication). When execution completes, the unit notifies the scoreboard.
    
    \item \textbf{Write Result}: Checks for \textit{WAR hazards} (anti-dependencies). Before a functional unit can write its result back to the register file, the scoreboard checks whether any earlier issued instruction has yet to read its source operand from this destination register. If such an instruction exists, the writeback stage stalls until the dependent instruction has completed its \textit{Read Operands} phase!
\end{enumerate}

Although the scoreboard achieved unprecedented performance for its time by enabling independent operations to complete out of order, it suffered from two key limitations:
\begin{itemize}
    \item \textbf{WAR and WAW Stalls}: Because registers are referenced strictly by their architectural names without renaming, instructions must stall on both WAR and WAW hazards.
    \item \textbf{Centralized Bottleneck}: All status tracking and hazard evaluations occur in a centralized scoreboard, restricting issue bandwidth and limiting scalability to deeply pipelined or wider-issue superscalar cores.
\end{itemize}

\subsubsection{Tomasulo's Algorithm and Dynamic Register Renaming (IBM 360/91)}\label{sec:tomasulo}\index{Tomasulo's algorithm: dynamic scheduling in out-of-order execution}\index{Tomasulo, Robert (1934-2008)}

To overcome the performance bottlenecks of scoreboarding, Robert M. Tomasulo invented an algorithm for dynamic instruction scheduling with register renaming at IBM in 1967 for the System/360 Model 91 floating-point unit \cite{tomasulo1967}. Tomasulo's algorithm introduces three revolutionary microarchitectural concepts:
\begin{enumerate}
    \item \textbf{Distributed Reservation Stations}: Instead of a centralized control structure, small storage buffers called \emph{Reservation Stations} (RS) are placed directly at the input of each functional unit. Instructions are dispatched immediately into an available reservation station, freeing the instruction issue logic to fetch and decode subsequent instructions.
    
    \item \textbf{Dynamic Register Renaming}: Register specifiers are replaced by \emph{tags} identifying the reservation station that will produce the result. If a source operand is not yet available at issue time, the reservation station stores the tag of the producing unit rather than the operand value. Because operands are buffered and referenced by tags rather than architectural register names, WAR and WAW hazards are completely eliminated without stalling.
    
    \item \textbf{Common Data Bus (CDB)}: Results are not written point-to-point into the register file. Instead, when a functional unit finishes, it broadcasts its reservation station tag along with the computed data over a shared broadcast bus called the \emph{Common Data Bus} (CDB). All reservation stations waiting for that tag snoop the bus and latch the result simultaneously, bypassing the register file entirely.
\end{enumerate}

Tomasulo's algorithm coordinates execution through three distinct phases:
\begin{enumerate}
    \item \textbf{Issue}: Checks for a structural hazard (is there a free reservation station for this instruction's functional unit type?). If a reservation station is free, the instruction is issued. If a source operand is already available in the register file, its value is copied directly into the reservation station's value field ($V_j$ or $V_k$). If the operand is currently being computed by another instruction, the tag of the producing reservation station is copied into the tag field ($Q_j$ or $Q_k$). Finally, the destination register in the register status table is updated to point to this reservation station ($Q_i$), dynamically renaming the register.
    
    \item \textbf{Execute}: When all required source operands are available in the reservation station (i.e., $Q_j = 0$ and $Q_k = 0$), the functional unit begins execution. While waiting, the reservation station snoops the CDB on every cycle to capture pending values when their producing tags are broadcast, resolving RAW hazards dynamically.
    
    \item \textbf{Write Result}: Upon completion, the functional unit broadcasts its result and tag over the CDB. Any reservation station waiting on that tag copies the value into its $V$ field and clears its $Q$ field. If the register status table indicates that this reservation station is still the latest producer for the destination register ($Q_i == \text{this RS}$), the register file is updated. Finally, the reservation station is marked free ($Busy = 0$).
\end{enumerate}

Each entry in a Reservation Station maintains the following status fields \cite{Patterson19}:
\begin{itemize}
    \item \textbf{Op}: The operation to perform on source operands $S_1$ and $S_2$.
    \item \textbf{Qj, Qk}: The reservation station tags that will produce the corresponding source operands; a value of zero indicates that the source operand is already available in $V_j$ or $V_k$, or is unnecessary.
    \item \textbf{Vj, Vk}: The values of the source operands. Note that for each operand, only one of the $V$ field or $Q$ field is valid. For memory store instructions, $V_k$ holds the data value to be stored.
    \item \textbf{A}: Holds memory address calculation information for load and store instructions. Initially, the immediate offset is stored here; after effective address calculation, the memory address is stored here.
    \item \textbf{Busy}: A 1-bit flag indicating whether this reservation station and its functional unit are currently occupied.
\end{itemize}

Complementing the reservation stations, the processor's register file includes a register result status field, \textbf{Qi}:
\begin{itemize}
    \item \textbf{Qi}: The identifier of the reservation station producing the result to be stored into register $R_i$. If $Q_i = 0$ (or blank), no currently active instruction is writing to $R_i$, meaning the value stored in the register file is architecturally valid.
\end{itemize}

\subsubsection{Speculative Execution, Precise Interrupts, and the Reorder Buffer}\label{sec:rob}
\index{reorder buffer (ROB)!speculative execution}\index{precise interrupts!out-of-order execution}\index{Smith, James E.}\index{Pleszkun, Andrew R.}\index{Sohi, Gurindar S.}

While Tomasulo's algorithm dynamically eliminates false dependencies (WAR and WAW) and tolerates long execution latencies, it possesses a fundamental architectural limitation: \textbf{imprecise exceptions}. In classic Tomasulo scheduling, results are written out of order directly to the architectural register file as soon as each functional unit completes. 

If an instruction triggers a hardware exception (such as an arithmetic overflow, divide by zero, or virtual memory page fault), or if a conditional branch is speculatively mispredicted, subsequent instructions that executed out of order may have already permanently overwritten architectural registers. Consequently, the processor cannot reconstruct the exact state of the program at the point of the fault, making software debugging, page-fault handling, and speculative branch recovery impossible.

To resolve this critical flaw, James E. Smith and Andrew R. Pleszkun introduced the \textbf{Reorder Buffer (ROB)} to support precise interrupts and speculative branch recovery \cite{smith1988precise}. Gurindar S. Sohi extended this approach with the Register Update Unit (RUU) \cite{sohi1990instruction}. Together, Smith and Sohi synthesized the foundational framework for modern speculative superscalar microarchitectures \cite{smith1991}.

The core insight of the Reorder Buffer is to decouple execution completion from architectural state update:
\begin{itemize}
    \item Instructions are dispatched and issued in strict program order.
    \item Instructions execute and produce results out of order.
    \item Completed results are buffered speculatively in the Reorder Buffer.
    \item Instructions commit and update the permanent architectural register file and memory strictly in program order.
\end{itemize}

\paragraph{ROB Organization and Entry Fields}
The Reorder Buffer is organized as a circular FIFO queue managed by head (commit) and tail (issue) pointers. When an instruction is decoded and dispatched, it is assigned a unique sequential slot at the tail of the ROB. The index of this ROB slot acts as the dynamic renaming tag for the instruction's destination register. 

Each entry in the Reorder Buffer contains the following fields:
\begin{itemize}
    \item \textbf{Type}: Identifies the instruction class (e.g., branch, store, integer ALU, floating-point, load).
    \item \textbf{Destination}: Specifies the target architectural register number ($rd$) for register-writing instructions, or the computed memory destination for store instructions.
    \item \textbf{Value}: Holds the speculative data result computed by the functional unit once execution completes.
    \item \textbf{Ready}: A 1-bit status flag indicating whether the functional unit has finished execution and broadcast its result to the ROB.
    \item \textbf{Exception}: Status flags indicating whether an arithmetic overflow, memory alignment fault, or page fault was raised during execution.
\end{itemize}

\paragraph{Four-Stage Speculative Out-of-Order Execution}
With a Reorder Buffer, instruction execution proceeds through four distinct stages:
\begin{enumerate}
    \item \textbf{Issue / Dispatch (In-Order)}: The next instruction in program order is decoded. If both a reservation station and an entry at the tail of the ROB are available, the instruction is allocated both resources. The destination register in the register status table is updated to point to the newly assigned ROB tag ($Q_i = \text{ROB}_{\text{tail}}$). If a source operand is already available in the architectural register file, it is read; if it is currently in flight in an active ROB entry, it is copied from the ROB (if ready) or the producing ROB tag is recorded in the reservation station.
    \item \textbf{Execute (Out-of-Order)}: As soon as all required source operands become available in the reservation station (via CDB forwarding or direct dispatch), the functional unit executes the operation.
    \item \textbf{Write Result (Out-of-Order)}: When the functional unit completes, it broadcasts its computed result and ROB tag over the Common Data Bus (CDB). The result is written into the assigned ROB entry, and its \textit{Ready} bit is set to 1. Simultaneously, any waiting reservation stations snoop the CDB and capture the value. \textbf{The architectural register file is not touched during this stage}.
    \item \textbf{Commit / Retire (Strictly In-Order)}: Only the instruction at the \textbf{head} of the ROB is evaluated for retirement. When the head entry has $\textit{Ready} = 1$:
    \begin{itemize}
        \item \textit{Normal Completion}: If no exception occurred, the speculative value stored in the ROB entry is written permanently into the architectural register file (or committed to data cache/memory if it is a store instruction). The head pointer advances, freeing the ROB entry.
        \item \textit{Branch Misprediction}: If the head instruction is a conditional branch that was mispredicted, all speculative entries currently in the ROB are instantaneously flushed in a single clock cycle, the processor redirects the program counter to the alternate target, and execution restarts without any corrupted architectural registers!
        \item \textit{Precise Exception}: If an exception flag is set, the pipeline and all subsequent ROB entries are discarded. Because no instruction past the faulting instruction has been allowed to commit to the architectural register file, the processor state is 100\% \textbf{precise}, allowing the operating system exception handler to service the interrupt and resume execution correctly.
    \end{itemize}
\end{enumerate}

\subsubsection{Instruction Compounding and SCISM}\label{sec:scism}
\index{SCISM: Scalable Compound Instruction Set Machine}
\index{Vassiliadis, Stamatis (1951-2008)}
\index{compound instructions!superscalar issue}
\index{branch folding!zero-cycle branch execution}

While out-of-order execution, register renaming, and reorder buffers successfully eliminate false dependencies and tolerate variable execution latencies, widening a superscalar datapath to issue multiple instructions per clock cycle introduces a severe microarchitectural bottleneck in the processor front-end: the quadratic scaling problem of dependency checking.

\paragraph{The Quadratic Issue-Width Bottleneck}
In a conventional $W$-issue superscalar core, the issue logic must concurrently examine all $W$ candidate instructions in each clock cycle to detect intra-cycle data dependencies (RAW, WAR, and WAW hazards), register write conflicts, and execution resource contention. For $W$ candidate instructions, the number of potential pairwise dependency checks scales quadratically as:
\begin{equation}
\binom{W}{2} = \frac{W(W-1)}{2} \in O(W^2)
\end{equation}
For a 2-issue processor, only 1 pairwise check is required; for a 4-issue processor, 6 checks are needed; for an 8-issue processor, 28 simultaneous pairwise comparisons are required across all source and destination register specifiers. This $O(W^2)$ comparator matrix creates severe wiring congestion, consumes substantial silicon area, dissipates high dynamic switching power, and critically lengthens the combinational path of the issue stage, directly threatening the processor's maximum clock frequency.

\paragraph{The SCISM Architecture}
To mitigate this complexity barrier, \textbf{Stamatis Vassiliadis}, \textbf{Bart Blaner}, and \textbf{Richard J. Eickemeyer} invented the \textit{Scalable Compound Instruction Set Machine (SCISM)} at IBM in 1994 \cite{vassiliadis1994scism}. 

The foundational insight of SCISM is to shift dependency analysis and grouping forward in the pipeline, pre-processing instructions to form \textit{compound instructions} that can be issued and dispatched concurrently without requiring an $O(W^2)$ interlock check during the time-critical issue cycle:
\begin{enumerate}
    \item \textbf{Instruction Compounding}: Instructions from a single sequential program stream are examined (either statically by the compiler, dynamically during instruction cache line reload, or via a lightweight pre-decode stage) and grouped into compound instruction packets. A compound instruction encapsulates multiple independent or chained operations that are structurally guaranteed to execute in parallel without dependency hazards.
    
    \item \textbf{Conflict-Free Parallel Execution}: Because inter-instruction dependencies are resolved prior to entering the issue stage, the issue logic treats the compound instruction as a single dispatch entity. The component operations of the compound instruction are routed directly to parallel execution units (such as a Compound Arithmetic Logic Unit \cite{vassiliadis1993calu}) without activating an $O(W^2)$ comparison matrix.
    
    \item \textbf{Branch Pre-Processing and Zero-Cycle Branch Folding}: SCISM integrates a specialized branch processing unit that dynamically scans ahead in the instruction stream, extracts conditional and unconditional branches before they reach the main instruction queue, and resolves or predicts their outcomes. By folding branches out of the sequential instruction stream, SCISM delivers uninterrupted, ``branchless'' compound instruction sequences to the execution core.
\end{enumerate}

The SCISM architecture achieves over $90\%$ of the performance of an idealized dual-issue superscalar machine while preserving the simple, high-frequency clock cycle and minimal control logic of a scalar pipeline \cite{vassiliadis1994scism}.


\subsubsection{Modern Frontiers in Superscalar Dispatch and Execution}\label{sec:modern_superscalar_frontiers}
\index{macro-op fusion!instruction decoding optimization}
\index{micro-op fusion!reorder buffer optimization}
\index{zero-cycle move elimination!register renaming optimization}
\index{physical register file (PRF)!unified register architecture}
\index{memory disambiguation!speculative store-to-load forwarding}

Modern high-performance cores (such as the Intel Core microarchitecture \cite{gochman2006intel}, AMD Zen \cite{singh2017zen, suggs2020zen2}, Berkeley BOOM \cite{celio2018boom}, and XiangShan \cite{xiangshan2022micro}) incorporate four advanced techniques that push superscalar execution far beyond the classic Tomasulo and ROB models:

\paragraph{1. Macro-Op and Micro-Op Fusion}
First deployed commercially in the Intel Core microarchitecture \cite{gochman2006intel} and now pervasive across x86, ARM, and RISC-V processors, \textit{instruction fusion} represents the direct modern commercial evolution of SCISM's compounding principle:
\begin{itemize}
    \item \textbf{Macro-Op Fusion}: During the instruction decode stage, hardware logic inspects adjacent architectural instructions and merges compatible pairs into a single internal micro-operation ($\mu$op):
    \begin{itemize}
        \item \textit{In x86}: A comparison or test instruction (\texttt{CMP} or \texttt{TEST}) followed by a conditional branch (\texttt{Jcc}) is fused into a single compare-and-branch $\mu$op that is renamed, queued, and executed as a single entity, saving decode bandwidth and ROB entries.
       
        \item \textit{In RISC-V}: Common two-instruction sequences are fused by the decoder into single micro-ops. For example, \texttt{lui} (Load Upper Immediate) followed by \texttt{addi} is fused into a single 32-bit constant generation $\mu$op; \texttt{auipc} followed by \texttt{jalr} is fused into a single direct function call; and address calculations followed by memory operations are fused into single indexed load/store operations.
    \end{itemize}
    \item \textbf{Micro-Op Fusion}: Merges two sub-operations of a single complex instruction (such as a memory load fused with an ALU arithmetic operation, or a store-address fused with store-data) into a single entry within the Reorder Buffer and issue queue. The fused $\mu$op occupies only a single slot in the ROB, expanding effective ROB capacity and issue bandwidth by $20\%\text{--}30\%$, and splits into separate execution components only at the functional unit issue ports.
\end{itemize}

\paragraph{2. Zero-Cycle Move Elimination (Zero-Latency Register Renaming)}
In classic superscalar execution, register-to-register copy instructions (such as \texttt{mov r1, r2} in x86, or \texttt{add x1, x2, x0} in RISC-V) allocate a reservation station slot, wait for operand availability, occupy an integer ALU for one clock cycle, and broadcast their result over the Common Data Bus.

To eliminate this waste, modern processors implement \textbf{Zero-Cycle Move Elimination} in the register renaming stage \cite{jourdan1999extended}:
\begin{itemize}
    \item When the register renamer encounters a register-to-register move instruction, it simply updates the Register Alias Table (RAT) so that the architectural destination register points to the exact same physical register as the source operand.
    \item The reference count of the physical register is incremented, and the move instruction is immediately marked as completed.
    \item \textbf{Hardware Impact}: The move instruction never enters the reservation stations, consumes zero ALU execution cycles, burns zero dynamic switching power on the execution buses, and has an effective latency of zero cycles.
\end{itemize}

\paragraph{3. Decoupled Physical Register File (PRF) Architecture vs. Data-Carrying ROB}
An architectural transition occurred between early out-of-order processors of the 1990s and modern processors:
\begin{itemize}
    \item \textbf{Data-Carrying ROB (Classic Intel P6 / Pentium Pro \cite{papworth1996tuning})}: In the classic Tomasulo + ROB scheme, speculative arithmetic results are written over the CDB directly into storage fields inside the Reorder Buffer entries. When instructions commit, the values are copied from the ROB into the separate Architectural Register File (ARF). Because each ROB entry must physically house wide 32-bit or 64-bit data registers and multi-ported forwarding multiplexers, the wiring capacitance and power dissipation scale rapidly, capping practical ROB capacities to $32\text{--}40$ entries.
    \item \textbf{Unified Physical Register File (PRF) (MIPS R10000 \cite{yeager1996mips}, DEC Alpha 21264 \cite{kessler1999alpha}, Intel Sandy Bridge \cite{rotem2012power}, AMD Zen \cite{singh2017zen, suggs2020zen2}, Berkeley BOOM \cite{celio2018boom})}:
    \begin{itemize}
        \item The ROB is completely decoupled from data storage: each ROB entry stores only instruction status, exception indicators, and physical register specifiers (tags). No data values are stored in the ROB.
        
        \item All data values (speculative and committed) reside in a centralized \textit{Unified Physical Register File (PRF)} containing $128\text{--}300+$ physical registers for 32 architectural registers.
        
        \item Renaming maps architectural registers to physical registers drawn from a Free List. When execution completes, the result is written once into the allocated physical register.
        
        \item When the instruction reaches the head of the ROB and commits, the processor merely marks the physical register as committed in the architectural RAT and returns the \emph{previous} physical register assigned to that architectural register back to the Free List.
    \end{itemize}
\end{itemize}
This data-decoupled PRF architecture is what enables modern out-of-order instruction windows to scale to massive dimensions: 512 entries in Intel Golden Cove, 320--448 entries in AMD Zen 4/5 \cite{suggs2020zen2}, and over 630 entries in Apple Silicon, allowing the processor to look ahead across hundreds of instructions to expose latent ILP and hide long-latency memory cache misses.

\paragraph{4. Dynamic Memory Disambiguation and Speculative Store-to-Load Forwarding}
Because memory addresses are computed dynamically at runtime by Address Generation Units (AGUs), the processor cannot determine whether a memory load instruction conflicts with an older, pending store instruction at decode time. Modern processors manage memory dependencies through \textit{Load and Store Queues (LSQ)}:
\begin{itemize}
    \item \textbf{Store-to-Load Forwarding}: If a younger load requires data from an older store whose address has already been computed and matches, the data is forwarded directly from the Store Queue entry to the load without waiting for an L1 cache access.
    
    \item \textbf{Speculative Memory Disambiguation} \cite{moshovos1997dynamic, chrysos1998memory}: Rather than stalling a ready load until all preceding store addresses have been computed, the processor uses dynamic predictors (such as Store Sets \cite{chrysos1998memory}) to predict whether the load aliases with any active store. If predicted independent, the load issues speculatively to memory immediately. If an address conflict is later detected when the older store address finishes computing (a memory order violation), the speculative load and all subsequent dependent instructions are squashed and replayed, analogous to branch misprediction recovery.
\end{itemize}

To convert this unutilized execution capacity into productive compute throughput, architects turn from Instruction-Level Parallelism to \textit{Thread-Level Parallelism (TLP)}. By maintaining multiple independent thread contexts on a single physical core, \textit{hardware multithreading} allows instructions from alternative threads to fill pipeline bubbles when one thread is stalled or lacks sufficient ILP.

\subsection{Taxonomy of Hardware Multithreading}

Hardware multithreading is classified into three foundational microarchitectural strategies based on how thread switching is scheduled across time and execution resources:

\subsubsection{Fine-Grained (Interleaved / Barrel) Multithreading}\label{sec:barrel_multithreading}
In fine-grained multithreading, the instruction fetch and issue logic switches between active threads on every consecutive clock cycle in a deterministic, round-robin sequence. 
\begin{itemize}
    \item \textbf{Hazard Elimination}: If a processor pipeline has $k$ stages and the hardware interleaves $N \ge k$ independent threads, no two instructions from the same thread can simultaneously occupy the pipeline. Consequently, data hazards, control hazards, and pipeline stalls are completely eliminated by structural design, requiring zero forwarding multiplexers and zero interlock logic!
    
    \item \textbf{Historical Implementations}: Fine-grained multithreading was pioneered in the peripheral processors of the CDC 6600, the Denelcor HEP (Heterogeneous Element Processor), and the Tera MTA (Multi-Threaded Architecture), which maintained up to 128 hardware thread contexts per processor \cite{thornton1964, smith1978hep}.
    
    \item \textbf{Trade-offs}: Fine-grained multithreading maximizes overall processor throughput and tolerates short execution latencies effortlessly. However, it slows down the individual execution time (latency) of a single thread, because an individual thread only executes one instruction every $N$ cycles even if all other threads are idle.
\end{itemize}

\subsubsection{Coarse-Grained (Blocked) Multithreading}
Coarse-grained multithreading executes instructions from a single primary thread continuously at full speed until that thread encounters a \textbf{long-latency event}---most commonly a level-2 or level-3 data cache miss that requires off-chip memory access.
\begin{itemize}
    \item When a stall is detected, the hardware traps execution, drains or freezes the stalled thread's pipeline state, and context-switches to an alternate ready thread.
    \item \textbf{Historical Implementations}: Implemented in machines such as the IBM Northstar (RS64-IV) and commercial network processors.
    \item \textbf{Trade-offs}: Unlike fine-grained multithreading, coarse-grained multithreading preserves peak single-thread execution latency under normal operation. However, the thread-switch itself incurs a non-zero latency penalty (the \emph{pipeline switch overhead}) to drain and prime the pipeline stages. Consequently, coarse-grained multithreading is effective only for very long stalls (tens to hundreds of cycles), and cannot hide short hazards such as ALU dependencies or branch mispredictions.
\end{itemize}

\subsubsection{Simultaneous Multithreading (SMT)}
\textit{Simultaneous Multithreading (SMT)}, introduced in landmark research by Dean M. Tullsen, Susan J. Eggers, and Henry M. Levy \cite{tullsen1995simultaneous}, does not restrict instruction issue to a single thread in any given cycle. Instead, SMT dynamically issues instructions from multiple independent threads within the same clock cycle to the shared pool of out-of-order execution units:
\begin{itemize}
    \item SMT simultaneously attacks both horizontal and vertical waste: if Thread 0 can only provide 2 ready instructions in a 4-issue machine, the dispatch logic fills the remaining 2 slots with ready instructions from Thread 1 or Thread 2.
    \item If Thread 0 suffers an L3 cache miss, the execution window is not left idle; instructions from other active threads immediately occupy the functional units.
    \item \textbf{Commercial Implementations}: Intel Hyper-Threading (introduced in the Pentium 4 Xeon and pervasive across modern Core architectures), IBM POWER5 through POWER10 (supporting up to 8 SMT threads per core, SMT8), and AMD Zen (SMT2).
\end{itemize}

\subsection{Hardware Resource Sharing in Multithreaded Processors}

Hardware multithreading is fundamentally an organizational optimization rather than an architectural reinvention. To the software running on each thread, the processor appears as an independent, private single-threaded core executing standard sequential machine code. 

The microarchitecture achieves this efficiency by selectively replicating low-cost architectural state while sharing expensive execution and memory structures:
\begin{enumerate}
    \item \textbf{Replicated per Thread (Architectural Context)}:
    \begin{itemize}
        \item Program Counter (PC) and instruction fetch buffers.
        \item Architectural Register File (or per-thread register alias tables in renamed out-of-order cores).
        \item Return Address Stack (RAS) for function return prediction.
        \item Control and Status Registers (CSRs), including interrupt mask registers and page table base pointers.
    \end{itemize}
    \item \textbf{Shared Dynamically Across All Threads}:
    \begin{itemize}
        \item Execution units (integer ALUs, floating-point units, address generation units, branch units).
        \item Common Data Bus (CDB) and forwarding networks.
        \item Memory hierarchy (L1 instruction and data caches, unified L2/L3 caches, Translation Lookaside Buffers).
        \item Branch Target Buffers (BTBs) and pattern history tables (PHTs), often indexed using thread ID bits to prevent cross-thread aliasing.
    \end{itemize}
    \item \textbf{Statically or Dynamically Partitioned}:
    \begin{itemize}
        \item Reorder Buffer (ROB) entries: Modern SMT cores often dynamically partition the ROB or maintain separate per-thread commit pointers to ensure that a stalled thread cannot monopolize ROB entries and starve other threads (a condition known as ROB starvation).
        \item Load and Store Queue (LSQ) buffers to enforce independent memory disambiguation per thread.
    \end{itemize}
\end{enumerate}

\subsection{Architectural Interface and Support for Multithreading}

Although hardware multithreading is implemented primarily within the microarchitecture, it requires three architectural support:

\begin{enumerate}
    \item \textbf{Hardware Thread Identification}:
    The instruction set must provide an unprivileged or supervisor mechanism for software to determine which physical thread context it is executing upon. In RISC-V, this is formalized through the \texttt{mhartid} (Machine Hardware Thread ID) register, which assigns a unique integer identifier to each hardware execution thread (\emph{hart}) in the system.
    
    \item \textbf{Atomic Synchronization Primitives}:
    When multiple hardware threads execute concurrently and share a common address space, software must coordinate access to shared memory variables without race conditions. The processor must provide atomic read-modify-write instructions:
    \begin{itemize}
        \item In RISC-V, concurrent memory synchronization is formalized by the \textbf{Standard `A' Extension (Atomic Instructions)} \cite{riscv-spec}:
        \begin{itemize}
            \item \textbf{Load-Reserved / Store-Conditional (\texttt{lr.w} / \texttt{sc.w})}: Enables lock-free optimistic synchronization primitives.
            \item \textbf{Atomic Memory Operations (AMOs)}: Monolithic read-modify-write instructions executed directly at memory/cache controllers, including \texttt{amoadd.w}, \texttt{amoswap.w}, \texttt{amoand.w}, and \texttt{amomax.w}.
        \end{itemize}
    \end{itemize}

    \item \textbf{Memory Consistency Models and Fences}:
    In a multithreaded core with out-of-order memory execution, load and store operations from one thread may be observed by another thread out of program order. To guarantee deterministic memory synchronization:
    \begin{itemize}
        \item The architecture defines a formal \textit{Memory Consistency Model} (such as RISC-V Weak Memory Ordering, \emph{RVWMO}, or Total Store Order, \emph{TSO}).
        
        \item The ISA provides explicit memory fence instructions (\texttt{fence} and \texttt{fence.i}) allowing software to enforce strict ordering between preceding and succeeding memory accesses across threads.
    \end{itemize}
\end{enumerate}


\section{Memory Hierarchy and Cache Optimization}\label{sec:memory_optimization}
\index{memory hierarchy: tiered storage organization from fast registers to slow auxiliary storage}
\index{cache memory!organization and optimization}
\index{memory wall: increasing disparity between processor clock speed and memory latency}
\index{locality principle: temporal and spatial tendency of program access patterns}

As demonstrated in Chapter \ref{ch:von_neumann_4-OS}, the classical von Neumann abstract model conceptualizes storage as a uniform, flat linear address space where instructions and operands reside together without microarchitectural hierarchy. In early computers such as the EDVAC and the Princeton IAS machine, the central processing unit interacted directly with a single memory technology (such as mercury acoustic delay lines or electrostatic Williams tubes) at uniform speed \cite{vonNeumann1945}.

However, modern high-performance microprocessors cannot operate directly against a single flat memory store. While processor execution pipelines have achieved multi-gigahertz clock frequencies and aggressive superscalar issue rates, dense semiconductor memory (DRAM) is governed by analog charge transfer dynamics that improve at an incomparably slower pace. Consequently, caching and memory hierarchy optimization are indispensable microarchitectural mechanisms designed to bridge this performance chasm.

\subsection{The Processor-Memory Performance Gap and the Memory Wall}\label{sec:memory_wall}

Throughout the history of semiconductor microprocessors, processing logic and primary memory followed dramatically divergent technological trajectories.

Between 1980 and the mid-2000s, microprocessor performance expanded at an extraordinary rate of approximately $52\%$ per year \cite{Hennessy19}. This unprecedented growth was sustained by the simultaneous convergence of architectural innovations (deep instruction pipelining, superscalar multi-issue, dynamic out-of-order execution, and branch prediction) and physical device scaling governed by Robert Dennard's MOSFET scaling laws. Dennard scaling permitted transistor switching speeds to increase in direct proportion to circuit density while maintaining constant power density per unit chip area.

In contrast, commodity Dynamic RAM (DRAM) followed an optimization trajectory focused overwhelmingly on capacity and cost-per-bit rather than access latency. Storing a bit of information in DRAM requires charging or discharging a minute capacitor through a single access transistor (the 1T-1C cell). The physics of capacitive charge transfer, long capacitive bitline charging delays, analog sense amplifier sensing times, and external bus multiplexing severely constrained latency improvements. Over the same era, DRAM access latency improved at an average rate of only $\sim 7\%$ per year \cite{Patterson97}.

In 1995, Wm. A. Wulf and Sally A. McKee formalized this divergence and coined the term \textit{The Memory Wall} \cite{wulf1995hitting}. They proved that because processor clock speeds improve exponentially faster than memory access times, the fraction of execution time spent waiting for off-chip memory references approaches $100\%$, rendering further processor frequency gains completely futile unless accompanied by aggressive caching and memory latency hiding techniques.

\subsection{The Locality Principle}\label{locprinc}
\index{locality principle: temporal and spatial tendency of program access patterns}
\index{locality principle!temporal locality}
\index{locality principle!spatial locality}

Despite the formidable gap between processor and DRAM speeds, computer systems achieve high performance because programs do not reference memory uniformly or randomly. Instead, empirical program execution strongly adheres to the \textit{Locality Principle}:

\paragraph{Temporal Locality (Locality in Time)}
If a specific memory location is referenced at time $t$, there is a high probability that the exact same location will be referenced again in the near future ($t + \Delta t$).
Temporal locality is exhibited by:
\begin{itemize}
    \item \textbf{Program Loops}: Repeatedly executing the same sequence of instructions within an iterative loop body.
    \item \textbf{Scalar Variables}: Frequently reading and updating loop induction variables, counters, and accumulators.
    \item \textbf{Call Stack}: Repeatedly accessing local variables, return pointers, and parameters residing at the top of the stack frame.
\end{itemize}

\paragraph{Spatial Locality (Locality in Space)}
If a memory location at address $A$ is referenced, there is a high probability that memory locations residing physically near $A$ (i.e., in the range $A \pm \delta$) will be referenced soon.
Spatial locality is exhibited by:
\begin{itemize}
    \item \textbf{Sequential Instruction Execution}: Instructions are fetched sequentially from contiguous program memory addresses, punctuated only by occasional branch instructions.
    \item \textbf{Array and Vector Traversals}: Processing elements of one-dimensional arrays, matrices, vectors, or string buffers stored in contiguous memory rows.
    \item \textbf{Record and Object Fields}: Reading adjacent fields stored sequentially within a common data structure or class instance.
\end{itemize}

The locality principle provides the theoretical foundation for memory hierarchy design. By transferring blocks (lines) of contiguous bytes upon a miss (exploiting spatial locality) and retaining recently accessed blocks in small, fast SRAM buffers positioned immediately adjacent to the processor core (exploiting temporal locality), the memory hierarchy creates the effective illusion of a storage system that is simultaneously as fast as the smallest on-chip SRAM register and as vast and inexpensive as off-chip DRAM.

\subsection{Cache Memory Microarchitecture}\label{sec:cache_microarchitecture}
\index{cache memory!placement policies}
\index{cache memory!address decomposition}
\index{cache memory!write policies}
\index{cache memory!miss classification (3 Cs)}
\index{average memory access time (AMAT)}

The concept of a cache memory was first articulated by Maurice Wilkes in 1965 as a \cite{wilkes1965slave} and was commercially implemented in hardware in the IBM System/360 Model 85 in 1968 \cite{liptay1968cache}. 

\subsubsection{Cache Organization and Address Decomposition}
A cache is organized into an array of $S$ sets, where each set contains $N$ cache lines (or blocks). Each cache line stores $B = 2^b$ bytes of contiguous data along with a \textit{Tag} and metadata status bits (a \textit{Valid bit} indicating valid data, and a \textit{Dirty bit} indicating modified data in write-back caches).

When the CPU issues an $m$-bit physical memory address, the cache hardware decomposes the address into three orthogonal bitfields:
\begin{equation}
\underbrace{a_{m-1} \quad \cdots \quad a_{s+b}}_{\text{Tag } (t \text{ bits})} \quad\mid\quad \underbrace{a_{s+b-1} \quad \cdots \quad a_b}_{\text{Index } (s \text{ bits})} \quad\mid\quad \underbrace{a_{b-1} \quad \cdots \quad a_0}_{\text{Block Offset } (b \text{ bits})}
\end{equation}
where:
\begin{itemize}
    \item \textbf{Block Offset} ($b = \log_2 B$ bits): Selects the specific byte(s) within the $B$-byte cache line.
    \item \textbf{Set Index} ($s = \log_2 S$ bits): Selects exactly one of the $S$ sets in the cache array.
    \item \textbf{Tag} ($t = m - s - b$ bits): Uniquely identifies which physical memory block is currently occupying that cache line.
\end{itemize}

The total data capacity of the cache is $C = S \times N \times B$ bytes.

\subsubsection{Cache Placement Policies}
Caches are categorized according to their associativity, which defines how many locations in the cache a given memory block can occupy:
\begin{enumerate}
    \item \textbf{Direct-Mapped Cache ($N = 1$)}: Each memory block maps to exactly one predetermined set:
    \[
    \text{Set Index} = (\text{Block Address}) \pmod S
    \]
    Direct-mapped caches require only a single tag comparator and zero multiplexing logic, providing the fastest hit time. However, if two frequently accessed memory blocks share the same index, they will repeatedly evict each other in a destructive cycle known as \textit{thrashing}.
    
    \item \textbf{Set-Associative Cache ($N$-Way Associative, $N > 1$)}: Each set contains $N$ distinct line slots (ways). A memory block maps to a specific set based on its index bits, but can reside in any of the $N$ ways within that set. The cache controller checks all $N$ tags concurrently using $N$ parallel comparators. Set associativity drastically reduces conflict misses at the expense of slightly higher lookup latency and silicon area.
    
    \item \textbf{Fully Associative Cache ($S = 1, N = C/B$)}: There are no set index bits ($s = 0$, so $t = m - b$). Any memory block can reside in any cache line in the entire array. Finding a block requires searching every line simultaneously using Content-Addressable Memory (CAM) cells or parallel comparators. Because fully associative search logic is silicon-intensive, it is typically restricted to small, latency-critical structures such as Translation Lookaside Buffers (TLBs) and small victim caches.
\end{enumerate}

\subsubsection{Cache Replacement Policies}
When a miss occurs in an $N$-way set-associative cache and all $N$ ways in the target set are currently occupied, one block must be evicted to make room for the newly fetched line. Common replacement strategies include:
\begin{itemize}
    \item \textbf{Least Recently Used (LRU)}: Tracks access history and replaces the block that has remained unreferenced for the longest period. LRU provides the lowest miss rates for typical workloads but requires $N(N-1)/2$ state bits per set to implement true LRU ordering.
    \item \textbf{Pseudo-LRU (PLRU)}: Approximates LRU using a binary decision tree requiring only $N - 1$ bits per set, providing near-LRU hit rates with minimal hardware overhead.
    \item \textbf{Random Replacement}: Selects an eviction victim uniformly at random using a pseudorandom number generator. Requires zero state bits per line and performs remarkably close to LRU for large cache capacities.
\end{itemize}

\subsubsection{Write Policies}
Because store instructions modify cache data, the microarchitecture must maintain memory consistency between the cache and lower memory levels:
\begin{itemize}
    \item \textbf{Write-Through}: Every store operation updates both the cache line and the underlying backing memory simultaneously. To prevent processor stalls on writes, stores are enqueued in a \textbf{Write Buffer}. While simple and inherently coherent, write-through creates high write traffic on the memory bus.
    \item \textbf{Write-Back}: Stores update only the cache line, setting a 1-bit \textbf{Dirty bit} in the line's tag array. The line is written back to main memory only when it is evicted. Write-back drastically reduces memory bus traffic because multiple updates to the same cache line occur entirely in SRAM without off-chip transactions.
    \item \textbf{Allocation on Write Miss}: A \textbf{Write-Allocate} cache fetches the entire block into the cache upon a write miss (typically paired with write-back). A \textbf{No-Write-Allocate} (write-around) cache bypasses the cache and updates lower memory directly upon a write miss (typically paired with write-through).
\end{itemize}

\subsubsection{The 3 Cs Model of Cache Misses}
\index{cache misses!compulsory (cold)}
\index{cache misses!capacity}
\index{cache misses!conflict}
\index{Hill, Mark D.}

In his doctoral dissertation, \textbf{Mark D. Hill} formalized the classic \textit{3 Cs model} to classify cache misses into three distinct categories based on their underlying cause \cite{hill1987aspects}:
\begin{enumerate}
    \item \textbf{Compulsory (Cold) Misses}: The very first reference to a memory block. Because the block has never been loaded into the cache, compulsory misses cannot be avoided by altering cache capacity or associativity. They can only be reduced by increasing the block size $B$ (which prefetches contiguous data via spatial locality) or through speculative hardware prefetching.
    \item \textbf{Capacity Misses}: Misses that occur because the cache cannot contain all the blocks needed to execute the program's active working set. A capacity miss occurs when a previously accessed block was evicted solely because the total cache capacity $C$ was exhausted. Capacity misses can be eliminated only by increasing total cache size.
    \item \textbf{Conflict (Collision) Misses}: Misses that occur in direct-mapped or set-associative caches when multiple active memory blocks map to the very same set index, evicting each other even though the total cache capacity has not been exhausted. Conflict misses are nonexistent in fully associative caches and decrease monotonically as associativity $N$ increases.
\end{enumerate}
In multiprocessor shared-memory systems, a fourth category---the \textbf{Coherence Miss} (the 4th C)---occurs when a cache line is invalidated by a write operation from another processor core.

\subsubsection{Multi-Level Caches and Average Memory Access Time (AMAT)}
To balance the competing requirements of single-cycle hit latency and low miss rates, modern processors organize caches into hierarchical levels (L1, L2, and L3):
\begin{itemize}
    \item \textbf{Level 1 (L1)}: Split into dedicated L1 Instruction (L1i) and L1 Data (L1d) caches ($32\text{--}64\,\text{KB}$ each, 4- to 8-way associative), operating at full core clock frequency with $1\text{--}4$ cycle hit latency.
    \item \textbf{Level 2 (L2)}: Typically unified per-core cache ($512\,\text{KB}\text{--}2\,\text{MB}$, 8- to 16-way associative, $10\text{--}14$ cycle latency).
    \item \textbf{Level 3 (L3)}: Shared Last-Level Cache (LLC) across all cores ($16\text{--}128\,\text{MB}$, 16- to 32-way associative, $30\text{--}50$ cycle latency).
\end{itemize}

The performance of a memory hierarchy is quantified by \textbf{Average Memory Access Time (AMAT)}:
\begin{equation}
\text{AMAT} = t_{\text{hit}, L1} + m_{L1} \times \text{Miss Penalty}_{L1}
\end{equation}
where $m_{L1}$ is the L1 miss rate. In a three-level hierarchy backed by off-chip DRAM:
\begin{equation}
\text{Miss Penalty}_{L1} = t_{\text{hit}, L2} + m_{\text{local}, L2} \times \left( t_{\text{hit}, L3} + m_{\text{local}, L3} \times t_{\text{DRAM}} \right)
\end{equation}
where $m_{\text{local}, L2}$ and $m_{\text{local}, L3}$ represent the \textbf{local miss rates} of the L2 and L3 caches respectively.

\subsection{Virtual Memory and Translation Lookaside Buffers (TLBs)}\label{lb:vmm}\label{sec:virtual_memory_tlb}
\index{virtual memory: architectural technique abstracting physical memory using page translation}
\index{translation lookaside buffer (TLB): cache of recent virtual-to-physical address translations}
\index{content-addressable memory (CAM)!TLB implementation}

Just as cache memory transparently bridges the processor-DRAM gap, \textbf{Virtual Memory} bridges primary DRAM and secondary storage (SSDs/HDDs):
\begin{enumerate}
    \item \textbf{Address Space Virtualization}: Each process is granted the illusion of a vast, contiguous, private linear address space independent of actual physical memory size.
    \item \textbf{Protection and Isolation}: Hardware access permissions (Read, Write, Execute) prevent erroneous or malicious processes from corrupting the address spaces of the operating system or other user tasks.
    \item \textbf{Demand Paging}: Pages are brought into physical DRAM from secondary storage only when referenced, allowing programs whose memory requirements exceed physical RAM capacity to execute seamlessly.
\end{enumerate}

\subsubsection{Page Translation Mechanics}
In a paged virtual memory system, the virtual and physical address spaces are partitioned into fixed-size blocks called \textbf{Pages} and \textbf{Page Frames} (typically $4\,\text{KB}$ in size, with optional $2\,\text{MB}$ and $1\,\text{GB}$ huge pages). 

As shown in Figure \ref{vmm}a, physical memory ($Level_i$, containing $m$ frames) holds an active subset of the pages residing in the much larger virtual address space ($Level_{i+1}$, containing $n$ pages, with $n \gg m$).

\placedrawing[H]{figures/06_04_virtual_memory.lp}{Virtual memory mechanism. {\bf a.} Page correspondence between virtual and physical levels. {\bf b.} Address translation mechanism mediated by the page translator.}{vmm}

The CPU generates a virtual address composed of two fields (Figure \ref{vmm}b):
\begin{itemize}
    \item \textbf{Virtual Page Number (VPN)}: The upper address bits specifying the requested virtual page.
    \item \textbf{Page Offset}: The lower address bits specifying the byte offset within the page. For a page size of $P = 2^p$ bytes, the offset is $p$ bits wide ($p = 12$ for a $4\,\text{KB}$ page). Because the page size is identical in both virtual and physical spaces, the offset passes through translation unperturbed.
\end{itemize}

The page translation hardware converts the Virtual Page Number into a Physical Page Number (PPN), which concatenates with the page offset to form the physical address for DRAM access.

\subsubsection{Associative Memory (CAM)-Based Translation Lookaside Buffer (TLB)}
Because page table structures reside in main memory, performing a full memory-based page table walk on every instruction fetch and data operand access would double or quadruple memory access latency. To eliminate this penalty, processors incorporate a specialized high-speed cache of recent address translations called the \textit{Translation Lookaside Buffer (TLB)}.

Two fundamental circuit strategies exist for implementing the page translation mechanism:
\begin{enumerate}
    \item \textbf{RAM-Based Lookup Table}: A direct RAM lookup structure would require an entry for each of the $n$ virtual pages ($n$ words of $\log_2 m$ bits). Because $n \gg m$, the overwhelming majority of entries in such a RAM are empty or invalid at any given moment; in Figure \ref{vmm}a, only $m$ of the $n$ locations are actively populated, yielding a memory utilization efficiency of at most $(m/n)\%$. The silicon area scales as $O(n \times (\log m + \log n))$.
    
    \item \textbf{Associative Memory (CAM)-Based TLB}: Rather than dimensioning the table to the vast virtual address space $n$, an \textit{Associative Memory (AM)} dimensions the structure to match the physical page capacity $m$. The TLB consists of:
    \begin{itemize}
        \item A Content-Addressable Memory (CAM) array of $m$ entries holding the active Virtual Page Numbers (tags) of length $\log_2 n$ bits (see Section \ref{assocMemory} and Section \ref{lb:cam}).
        \item A paired RAM data array of $m$ entries holding the corresponding Physical Page Numbers of length $\log_2 m$ bits.
    \end{itemize}
    When the CPU presents a virtual address, the CAM compares the incoming VPN against all $m$ entries in parallel within a fraction of a clock cycle. When a match occurs, the corresponding line enables the PPN from the RAM array.
\end{enumerate}

The dimensioning and silicon area occupied by the two alternatives scale as:
\begin{equation}
S_{\text{TLB}}(\text{RAM}) \in O(n \times (\log m + \log n)) \quad \text{versus} \quad S_{\text{TLB}}(\text{AM}) \in O(m \times (\log m + \log n))
\end{equation}
The area reduction factor achieved by the associative CAM approach is:
\begin{equation}
\frac{S_{\text{TLB}}(\text{RAM})}{S_{\text{TLB}}(\text{AM})} \in O(n/m)
\end{equation}
Even though a CAM bit cell (see Figure \ref{cam_cell}) requires more transistors than a standard SRAM cell due to internal comparison logic, the enormous ratio $n/m$ (often $10^3\text{--}10^6$) renders the associative CAM implementation vastly smaller, faster, and more energy-efficient.

\begin{problem}
\textbf{Pipeline Speedup and Imbalance Analysis}:
Consider an unpipelined processor where the major datapath operations have the following latencies:
Instruction Fetch ($\text{IF}$) = $250\,\text{ps}$,
Operand Fetch / Decode ($\text{OF}$) = $150\,\text{ps}$,
Execute ($\text{EX}$) = $320\,\text{ps}$,
Memory Access ($\text{MEM}$) = $380\,\text{ps}$,
Write Back ($\text{WB}$) = $150\,\text{ps}$.
Suppose the processor is partitioned into a 5-stage pipeline ($\text{IF}, \text{OF}, \text{EX}, \text{MEM}, \text{WB}$). Adding pipeline registers between each stage introduces a setup and clock-to-Q latch overhead of $t_{\text{reg}} = 30\,\text{ps}$ per stage.
\begin{enumerate}
    \item Determine the minimum clock period and operating frequency for both the unpipelined and pipelined processors.
    \item Calculate the ideal speedup achieved by pipelining for an arbitrarily large number of instructions ($N \to \infty$), assuming zero hazard stalls.
    \item Suppose that due to data load delays and branch mispredictions, dynamic execution incurs an average penalty of 0.25 stall cycles per instruction. What is the actual speedup achieved over the unpipelined core?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item For the unpipelined processor, an instruction executes sequentially through all five functional blocks in a single clock cycle:
    \[
    T_{\text{unpipe}} = 250 + 150 + 320 + 380 + 150 = 1250\,\text{ps} \quad (f_{\text{unpipe}} = 800\,\text{MHz})
    \]
    For the 5-stage pipelined processor, the clock cycle is limited by the critical path of the slowest (bottleneck) stage plus the pipeline register overhead:
    \[
    T_{\text{pipe}} = \max(250, 150, 320, 380, 150) + t_{\text{reg}} = 380\,\text{ps} + 30\,\text{ps} = 410\,\text{ps} \quad (f_{\text{pipe}} \approx 2.439\,\text{GHz})
    \]
    \item Under ideal conditions with no stalls, the pipelined processor retires 1 instruction per cycle ($\text{CPI}_{\text{pipe}} = 1.0$), while the unpipelined processor executes 1 instruction per cycle with clock period $T_{\text{unpipe}}$ ($\text{CPI}_{\text{unpipe}} = 1.0$). The ideal speedup is:
    \[
    S_{\text{ideal}} = \frac{T_{\text{unpipe}}}{T_{\text{pipe}}} = \frac{1250\,\text{ps}}{410\,\text{ps}} \approx 3.049\times
    \]
    Notice that the speedup is significantly less than the number of stages ($k = 5$) due to stage imbalance (the $380\,\text{ps}$ MEM stage vs. $150\,\text{ps}$ stages) and register overhead ($30\,\text{ps}$).
    \item With $0.25$ stall cycles per instruction, the average CPI of the pipelined processor increases to $\text{CPI}_{\text{actual}} = 1.0 + 0.25 = 1.25$. The actual speedup becomes:
    \[
    S_{\text{actual}} = \frac{\text{CPI}_{\text{unpipe}} \times T_{\text{unpipe}}}{\text{CPI}_{\text{actual}} \times T_{\text{pipe}}} = \frac{1.0 \times 1250\,\text{ps}}{1.25 \times 410\,\text{ps}} = \frac{1250}{512.5} \approx 2.439\times
    \]
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
\textbf{Forwarding Unit Hazard Equations and Priority}:
In the pipelined toyRISC processor with forwarding, the Execute stage ($\text{EX}$) receives operands selected from the register file, from \texttt{PipeReg\_3} (holding the result of the instruction issued 1 cycle earlier), or from \texttt{PipeReg\_4} (holding the result of the instruction issued 2 cycles earlier).
\begin{enumerate}
    \item Specify the Boolean logic expressions for selecting the left ALU operand multiplexer control signals ($\text{ForwardA}$).
    \item Consider the following assembly code snippet:
\begin{verbatim}
    ADD(1, 2, 3)  ;   // rf[1] <= rf[2] + rf[3]
    ADD(1, 4, 5)  ;   // rf[1] <= rf[4] + rf[5]
    SUB(6, 1, 7)  ;   // rf[6] <= rf[1] - rf[7]
\end{verbatim}
Trace the contents of \texttt{PipeReg\_3}, \texttt{PipeReg\_4}, and \texttt{PipeReg\_2} when \texttt{SUB} enters the Execute stage. Explain why a naive forwarding unit that checks \texttt{PipeReg\_4} without masking by \texttt{PipeReg\_3} would produce an erroneous architectural result.
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Let $\text{ForwardA} = 01$ select \texttt{result3} from \texttt{PipeReg\_3}, $\text{ForwardA} = 10$ select \texttt{result4} from \texttt{PipeReg\_4}, and $\text{ForwardA} = 00$ select the register file output. The Boolean conditions are:
    \begin{align*}
    \text{ForwardA}_{01} &= \texttt{RegWrite\_3} \land (\texttt{rd\_3 == rs1\_2}) \\
    \text{ForwardA}_{10} &= \texttt{RegWrite\_4} \land (\texttt{rd\_4 == rs1\_2}) \land \neg(\texttt{RegWrite\_3} \land (\texttt{rd\_3 == rs1\_2}))
    \end{align*}
    \item When \texttt{SUB(6,1,7)} reaches the Execute stage:
    \begin{itemize}
        \item \texttt{PipeReg\_2} holds \texttt{SUB(6,1,7)} with source register $\texttt{rs1} = 1$.
        \item \texttt{PipeReg\_3} holds the second \texttt{ADD(1,4,5)} with destination register $\texttt{rd} = 1$.
        \item \texttt{PipeReg\_4} holds the first \texttt{ADD(1,2,3)} with destination register $\texttt{rd} = 1$.
    \end{itemize}
    Both \texttt{PipeReg\_3} and \texttt{PipeReg\_4} have $\texttt{rd} = 1$, matching $\texttt{rs1} = 1$. However, in program order, the second instruction (\texttt{ADD(1,4,5)}) overwrote the value computed by the first. If the hardware does not prioritize \texttt{PipeReg\_3} over \texttt{PipeReg\_4}, the forwarding unit might select the stale result from the older instruction in \texttt{PipeReg\_4}, violating RAW data integrity. Masking the \texttt{PipeReg\_4} condition with $\neg(\texttt{RegWrite\_3} \land (\texttt{rd\_3 == rs1\_2}))$ guarantees that the newest program value is always consumed.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
\textbf{Branch Predictor Performance and CPI Penalty}:
A pipelined processor executes a dynamic benchmark where 20\% of all executed instructions are conditional branches. Due to the branch resolution latency in the pipeline, each mispredicted branch incurs a 3-cycle flush penalty, whereas a correctly predicted branch incurs 0 penalty cycles.
Assume that 70\% of all executed conditional branches are taken in practice.
\begin{enumerate}
    \item Calculate the effective CPI (assuming ideal $\text{CPI}_{\text{base}} = 1.0$) for a static branch predictor that predicts Always Not Taken.
    \item Calculate the effective CPI for a 1-bit dynamic predictor that achieves an 82\% prediction accuracy on this workload.
    \item Calculate the effective CPI for a 2-bit saturating counter dynamic predictor that achieves a 93\% prediction accuracy.
    \item What is the percentage speedup of the 2-bit predictor over the static Always Not Taken predictor?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item The general formula for CPI including branch misprediction penalty is:
    \[
    \text{CPI} = \text{CPI}_{\text{base}} + (\text{Branch Frequency}) \times (\text{Misprediction Rate}) \times (\text{Penalty})
    \]
    For the static Always Not Taken predictor, every branch that is actually taken is mispredicted. Since 70\% of branches are taken, the misprediction rate is $0.70$:
    \[
    \text{CPI}_{\text{static}} = 1.0 + 0.20 \times 0.70 \times 3 = 1.0 + 0.420 = 1.420
    \]
    \item For the 1-bit dynamic predictor with 82\% accuracy, the misprediction rate is $1.0 - 0.82 = 0.18$ (18\%):
    \[
    \text{CPI}_{\text{1-bit}} = 1.0 + 0.20 \times 0.18 \times 3 = 1.0 + 0.108 = 1.108
    \]
    \item For the 2-bit saturating counter predictor with 93\% accuracy, the misprediction rate is $1.0 - 0.93 = 0.07$ (7\%):
    \[
    \text{CPI}_{\text{2-bit}} = 1.0 + 0.20 \times 0.07 \times 3 = 1.0 + 0.042 = 1.042
    \]
    \item The execution speedup of the 2-bit predictor over the static Always Not Taken predictor is:
    \[
    \text{Speedup} = \frac{\text{CPI}_{\text{static}}}{\text{CPI}_{\text{2-bit}}} = \frac{1.420}{1.042} \approx 1.3628 \implies \mathbf{36.3\% \text{ speedup}}
    \]
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
\textbf{Associative Memory-Based Page Translator Design}:
Design a page translation system based on an associative memory (see Section \ref{assocMemory} and Section \ref{lb:cam} in this book). The principle is described in Section \ref{lb:vmm}. Consider pages of $1\,\text{KW}$ ($1024$ 32-bit words) in a physical memory space of $1024$ pages ($m = 1024$) and a virtual memory space of $1024^2$ pages ($n = 1024^2 = 1{,}048{,}576$).
\begin{enumerate}
    \item Determine the total number of bits in the virtual address, the physical address, and the page offset.
    \item Calculate the total memory storage capacity in bits required for a conventional flat RAM-based page table versus an associative CAM-based Translation Lookaside Buffer (TLB).
    \item Derive the memory storage savings factor achieved by the associative implementation.
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Each page contains $1\,\text{KW} = 1024 = 2^{10}$ words. With byte-addressable 32-bit words (4 bytes/word), a page is $4096\,\text{B} = 2^{12}$ bytes, requiring a $12$-bit page offset ($p = 12$).
    \begin{itemize}
        \item Physical space contains $m = 1024 = 2^{10}$ pages. The Physical Page Number (PPN) requires $\log_2(1024) = 10$ bits. The physical address is $10 + 12 = 22$ bits ($4\,\text{MB}$).
        \item Virtual space contains $n = 1024^2 = 2^{20}$ pages. The Virtual Page Number (VPN) requires $\log_2(2^{20}) = 20$ bits. The virtual address is $20 + 12 = 32$ bits ($4\,\text{GB}$).
    \end{itemize}
    \item Memory requirements:
    \begin{itemize}
        \item \textbf{RAM-Based Lookup Table}: Must allocate an entry for every virtual page ($n = 2^{20}$). Each entry stores at least the 10-bit PPN plus a valid bit (11 bits total):
        \[
        \text{RAM Size} = 2^{20} \times 11\,\text{bits} \approx 11{,}534{,}336\,\text{bits} \approx 1.376\,\text{MB}
        \]
        \item \textbf{Associative CAM-Based TLB}: Stores only the active mappings for physical pages ($m = 1024 = 2^{10}$). Each entry consists of a 20-bit CAM tag (VPN) plus a 10-bit RAM data field (PPN) and status bits (valid/dirty $\approx 2$ bits), totaling 32 bits per entry:
        \[
        \text{CAM TLB Size} = 1024 \times 32\,\text{bits} = 32{,}768\,\text{bits} = 4\,\text{KB}
        \]
    \end{itemize}
    \item The memory savings ratio achieved by the associative implementation is:
    \[
    \text{Savings Ratio} = \frac{11{,}534{,}336\,\text{bits}}{32{,}768\,\text{bits}} \approx 352\times
    \]
    The associative CAM reduces the translation storage hardware footprint by over $350\times$, while providing simultaneous single-cycle translation for all resident pages.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
\textbf{Multi-Level Cache Performance and AMAT Analysis}:
A processor operates at a clock frequency of $4.0\,\text{GHz}$ ($\tau = 0.25\,\text{ns}$) and executes a benchmark workload where $30\%$ of all instructions are data memory references (loads and stores). The baseline datapath achieves an ideal $\text{CPI}_{\text{base}} = 1.0$ assuming perfect cache hits.
The memory hierarchy consists of:
\begin{itemize}
    \item \textbf{L1 Data Cache}: $64\,\text{KB}$, 4-way set-associative, 64-byte line size, 1-cycle hit latency ($0.25\,\text{ns}$), local miss rate $m_{L1} = 4\%$.
    \item \textbf{L2 Unified Cache}: $512\,\text{KB}$, 8-way set-associative, 64-byte line size, 12-cycle hit latency ($3.0\,\text{ns}$), local miss rate $m_{\text{local}, L2} = 15\%$.
    \item \textbf{L3 Unified Cache}: $8\,\text{MB}$, 16-way set-associative, 64-byte line size, 40-cycle hit latency ($10.0\,\text{ns}$), local miss rate $m_{\text{local}, L3} = 25\%$.
    \item \textbf{Main Memory (DRAM)}: Access latency of $60\,\text{ns}$ ($240$ clock cycles).
\end{itemize}
\begin{enumerate}
    \item For the L1 data cache, determine the bit breakdown (Tag, Index, Block Offset) for a 48-bit physical address space.
    \item Calculate the global miss rate for the L2 and L3 caches.
    \item Calculate the Average Memory Access Time (AMAT) in nanoseconds and clock cycles.
    \item Calculate the effective CPI of the processor accounting for data memory stalls.
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item For the L1 cache:
    \begin{itemize}
        \item Block size $B = 64 = 2^6$ bytes $\implies b = 6$ offset bits.
        \item Cache capacity $C = 64\,\text{KB} = 65{,}536$ bytes, associativity $N = 4$.
        \item Number of sets $S = \frac{C}{N \times B} = \frac{65{,}536}{4 \times 64} = 256 = 2^8 \implies s = 8$ index bits.
        \item Tag bits $t = 48 - s - b = 48 - 8 - 6 = 34$ bits.
    \end{itemize}
    \item Global miss rates:
    \begin{align*}
    m_{\text{global}, L2} &= m_{L1} \times m_{\text{local}, L2} = 0.04 \times 0.15 = 0.006 \quad (0.6\%) \\
    m_{\text{global}, L3} &= m_{\text{global}, L2} \times m_{\text{local}, L3} = 0.006 \times 0.25 = 0.0015 \quad (0.15\%)
    \end{align*}
    \item AMAT calculation (measured in processor clock cycles):
    \begin{align*}
    \text{Miss Penalty}_{L2} &= t_{\text{hit}, L3} + m_{\text{local}, L3} \times t_{\text{DRAM}} = 40 + 0.25 \times 240 = 40 + 60 = 100\,\text{cycles} \\
    \text{Miss Penalty}_{L1} &= t_{\text{hit}, L2} + m_{\text{local}, L2} \times \text{Miss Penalty}_{L2} = 12 + 0.15 \times 100 = 12 + 15 = 27\,\text{cycles} \\
    \text{AMAT} &= t_{\text{hit}, L1} + m_{L1} \times \text{Miss Penalty}_{L1} = 1 + 0.04 \times 27 = 1 + 1.08 = 2.08\,\text{cycles}
    \end{align*}
    In nanoseconds: $\text{AMAT} = 2.08 \times 0.25\,\text{ns} = 0.52\,\text{ns}$.
    \item Effective CPI:
    Since memory references account for $30\%$ of instructions, memory stall cycles per instruction are:
    \[
    \text{Stall CPI} = 0.30 \times (\text{AMAT} - t_{\text{hit}, L1}) = 0.30 \times 1.08 = 0.324
    \]
    \[
    \text{CPI}_{\text{effective}} = \text{CPI}_{\text{base}} + \text{Stall CPI} = 1.0 + 0.324 = \mathbf{1.324}
    \]
\end{enumerate}
$\diamond$
\end{problem}

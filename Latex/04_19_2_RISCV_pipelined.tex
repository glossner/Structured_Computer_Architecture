\section{Hardware Implementation of the Pipelined Processor}\label{riscvPipelined}
\index{RISC-V!pipelined implementation}\index{pipelining!4-stage hazard detection and stall}\index{hazard detection unit}\index{pipeline stall}

While the single-cycle processor developed in Section \ref{riscvArch} executes each instruction in a single clock cycle ($\text{CPI} = 1.0$), its operating clock frequency is fundamentally constrained by the cumulative propagation delay across all combinational subsystems within a single clock period:
\begin{equation}
T_{\text{clock, single}} \ge T_{\text{fetch}} + T_{\text{decode}} + T_{\text{ALU}} + T_{\text{dmem}} + T_{\text{wb}} + T_{\text{setup}}.
\end{equation}
In advanced physical processes, this monolithic combinational path limits clock frequencies. To improve computational throughput, this section develops a 4-stage pipelined implementation of the base \texttt{RV32I} processor, designated \texttt{RiscvPipelined} (and explores its extension to \texttt{RV32I\_Zmmul}). Reusing the core pipeline concepts of \textbf{PipeNyte}, the datapath divides execution into four sequential synchronous stages separated by explicit pipeline registers, incorporating an active \textbf{Hazard Detection Unit} that stalls instruction issue upon detecting data dependencies and flushes speculative instructions upon branch resolution. Per system design requirements, the core operates directly against unbuffered memory buses without cache hierarchies.

\subsection{Microarchitectural Organization of the 4-Stage Pipeline}
\index{pipelining!microarchitectural stages}\index{PipeNyte!4-stage architecture}

The 4-stage pipeline partitions the Fetch-Execute cycle into four balanced operational stages (Figure \ref{fig:riscv_4stage_pipeline}):
\begin{enumerate}
    \item \textbf{Stage 1: Instruction Fetch (IF)}:
    Maintains the architectural Program Counter register (\texttt{pcReg}). Drives the unbuffered instruction memory bus (\texttt{io.imem.addr}) and latches the incoming 32-bit instruction word into the \texttt{if\_id} pipeline register. Under normal sequential execution, the PC increments by 4 ($\text{PC} \leftarrow \text{PC} + 4$). When a control transfer (branch or jump) resolves taken in the EX stage, the PC updates to the target address, and the \texttt{if\_id} register is flushed. When a data hazard stall is signaled by the ID stage, the PC and \texttt{if\_id} register are frozen.
    
    \item \textbf{Stage 2: Instruction Decode and Operand Fetch (ID)}:
    Decodes the instruction latched in \texttt{if\_id} using \texttt{RiscvDecoder}, generates sign-extended immediates via \texttt{RiscvImmGen}, and accesses the architectural register file (\texttt{RiscvRegFile}). To eliminate unnecessary stalls between consecutive dependent instructions, the register file incorporates internal \textbf{write-through bypass}: if an instruction currently retiring in the MEM/WB stage writes to the same register address currently being read in ID, the write-back data is forwarded combinationally to the read port.
    
    The ID stage also houses the \textbf{Hazard Detection Unit}. If an instruction in ID depends on a result produced by an in-flight instruction currently in the EX stage, the hazard detection unit asserts a pipeline stall.
    
    \item \textbf{Stage 3: Execute (EX)}:
    Executes arithmetic, logical, and shift operations via the 32-bit executive ALU (\texttt{RiscvALU}), with optional support for the standard \texttt{Zmmul} multiplication extension. The EX stage evaluates branch conditions (\texttt{BEQ}, \texttt{BNE}, \texttt{BLT}, \texttt{BGE}, \texttt{BLTU}, \texttt{BGEU}) and calculates branch/jump target addresses:
    \begin{align}
    \text{Target}_{\text{branch/jal}} &= \text{PC}_{\text{EX}} + \text{imm}_{\text{EX}}, \\
    \text{Target}_{\text{jalr}} &= (\text{rs1}_{\text{EX}} + \text{imm}_{\text{EX}}) \ \& \ \sim 1.
    \end{align}
    Taken control transfers trigger a pipeline redirection, squashing the younger instructions in IF and ID.
    
    \item \textbf{Stage 4: Memory Access and Write-Back (MEM/WB)}:
    Combines data memory access and register file write-back into a unified terminal stage. For load and store instructions, the stage drives \texttt{io.dmem.addr}, \texttt{io.dmem.writeData}, \texttt{io.dmem.funct3}, and read/write strobes. Load data delivered by the memory bus is multiplexed with computational ALU results, upper immediates (\texttt{LUI}), and PC offsets (\texttt{AUIPC}, \texttt{JAL}, \texttt{JALR}) to generate the final write-back operand \texttt{wbData}, which commits synchronously to the register file.
\end{enumerate}

\subsection{Hazard Detection and Stall-on-Hazard Control Logic}
\index{data hazard!RAW stall}\index{hazard detection unit!boolean equations}

Data hazards arise when an instruction in the decode stage requires an operand that has not yet been committed to the architectural register file by an earlier instruction in the pipeline. Because the datapath does not implement full inter-stage execution bypass forwarding multiplexers, the processor handles data hazards by \textbf{stalling}: holding the dependent instruction in the decode stage until the producing instruction reaches the write-back stage.

\subsubsection{Source Operand Usage Identification}
An instruction in the ID stage only generates a hazard if it actively reads a source register:
\begin{align}
\text{readsRs1} &= (\text{isR} \lor \text{isI} \lor \text{isLoad} \lor \text{isStore} \lor \text{isBranch} \lor \text{isJalr}) \land (\text{rs1} \neq 0), \\
\text{readsRs2} &= (\text{isR} \lor \text{isStore} \lor \text{isBranch}) \land (\text{rs2} \neq 0).
\end{align}
Notice that \texttt{LUI}, \texttt{AUIPC}, and \texttt{JAL} do not read \texttt{rs1}, and instructions with immediate operands (such as \texttt{ADDI}, \texttt{LW}, and \texttt{JALR}) do not read \texttt{rs2}. Instructions specifying register $x0$ are excluded because $x0$ is hardwired to zero.

\subsubsection{Hazard Condition with the Execute Stage}
When an instruction is in the EX stage (\texttt{id\_ex}), its result has not yet been evaluated by the ALU or loaded from memory. Therefore, if the instruction in ID reads a register targeted by the instruction in EX, a Read-After-Write (RAW) hazard exists:
\begin{align}
\text{exWillWrite} &= \text{id\_ex.valid} \land \text{id\_ex.regWrite} \land (\text{id\_ex.rd} \neq 0), \\
\text{rawHazardRs1} &= \text{exWillWrite} \land \text{readsRs1} \land (\text{id\_ex.rd} == \text{d.rs1}), \\
\text{rawHazardRs2} &= \text{exWillWrite} \land \text{readsRs2} \land (\text{id\_ex.rd} == \text{d.rs2}), \\
\text{stall} &= \text{if\_id.valid} \land (\text{rawHazardRs1} \lor \text{rawHazardRs2}).
\end{align}

\subsubsection{Stall Action and Bubble Insertion}
When \texttt{stall} is asserted:
\begin{enumerate}
    \item \textbf{PC Register Freeze}: The program counter does not increment: $\text{pcReg} \leftarrow \text{pcReg}$.
    \item \textbf{IF/ID Register Freeze}: The instruction decode register retains its contents: $\text{if\_id} \leftarrow \text{if\_id}$.
    \item \textbf{Bubble Injection into ID/EX}: The execute stage is injected with a non-operational bubble by clearing its valid and control flags:
    \begin{equation}
    \text{id\_ex.valid} \leftarrow \text{false}, \quad \text{id\_ex.regWrite} \leftarrow \text{false}, \quad \text{id\_ex.memWrite} \leftarrow \text{false}.
    \end{equation}
\end{enumerate}

\subsubsection{Elimination of MEM/WB Stalls via Register Write-Through Bypass}
In the subsequent clock cycle, the producing instruction advances from EX to MEM/WB (\texttt{ex\_mem}), while the consuming instruction remains in ID. In the MEM/WB stage, the producing instruction evaluates its write-back data \texttt{wbData} (from the ALU, memory load, or immediate).

To avoid requiring a second stall cycle while the data commits to the register flip-flops, the datapath implements combinational write-through bypass at the register file read interface:
\begin{align}
\text{rs1Val} &= (\text{wbWen} \land \text{wbRd} == \text{d.rs1} \land \text{d.rs1} \neq 0) \ ? \ \text{wbData} : \text{regFile.io.rs1\_data}, \\
\text{rs2Val} &= (\text{wbWen} \land \text{wbRd} == \text{d.rs2} \land \text{d.rs2} \neq 0) \ ? \ \text{wbData} : \text{regFile.io.rs2\_data}.
\end{align}
Because \texttt{wbData} is forwarded combinationally during the MEM/WB cycle:
\begin{itemize}
    \item \textbf{Distance-1 RAW Dependencies} (e.g., \texttt{ADD x1, x2, x3} followed immediately by \texttt{SUB x4, x1, x5}): Stall penalty is exactly \textbf{1 clock cycle}.
    \item \textbf{Distance-2 RAW Dependencies} (e.g., \texttt{ADD x1, x2, x3}, an independent instruction, followed by \texttt{SUB x4, x1, x5}): Stall penalty is \textbf{0 clock cycles}, as the producer is already in MEM/WB when the consumer is decoded.
    \item \textbf{Load-Use Dependencies} (e.g., \texttt{LW x1, 0(x2)} followed by \texttt{ADD x3, x1, x4}): Stall penalty is \textbf{1 clock cycle}, because unbuffered memory returns \texttt{io.dmem.readData} during the MEM/WB stage.
\end{itemize}

\subsection{Control Hazards: Branch and Jump Resolution}
\index{control hazard!branch penalty}\index{pipeline flush!control transfer}

Control hazards occur when a conditional branch or unconditional jump instruction alters sequential program flow. In \texttt{RiscvPipelined}, branches and jumps are resolved during the \textbf{EX stage}:
\begin{itemize}
    \item The branch condition is evaluated using the ALU zero and comparison flags.
    \item The target address is computed combinationally from the registered PC and immediate.
\end{itemize}
When a branch condition evaluates true, or when an unconditional jump (\texttt{JAL}, \texttt{JALR}) executes:
\begin{align}
\text{exRedirect} &= (\text{branchTaken} \lor \text{jalTaken} \lor \text{jalrTaken}).
\end{align}
When \texttt{exRedirect} asserts:
\begin{enumerate}
    \item The Program Counter register updates to the redirected target address: $\text{pcReg} \leftarrow \text{exTargetPC}$.
    \item The \texttt{if\_id} register is flushed: $\text{if\_id.valid} \leftarrow \text{false}$.
    \item The \texttt{id\_ex} register is injected with a bubble: $\text{id\_ex.valid} \leftarrow \text{false}$.
\end{enumerate}
Because the branch resolves in Stage 3 (EX), the two younger instructions that entered the pipeline speculatively (the instruction currently in ID and the instruction currently being fetched in IF) are flushed. Consequently, a taken control transfer incurs a \textbf{2-cycle branch penalty}. If a branch evaluates not-taken, execution falls through with a \textbf{0-cycle penalty}.

Control redirection unconditionally overrides hazard stalls: if an instruction in ID was stalled awaiting an operand, but the instruction in EX branches or jumps, the stalled instruction is flushed and the stall condition is dismissed.


\section{Performance Evaluation and ASIC Physical Design of the RV32I Pipeline}\label{riscvPerformance}
\index{performance evaluation!pure RV32I}\index{ASIC synthesis!SkyWater 130nm}\index{SkyWater 130nm!standard cell synthesis}

To establish a rigorous baseline for pipelined processor design, the unpipelined (\texttt{RiscvFetchExecute}) and 4-stage pipelined (\texttt{RiscvPipelined}) processors were first configured in the pure, baseline \texttt{RV32I} architecture (with hardware multiplication disabled, \texttt{enableZmmul = false}). Both designs were subjected to three evaluation workflows:
\begin{enumerate}
    \item Architectural conformance verification against the official RISC-V \texttt{RV32I} test suite.
    \item Cycle-accurate execution of a real Digital Signal Processing (DSP) benchmark application.
    \item Full standard-cell ASIC synthesis targeting the open-source \textbf{SkyWater 130\,nm} process technology.
\end{enumerate}

\subsubsection{Architectural Analysis of the RV32I Pipelined Speedup}

The synthesis and performance results of the pure \texttt{RV32I} baseline illustrate classic computer architecture principles:
\begin{enumerate}
    \item \textbf{Well-Balanced Stage Delays}:
    In the pure \texttt{RV32I} architecture, the execution stage contains only simple integer arithmetic, logic, and shift operations. Standalone synthesis of the pure \texttt{RV32I} ALU indicates an intrinsic delay of 6.11\,ns. When embedded in the processor, the four pipeline stages exhibit well-balanced propagation delays: $T_{\text{IF}} \approx 5\,\text{ns}$, $T_{\text{ID}} \approx 4\,\text{ns}$, $T_{\text{EX}} = 7.17\,\text{ns}$, and $T_{\text{MEM}} \approx 5\,\text{ns}$.
    
    Consequently, pipelining cuts the core combinational critical path from 10.57\,ns down to 7.17\,ns, producing a \textbf{+47.4\% operating frequency boost} ($94.60\,\text{MHz} \to 139.47\,\text{MHz}$) for an area overhead of only 27.5\% ($53,902\,\mu\text{m}^2 \to 68,710\,\mu\text{m}^2$).
    
    \item \textbf{The Power of Memory Latency Overlap}:
    In real hardware systems, memory access is not instantaneous ($T_{\text{mem}} \approx 3\text{--}6\,\text{ns}$). In the single-cycle core, instruction fetch and data memory access must both complete within the \textit{same} clock period:
    \begin{equation}
    T_{\text{clk, single}} = T_{\text{imem}} + T_{\text{core}} + T_{\text{dmem}} = 5\,\text{ns} + 10.57\,\text{ns} + 5\,\text{ns} = 20.57\,\text{ns} \quad (48.61\,\text{MHz}).
    \end{equation}
    In the 4-stage pipeline, instruction fetch and data memory access occur in separate clock cycles (Stage 1 and Stage 4, respectively). Because memory latency overlaps with instruction execution, the clock period is governed solely by the maximum stage delay:
    \begin{equation}
    T_{\text{clk, pipe}} = \max(T_{\text{imem}}, T_{\text{ID}}, T_{\text{EX}}, T_{\text{dmem}}) = \max(5\,\text{ns}, 7.17\,\text{ns}) = 7.17\,\text{ns} \quad (139.47\,\text{MHz}).
    \end{equation}
    This decouples system clock frequency from cumulative memory latency, achieving a \textbf{+186.9\% frequency increase} ($48.61\,\text{MHz} \to 139.47\,\text{MHz}$).
    
    \item \textbf{Net Application Speedup}:
    Despite the pipeline CPI increasing from 1.00 to 1.63 (+63.5\% cycles due to hazard stalls and branch flushes), the 2.87$\times$ clock frequency advantage easily dominates the cycle penalty:
    \begin{equation}
    \text{Speedup} = \frac{T_{\text{exec, single}}}{T_{\text{exec, pipe}}} = \frac{6,511 \times 20.57\,\text{ns}}{10,645 \times 7.17\,\text{ns}} = \frac{133,931\,\text{ns}}{76,325\,\text{ns}} = \mathbf{1.75\times}.
    \end{equation}
    The pipelined \texttt{RV32I} core delivers a \textbf{1.75$\times$ application speedup} on the real DSP workload.
\end{enumerate}


\section{Microarchitectural Case Study: Hardware Multiplication (Zmmul) and the Pipeline Balancing Dilemma}\label{riscvZmmulCaseStudy}
\index{Zmmul extension!microarchitectural case study}\index{pipeline balancing!multiplier bottleneck}\index{Amdahl's law!clock period unbalancing}

Having established the baseline performance of the 4-stage \texttt{RV32I} pipeline, we now examine what happens when hardware multiplication is added. In scientific computing, machine learning, and digital signal processing, multiplication is ubiquitous. Implementing multiplication in software via shift-and-add requires roughly 35 instructions per multiply, bloating code size and consuming significant execution cycles. 

To accelerate multiplication, the RISC-V standard defines the \texttt{Zmmul} extension, introducing four 32-bit multiplication instructions: \texttt{MUL} (lower 32 bits), \texttt{MULH} (upper 32 bits, signed $\times$ signed), \texttt{MULHSU} (upper 32 bits, signed $\times$ unsigned), and \texttt{MULHU} (upper 32 bits, unsigned $\times$ unsigned).

A naive microarchitectural approach is to simply integrate a $32 \times 32$ combinational multiplier directly into the execution stage ALU (\texttt{RiscvALU}). However, this case study reveals how an unpipelined complex execution unit catastrophically destroys pipeline stage balancing.

\begin{itemize}

The \textit{microarchitectural efficiency} of pipelining was severely compromised by the unpipelined multiplier bottleneck.
\end{itemize}

\subsection{Architectural Solutions: Restoring Pipeline Balance}
\index{pipeline balancing!architectural solutions}\index{multi-cycle multiplier}\index{pipelined multiplier}

The case study illustrates \textbf{Amdahl's Law applied to pipeline cycle time}:
\begin{equation}
T_{\text{clk}} = \max\left(T_{\text{IF}}, T_{\text{ID}}, T_{\text{EX}}, T_{\text{MEM}}\right) + T_{\text{overhead}}.
\end{equation}
When one stage is significantly slower than the rest, improving or subdividing the other stages yields diminishing returns.

How do production computer architects resolve this dilemma when integrating multiplication and other complex functional units?
\begin{enumerate}
    \item \textbf{Multi-Cycle Execution Unit}:
    Rather than forcing the entire processor to run at a slow 13.25\,ns clock period to accommodate the multiplier, the multiplier is designed as a multi-cycle iterative unit (e.g., taking 2 to 4 cycles). 
    
    When a non-multiplying instruction enters EX, it completes in a single fast clock cycle (e.g., 7.17\,ns). When a \texttt{MUL} instruction enters EX, the Hazard Detection Unit asserts a temporary stall for 2--3 cycles while the multiplier computes. Because multiplications typically represent only 5--15\% of instructions in real workloads, running 90\% of instructions at 139.47\,MHz with occasional 3-cycle stalls yields vastly superior overall performance compared to running 100\% of instructions at 75.47\,MHz.
    
    \item \textbf{Internally Pipelined Multiplier}:
    In high-performance processors, the multiplier logic array is itself divided into multiple synchronous pipeline stages separated by internal pipeline registers:
    \begin{itemize}
        \item \textbf{Stage 1}: Booth recoding and partial product generation.
        \item \textbf{Stage 2}: Carry-save reduction tree (Wallace tree or Dadda tree compression).
        \item \textbf{Stage 3}: Final carry-propagate addition (lookahead adder).
    \end{itemize}
    By inserting pipeline registers within the multiplier, each sub-stage delay is reduced to $\approx 3.5\,\text{ns}$, restoring pipeline balance and allowing the entire processor to operate at high frequencies ($>250\,\text{MHz}$) with a multiplier throughput of 1 instruction per cycle and a latency of 3 cycles.
\end{enumerate}

\subsection{Why Ideal Pipeline Speedup is Inaccessible in Practice}
\index{pipeline speedup!theoretical vs actual}\index{pipeline balancing!physical impediments}\index{stage delay quantization}\index{clock overhead}

A common observation among novice computer architects is that a pipelined processor runs ``only a tiny bit faster'' than a single-cycle core, or in some configurations even slightly slower. In introductory textbooks, pipelining an $N$-stage processor is frequently described as achieving a theoretical speedup of:
\begin{equation}
S_{\text{ideal}} = N.
\end{equation}
For our 4-stage pipeline ($N = 4$), naive theory predicts a $4.0\times$ speedup. Yet, as demonstrated in Table \ref{tab:riscv_all_benchmarks}, the measured speedup in physical silicon is between $1.75\times$ and $1.94\times$ when overlapping memory latency, and actually \textit{less than 1.0$\times$} ($0.90\times\text{--}0.996\times$) when comparing core execution times alone!

Why is ideal pipeline speedup impossible to achieve in physical silicon? The actual speedup of a pipelined processor over a single-cycle implementation is governed by the classic processor performance equation:
\begin{equation}
\text{Speedup} = \frac{\text{Time}_{\text{single}}}{\text{Time}_{\text{pipe}}} = \frac{I \times \text{CPI}_{\text{single}} \times T_{\text{clk, single}}}{I \times \text{CPI}_{\text{pipe}} \times T_{\text{clk, pipe}}} = \left(\frac{\text{CPI}_{\text{single}}}{\text{CPI}_{\text{pipe}}}\right) \times \left(\frac{T_{\text{clk, single}}}{T_{\text{clk, pipe}}}\right).
\end{equation}
For an $N$-stage pipeline, achieving $S = N$ requires two simultaneous conditions:
\begin{enumerate}
    \item \textbf{Perfect CPI Invariance}: $\text{CPI}_{\text{pipe}} = \text{CPI}_{\text{single}} = 1.00$.
    \item \textbf{Perfect Frequency Scaling}: $T_{\text{clk, pipe}} = \frac{1}{N} T_{\text{clk, single}}$.
\end{enumerate}
In physical hardware, three fundamental physical barriers guarantee that neither condition can ever be met:

\subsubsection{1. Stage Delay Quantization and Imbalance}
\index{pipeline balancing!delay quantization}\index{Amdahl's Law!for clock periods}
Combinational logic cannot be sliced arbitrarily like a fluid. Logic circuits are constructed from discrete boolean primitives: multiplexers, adders, decoders, shifters, and comparator trees. In our pure \texttt{RV32I} core:
\begin{itemize}
    \item The complete unpipelined combinational critical path from instruction register through decode, 32-bit ALU, and writeback multiplexers is $10.57\,\text{ns}$ in SkyWater 130\,nm.
    \item When partitioned into four stages, the Execute (EX) stage requires $7.17\,\text{ns}$ (dominated by the 32-bit adder, barrel shifter, branch comparator, and ALU output multiplexers).
    \item The Instruction Decode (ID) and Memory/Write-Back (MEM/WB) stages require only $\approx 4.2\,\text{ns}$ and $\approx 3.8\,\text{ns}$, respectively.
\end{itemize}
Because synchronous sequential pipelines require all stages to operate at a common clock period, the clock period is strictly bounded by the slowest stage:
\begin{equation}
T_{\text{clk, pipe}} = \max\left(T_{\text{IF}}, T_{\text{ID}}, T_{\text{EX}}, T_{\text{MEM}}\right) + T_{\text{overhead}} = 7.17\,\text{ns}.
\end{equation}
Consequently, the frequency improvement is only:
\begin{equation}
\frac{T_{\text{clk, single}}}{T_{\text{clk, pipe}}} = \frac{10.57\,\text{ns}}{7.17\,\text{ns}} = 1.474\times \quad (\text{a } +47.4\% \text{ frequency gain, far below } 4.0\times).
\end{equation}
Stage delay imbalance alone annihilates $(4.0 - 1.474) / 4.0 = \mathbf{63.1\%}$ of the theoretical speedup before a single instruction has executed!

\subsubsection{2. Sequential Register Overhead}
\index{pipeline register overhead}\index{setup time}\index{clock-to-Q delay}
Every pipeline stage boundary requires sequential state storage (D flip-flops in standard cells):
\begin{equation}
T_{\text{stage}} = T_{\text{comb}} + t_{\text{setup}} + t_{\text{cq}} + t_{\text{skew}}.
\end{equation}
In the SkyWater 130\,nm standard cell library (\texttt{sky130\_fd\_sc\_hd}):
\begin{itemize}
    \item Flip-flop setup time: $t_{\text{setup}} \approx 0.25\,\text{ns}$.
    \item Clock-to-Q propagation delay: $t_{\text{cq}} \approx 0.35\,\text{ns}$.
    \item Clock distribution skew and jitter margin: $t_{\text{skew}} \approx 0.20\,\text{ns}$.
\end{itemize}
This introduces an unshrinkable sequential overhead of $T_{\text{reg\_overhead}} \approx 0.80\,\text{ns}$ at \textit{every stage boundary}. Over a 4-stage pipeline, $3.20\,\text{ns}$ of cumulative delay is consumed solely by registers. This overhead represents a dead penalty that performs zero computational work, directly diminishing the achievable clock frequency.

\subsubsection{3. Hazard-Induced CPI Expansion}
\index{hazard penalties}\index{CPI expansion}
In a single-cycle processor, data dependencies and branch decisions are resolved combinationally within the same clock period in which the instruction executes:
\begin{equation}
\text{CPI}_{\text{single}} \equiv 1.00.
\end{equation}
In a pipelined processor, instructions execute concurrently across time. When an instruction in the Decode stage depends on a value being computed in Execute, the Hazard Detection Unit must inject a stall cycle (bubble). Furthermore, when a branch or jump condition is evaluated in the Execute stage, the two instructions fetched speculatively into IF and ID must be discarded, incurring a 2-cycle branch penalty.

Across real embedded workloads, this hazard overhead expands the effective CPI:
\begin{itemize}
    \item \textbf{Dhrystone 2.1}: $\text{CPI}_{\text{pipe}} = 1.48$ (+48.0\% cycle penalty).
    \item \textbf{CoreMark 1.0}: $\text{CPI}_{\text{pipe}} = 1.53$ (+53.3\% cycle penalty).
    \item \textbf{DSP Kernel (Soft Mul)}: $\text{CPI}_{\text{pipe}} = 1.63$ (+63.5\% cycle penalty).
\end{itemize}

Now observe what happens when we calculate the net core performance speedup (without memory latency):
\begin{equation}
\text{Speedup}_{\text{core}} = \left(\frac{1}{\text{CPI}_{\text{pipe}}}\right) \times \left(\frac{T_{\text{clk, single}}}{T_{\text{clk, pipe}}}\right) = \left(\frac{1}{1.53}\right) \times 1.474 = 0.654 \times 1.474 = \mathbf{0.963\times}.
\end{equation}
The core-only speedup is actually less than $1.0\times$! The 47.4\% frequency improvement obtained from pipelining the datapath is completely canceled out by the 53.3\% cycle penalty caused by pipeline stalls and branch flushes.

\subsubsection{The Real Triumph of Pipelining: Overlapping Memory Access Latency}
\index{memory latency overlapping}\index{Harvard architecture!pipelined overlap}
Why, then, do computer architects pipeline processors? The answer lies in the system-level memory interface:
\begin{itemize}
    \item In a \textbf{single-cycle machine}, the clock cycle must encompass the entire round-trip latency of instruction memory access ($T_{\text{imem}}$), core combinational datapath delay ($T_{\text{core}}$), and data memory access ($T_{\text{dmem}}$) sequentially within a single tick:
    \begin{equation}
    T_{\text{clk, single}} = T_{\text{imem}} + T_{\text{core}} + T_{\text{dmem}} = 5.0\,\text{ns} + 10.57\,\text{ns} + 5.0\,\text{ns} = 20.57\,\text{ns} \quad (48.61\,\text{MHz}).
    \end{equation}
    \item In a \textbf{pipelined machine}, instruction fetch (IF) and data memory access (MEM) occur in completely separate pipeline stages separated by synchronous registers. Memory latency is overlapped across distinct clock cycles:
    \begin{equation}
    T_{\text{clk, pipe}} = \max\left(T_{\text{core}}, T_{\text{mem}}\right) = \max(7.17\,\text{ns}, 5.0\,\text{ns}) = 7.17\,\text{ns} \quad (139.47\,\text{MHz}).
    \end{equation}
\end{itemize}
Overlapping memory latency increases system operating frequency by:
\begin{equation}
\frac{T_{\text{clk, single, sys}}}{T_{\text{clk, pipe, sys}}} = \frac{20.57\,\text{ns}}{7.17\,\text{ns}} = \mathbf{2.869\times}.
\end{equation}
Multiplying this $2.869\times$ frequency advantage by the CPI factor ($1 / 1.53$) yields the net system speedup:
\begin{equation}
\text{Speedup}_{\text{sys}} = 2.869 \times \frac{1}{1.53} = \mathbf{1.87\times} \quad (\text{CoreMark}), \quad \mathbf{1.94\times} \quad (\text{Dhrystone}).
\end{equation}
Thus, pipelining delivers a robust $+87\%\text{--}94\%$ application speedup in realistic systems, but the theoretical $4.0\times$ speedup is fundamentally inaccessible due to the physics of stage imbalance, register overhead, and control/data hazards.

\subsubsection{Why SPEC CPU Cannot Run on Bare-Metal Microcontrollers}
Students frequently inquire why standard desktop/server benchmarks such as \textbf{SPEC CPU} (SPEC CPU2006 or SPEC CPU2017) are not used to evaluate microcontroller cores like the baseline \texttt{RV32I} core developed in this chapter. 

SPEC CPU is designed exclusively for \textbf{application-class processors} (e.g., 64-bit x86-64, ARM Cortex-A, or RISC-V RV64GC) and requires an extensive underlying system software infrastructure:
\begin{enumerate}
    \item \textbf{Memory Management Unit (MMU)}: SPEC benchmarks rely heavily on virtual memory address spaces, demand paging, and memory protection provided by hardware page tables (e.g., RISC-V Sv39 or Sv48 MMUs). A bare-metal microcontroller core without an MMU cannot provide virtual memory.
    \item \textbf{Full Operating System}: SPEC workloads are full Unix/C++ applications requiring POSIX system calls (\texttt{fork}, \texttt{exec}, \texttt{mmap}, file I/O, threads) provided by a full Linux or BSD operating system.
    \item \textbf{Gigabyte Memory Capacity}: SPEC CPU2017 benchmarks require a minimum of 1 to 2\,GB of physical RAM to load their multi-megabyte reference datasets into memory. Microcontrollers typically operate with tens of kilobytes of SRAM.
    \item \textbf{Proprietary Licensing}: SPEC benchmarks are commercial software licensed by the Standard Performance Evaluation Corporation for several thousand dollars, preventing public redistribution or open academic inclusion.
\end{enumerate}

\subsubsection{The Embedded Benchmark Standards: Dhrystone, CoreMark, and Embench}
For microcontroller-class architectures (such as \texttt{RV32I}, ARM Cortex-M0/M3/M4, and MicroBlaze), the computer architecture community relies on lightweight, freestanding benchmark suites:
\begin{itemize}
    \item \textbf{Dhrystone 2.1}: Developed in 1984, Dhrystone is a synthetic integer benchmark that measures CPU throughput in terms of ``Dhrystones per second.'' Results are typically normalized to the VAX 11/780 (which scored 1,757 Dhrystones per second, defining 1 DMIPS):
    \begin{equation}
    \text{DMIPS/MHz} = \frac{10^6}{\text{Cycles per Dhrystone Run} \times 1,757}.
    \end{equation}
    Our single-cycle \texttt{RV32I} core scores $\mathbf{0.824\,\text{DMIPS/MHz}}$, while the 4-stage pipeline scores $\mathbf{0.556\,\text{DMIPS/MHz}}$ (reflecting its 1.48 CPI). Although historically widespread, Dhrystone has fallen out of modern favor because its tight loops can be disproportionately affected by compiler string inlining and dead-code elimination.
    
    \item \textbf{EEMBC CoreMark}: Developed by EEMBC to replace Dhrystone, CoreMark executes realistic algorithms (matrix manipulation, linked lists, state machines) specifically designed to prevent optimizing compilers from eliminating computation. Its self-checking CRC guarantees that every algorithmic step produces valid data. On our 4-stage pipeline, CoreMark delivers $\mathbf{0.746\,\text{CoreMark/MHz}}$ ($\mathbf{104.04\,\text{CoreMarks}}$ at system frequency).
    
    \item \textbf{Embench-IoT}: Developed by the Free and Open Source Silicon (FOSSi) Foundation in collaboration with David Patterson, Embench is a modern, open-source suite of 19 real-world embedded programs (e.g., AES encryption, Huffman decoding, Minver, QR-code, Wic) designed specifically to provide a reproducible, open-source alternative to proprietary benchmarks for microcontroller-class RISC-V cores.
\end{itemize}


\section{Summary}\label{riscvSummary}
\index{RISC-V!chapter summary}

This chapter presented the comprehensive architecture, microarchitectural implementation, formal verification, and physical ASIC design of the open standard RISC-V processor:
\begin{itemize}
    \item The RISC-V Instruction Set Architecture organizes execution around a clean 32-bit regular format with symmetric register source/destination fields, fixed opcode locations, and sign bits fixed at bit 31 across all formats.
    \item A single-cycle Harvard 5-OS processor core (\texttt{RiscvFetchExecute}) was implemented by modularly integrating library automata developed across prior chapters: \texttt{ProgramCounter}, \texttt{RiscvDecoder}, \texttt{RiscvImmGen}, \texttt{RiscvRegFile}, \texttt{RiscvALU}, and \texttt{RiscvDataMemory}.
    \item A 4-stage pipelined processor core (\texttt{RiscvPipelined}) was developed, partitioning the datapath into Instruction Fetch (IF), Instruction Decode (ID), Execute (EX), and Memory/Write-Back (MEM/WB) stages.
    \item An active Hazard Detection Unit was designed to detect Read-After-Write (RAW) data dependencies and stall the pipeline by freezing the PC and IF/ID registers while injecting bubbles into ID/EX. Internal register file write-through bypass was incorporated to reduce RAW stall penalties to a single cycle.
    \item Branch and jump conditions are evaluated in the EX stage, incurring a 2-cycle control hazard penalty on taken transfers while executing non-taken branches with zero cycle overhead.
    \item Both processor cores were verified against all official RISC-V architectural conformance test suites (38 RV32I suites and 4 Zmmul suites) using Chisel simulation, achieving a 100\% signature match against Spike golden references.
    \item Full physical synthesis targeting the open-source SkyWater 130\,nm standard cell library was conducted for the baseline \texttt{RV32I} cores. The 4-stage pipeline delivered a +47.4\% core clock frequency increase ($94.6\,\text{MHz} \to 139.5\,\text{MHz}$) and a +186.9\% system clock frequency increase when overlapping realistic 5\,ns memory latency ($48.6\,\text{MHz} \to 139.5\,\text{MHz}$), achieving a measured \textbf{1.75$\times$ application speedup} on a real DSP benchmark.
    \item Comprehensive physical benchmark evaluation was performed across DSP kernels, Dhrystone 2.1 (20 runs), and EEMBC CoreMark 1.0 (1 iteration, 2K data footprint). The 4-stage pipeline achieved $100\%$ validation matching golden signatures, scoring $0.556\,\text{DMIPS/MHz}$ ($77.55\,\text{DMIPS}$ at system frequency) and $0.746\,\text{CoreMark/MHz}$ ($104.04\,\text{CoreMarks}$ at system frequency).
    \item Pipelining an $N$-stage processor was shown to be bounded in practice by three physical barriers: (1) stage delay quantization/imbalance (Amdahl's Law for clock frequencies), (2) sequential flip-flop overhead ($t_{\text{setup}} + t_{\text{cq}} + t_{\text{skew}}$), and (3) hazard-induced CPI expansion ($\text{CPI} \approx 1.48\text{--}1.63$). Without memory latency, the pipelined core is actually slightly slower than single-cycle ($0.96\times$ on CoreMark); real system performance gains ($1.87\times\text{--}1.94\times$) arise fundamentally from overlapping memory access latency across clock cycles.
    \item A taxonomy of computer architecture benchmarks was established: application-class benchmarks such as SPEC CPU2017 require virtual memory (MMU), a full POSIX OS (Linux), and gigabytes of RAM, rendering them physically inapplicable to bare-metal microcontroller-class cores. Microcontroller-class architectures rely on freestanding suites including Dhrystone, EEMBC CoreMark, and Embench-IoT.
\end{itemize}


\section{Problems}\label{riscvProblems}
\index{problems!RISC-V architecture and implementation}

\begin{problem}
Explain why the RISC-V instruction format places the sign bit of all immediate values in bit 31 ($\text{inst}[31]$) across all instruction formats (I, S, B, U, J). How does this design choice benefit hardware decoders?

\textbf{Solution}:
By fixing the immediate sign bit at $\text{inst}[31]$, the hardware immediate generator can immediately begin sign-extending the most significant bit across upper datapath wires (e.g., replicating $\text{inst}[31]$ into bits 31:12 or 31:20) concurrently with opcode decoding, before the instruction format is even identified. This reduces decoding latency and simplifies fan-out buffering.
$\diamond$
\end{problem}

\begin{problem}
In the implementation of \texttt{JALR}, the RISC-V specification dictates that the least significant bit of the computed target address must be forced to zero: $\text{target} = (\text{rs1} + \text{imm}) \ \& \ \sim 1$.
\begin{enumerate}
    \item What software purpose does this requirement serve?
    \item Where is this masking implemented in the \texttt{RiscvPipelined} processor?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Forcing bit 0 to 0 guarantees that control never transfers to an unaligned byte address that would cause an instruction-address-misaligned exception. It also enables software to use pointer arithmetic where low bits store tag flags, stripping the flag during return or indirect call.
    \item In \texttt{RiscvPipelined.scala}, the EX stage computes:
    \texttt{val jalrTarget = Cat((id\_ex.rs1Data + id\_ex.imm)(xlen - 1, 1), 0.U(1.W))}, explicitly forcing bit 0 to zero before routing to the next-PC multiplexer.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider the following sequence of instructions executing on the 4-stage \texttt{RiscvPipelined} processor:
\begin{lstlisting}[language=c]
add x1, x2, x3
sub x4, x1, x5
and x6, x1, x7
\end{lstlisting}
\begin{enumerate}
    \item Identify the data hazards present in this sequence.
    \item How many stall cycles are incurred between \texttt{add} and \texttt{sub}?
    \item How many stall cycles are incurred between \texttt{add} and \texttt{and}?
    \item How does the register file write-through bypass affect the execution of \texttt{and}?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Both \texttt{sub} and \texttt{and} have a Read-After-Write (RAW) data hazard on register \texttt{x1} produced by \texttt{add}.
    \item When \texttt{sub} is in the ID stage, \texttt{add} is in the EX stage. The Hazard Detection Unit detects that $\text{id\_ex.rd} == \text{x1}$ and stalls \texttt{sub} for \textbf{1 clock cycle}, inserting a bubble into ID/EX.
    \item In the following cycle, \texttt{add} moves to the MEM/WB stage. The register file write-through bypass forwards \texttt{wbData} combinationally to \texttt{rs1Val} in ID. Therefore, \texttt{sub} advances to EX. When \texttt{and} reaches the ID stage, \texttt{add} has already committed its value to \texttt{x1} in the register file. Thus, \textbf{0 stall cycles} are incurred for \texttt{and}.
    \item Without register file write-through bypass, \texttt{sub} would require 2 stall cycles, and \texttt{and} would require 1 stall cycle. Write-through eliminates both redundant stalls.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
In the 4-stage pipeline, branch condition evaluation and target address generation are performed in the EX stage.
\begin{enumerate}
    \item What is the branch penalty (in clock cycles) when a conditional branch evaluates taken?
    \item What is the branch penalty when a conditional branch evaluates not-taken?
    \item If branches represent 20\% of all executed instructions in a program, and 60\% of branches are taken, what is the branch contribution to the overall CPI?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item When a branch is taken, the two instructions fetched speculatively into the IF and ID stages are flushed. Thus, the penalty is \textbf{2 clock cycles}.
    \item When a branch is not taken, execution falls through sequentially without flushing the pipeline. Thus, the penalty is \textbf{0 clock cycles}.
    \item Average branch penalty per instruction:
    \begin{equation}
    \text{CPI}_{\text{branch}} = 0.20 \times (0.60 \times 2 + 0.40 \times 0) = 0.20 \times 1.20 = 0.24 \ \text{cycles/instruction}.
    \end{equation}
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Compare the physical synthesis data of the pure \texttt{RV32I} core (Table \ref{tab:sky130_rv32i_synthesis}) with the \texttt{RV32I\_Zmmul} core (Table \ref{tab:riscv_grand_comparison}):
\begin{enumerate}
    \item In pure \texttt{RV32I}, pipelining increased the core clock frequency by +47.4\% ($94.6\,\text{MHz} \to 139.5\,\text{MHz}$). Why did pipelining the \texttt{RV32I\_Zmmul} core only improve core frequency by +2.95\% ($73.3\,\text{MHz} \to 75.5\,\text{MHz}$)?
    \item Calculate the silicon area overhead of adding the unpipelined multiplier to the 4-stage pipelined processor in SkyWater 130\,nm technology.
    \item State Amdahl's Law as it applies to pipeline stage delays and clock periods.
    \item Propose two microarchitectural techniques that would allow the processor to retain the high operating frequency of pure \texttt{RV32I} while providing hardware multiplication acceleration.
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item In pure \texttt{RV32I}, all pipeline stages have balanced delays ($T \approx 4\text{--}7\,\text{ns}$). In \texttt{RV32I\_Zmmul}, the unpipelined $32 \times 32$ multiplier logic array in the EX stage requires 11.09\,ns of combinational delay, making the EX stage critical path 13.25\,ns. By Amdahl's Law for clock periods, the clock frequency is constrained by the slowest stage ($\max_i T_i$). Thus, the pipelined core cannot run faster than 75.47\,MHz regardless of the speed of the other three stages.
    \item The silicon area increases from $68,710\,\mu\text{m}^2$ (pure RV32I 4-stage) to $151,075\,\mu\text{m}^2$ (RV32I\_Zmmul 4-stage). This represents an increase of:
    \begin{equation}
    \Delta \text{Area} = 151,075 - 68,710 = 82,365\,\mu\text{m}^2 \quad (+120\% \ \text{silicon area overhead}).
    \end{equation}
    \item Amdahl's Law for clock periods dictates that:
    \begin{equation}
    T_{\text{clk}} \ge \max_{1 \le i \le N} (T_{\text{stage}, i}) + T_{\text{reg\_overhead}}.
    \end{equation}
    The minimum clock period of a synchronous pipeline is strictly bounded by the delay of the single slowest stage. Subdividing or optimizing the remaining $N-1$ stages cannot reduce the clock period below the slowest stage's delay.
    \item Two microarchitectural techniques:
    \begin{itemize}
        \item \textbf{Multi-cycle Multiplier}: Implement the multiplier as a multi-cycle iterative unit (e.g., 3-cycle stall only on \texttt{MUL}), keeping the base processor clock at 139.5\,MHz for all other instructions.
        \item \textbf{Pipelined Multiplier}: Subdivide the multiplier logic array into 2 or 3 internal synchronous pipeline stages (partial product generation, tree compression, final adder), reducing each stage's delay to $<4\,\text{ns}$.
    \end{itemize}
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider the empirical EEMBC CoreMark 1.0 benchmark results from Table \ref{tab:riscv_all_benchmarks} executing on the pure \texttt{RV32I} single-cycle core ($T_{\text{clk}} = 10.57\,\text{ns}$) and 4-stage pipelined core ($T_{\text{clk}} = 7.17\,\text{ns}$):
\begin{enumerate}
    \item A student expects a 4-stage pipeline to achieve a $4.0\times$ speedup over the single-cycle core. Compute the actual core-only speedup (without memory latency) using the instruction count $I = 874,891$, single-cycle cycles $C_1 = 874,891$, and pipelined cycles $C_4 = 1,340,964$. Explain why the pipelined core is actually slower than the single-cycle core in isolation.
    \item In a realistic system, instruction and data memories exhibit an access latency of $T_{\text{mem}} = 5.0\,\text{ns}$. Compute the single-cycle and pipelined system clock periods, system frequencies, and total system execution times. What is the actual system speedup?
    \item Why cannot desktop/server benchmarks such as SPEC CPU2017 be executed directly on bare-metal \texttt{RV32I} microcontroller cores? What modern open-source benchmark suite was created to evaluate microcontroller-class RISC-V processors?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Core-only execution times:
    \begin{equation}
    T_{\text{exec, single}} = C_1 \times T_{\text{clk, single}} = 874,891 \times 10.57\,\text{ns} = 9,247,598\,\text{ns}.
    \end{equation}
    \begin{equation}
    T_{\text{exec, pipe}} = C_4 \times T_{\text{clk, pipe}} = 1,340,964 \times 7.17\,\text{ns} = 9,614,712\,\text{ns}.
    \end{equation}
    \begin{equation}
    \text{Speedup}_{\text{core}} = \frac{9,247,598\,\text{ns}}{9,614,712\,\text{ns}} = \mathbf{0.962\times}.
    \end{equation}
    The pipelined core is $3.8\%$ slower because stage delay imbalance limits the frequency scaling factor to $10.57 / 7.17 = 1.474\times$, while RAW data hazard stalls and branch flush bubbles inflate the pipelined CPI to $C_4 / I = 1.533$ ($+53.3\%$ cycle overhead). Because $1.533 > 1.474$, the stall overhead completely negates the frequency advantage.
    \item With $5.0\,\text{ns}$ memory latency:
    \begin{equation}
    T_{\text{sys, single}} = T_{\text{imem}} + T_{\text{core}} + T_{\text{dmem}} = 5.0 + 10.57 + 5.0 = 20.57\,\text{ns} \quad (f_{\text{sys, single}} = 48.61\,\text{MHz}).
    \end{equation}
    \begin{equation}
    T_{\text{sys, pipe}} = \max(T_{\text{core}}, T_{\text{mem}}) = \max(7.17, 5.0) = 7.17\,\text{ns} \quad (f_{\text{sys, pipe}} = 139.47\,\text{MHz}).
    \end{equation}
    Total system execution times:
    \begin{equation}
    T_{\text{sys-exec, single}} = 874,891 \times 20.57\,\text{ns} = 17,996,508\,\text{ns}.
    \end{equation}
    \begin{equation}
    T_{\text{sys-exec, pipe}} = 1,340,964 \times 7.17\,\text{ns} = 9,614,712\,\text{ns}.
    \end{equation}
    \begin{equation}
    \text{Actual System Speedup} = \frac{17,996,508\,\text{ns}}{9,614,712\,\text{ns}} = \mathbf{1.872\times} \quad (+87.2\% \ \text{performance boost}).
    \end{equation}
    Memory overlapping increases the operating frequency ratio to $20.57 / 7.17 = 2.869\times$, converting the core-only deficit into a significant system-level performance gain.
    \item SPEC CPU2017 cannot run on bare-metal \texttt{RV32I} microcontroller cores because SPEC benchmarks require a Memory Management Unit (MMU) with virtual memory paging, a full POSIX operating system (Linux), multi-gigabyte RAM capacity, glibc with dynamic file I/O, and commercial proprietary licenses. The modern open-source embedded alternative created by David Patterson and the FOSSi consortium is \textbf{Embench-IoT}.
\end{enumerate}
$\diamond$
\end{problem}

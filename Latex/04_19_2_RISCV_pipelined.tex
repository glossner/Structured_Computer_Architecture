\section{Hardware Implementation of the Pipelined Processor}\label{riscvPipelined}
\index{RISC-V!pipelined implementation}\index{pipelining!4-stage hazard detection and stall}\index{hazard detection unit}\index{pipeline stall}

While the single-cycle processor developed in Section \ref{riscvArch} executes each instruction in a single clock cycle ($\text{CPI} = 1.0$), its operating clock frequency is fundamentally constrained by the cumulative propagation delay across all sequential and combinational subsystems traversed within a single clock period. Grouping these delays by their four physical pipeline steps yields:
\begin{equation}
T_{\text{clock, single}} \ge T_{\text{fetch}} + T_{\text{decode}} + T_{\text{execute}} + T_{\text{sram\_wb}},
\end{equation}
where $T_{\text{fetch}}$ represents instruction SRAM address driving and retrieval ($T_{\text{IF}}$), $T_{\text{decode}}$ represents instruction decoding and dual-port register file read ($T_{\text{ID}}$), $T_{\text{execute}}$ represents ALU arithmetic, shifting, and branch comparison ($T_{\text{EX}}$), and $T_{\text{sram\_wb}}$ represents data SRAM access and write-back register commit ($T_{\text{MEM/WB}}$).

In advanced physical processes, this monolithic combinational path limits clock frequencies. To improve computational throughput, this section develops a 4-stage pipelined implementation of the base \texttt{RV32I} processor, designated \texttt{RiscvPipelined} (and explores its extension to \texttt{RV32I\_Zmmul}). Reusing the core pipeline concepts of \textit{PipeNyte},\footnote{\url{https://github.com/Ypologist/KryptoNyte}} the datapath divides execution into four sequential synchronous stages separated by explicit pipeline registers. In this pipelined processor, each stage executes concurrently in its own clock cycle, so the minimum clock period is constrained not by the sum of delays, but by the maximum delay among the individual pipeline stages:
\begin{equation}
T_{\text{clock, pipe}} \ge \max\left(T_{\text{fetch}}, T_{\text{decode}}, T_{\text{execute}}, T_{\text{sram\_wb}}\right) + T_{\text{reg\_overhead}},
\end{equation}
where $T_{\text{reg\_overhead}} = t_{\text{setup}} + t_{\text{cq}} + t_{\text{skew}}$ denotes the sequential register setup, clock-to-Q, and clock skew overhead introduced at every pipeline stage boundary. Incorporating an active \textit{Hazard Detection Unit}, the core stalls instruction issue upon detecting data dependencies and flushes speculative instructions upon branch resolution. In this design, the core operates directly against unbuffered memory buses without cache hierarchies.


\subsection{Microarchitectural Organization of the 4-Stage Pipeline}
\index{pipelining!microarchitectural stages}\index{PipeNyte!4-stage architecture}

The 4-stage pipeline partitions the Fetch-Execute cycle into four (hopefully) balanced operational stages (Figure \ref{fig:riscv_4stage_pipeline}):
\begin{enumerate}
    \item \textbf{Stage 1: Instruction Fetch (IF)}:
    Maintains the architectural Program Counter register (\texttt{pcReg}). Drives the unbuffered instruction memory bus (\texttt{io.imem.addr}) and latches the incoming 32-bit instruction word into the \texttt{if\_id} pipeline register. Under normal sequential execution, the PC increments by 4 ($\text{PC} \leftarrow \text{PC} + 4$). When a control transfer (branch or jump) resolves taken in the EX stage, the PC updates to the target address, and the \texttt{if\_id} register is flushed. When a data hazard stall is signaled by the ID stage, the PC and \texttt{if\_id} register are frozen.
    
    \item \textbf{Stage 2: Instruction Decode and Operand Fetch (ID)}:
    Decodes the instruction latched in \texttt{if\_id} using \texttt{RiscvDecoder}, generates sign-extended immediates via \texttt{RiscvImmGen}, and accesses the architectural register file (\texttt{RiscvRegFile}). In this baseline implementation, \textit{no forwarding} is implemented (operands are read directly from the register storage array). All data dependencies are resolved strictly by stalling until writeback commits.
    
    The ID stage houses the \textit{Hazard Detection Unit}. If an instruction in ID reads a register targeted by an in-flight instruction currently in either the EX stage (distance-1 dependency) or the MEM/WB stage (distance-2 dependency), the hazard detection unit asserts a pipeline stall.
    
    \item \textbf{Stage 3: Execute (EX)}:
    Executes arithmetic, logical, and shift operations via the 32-bit executive ALU (\texttt{RiscvALU}), with optional support for the standard \texttt{Zmmul} multiplication extension. The EX stage evaluates branch conditions (\texttt{BEQ}, \texttt{BNE}, \texttt{BLT}, \texttt{BGE}, \texttt{BLTU}, \texttt{BGEU}) and calculates branch/jump target addresses:
    \begin{align}
    \text{Target}_{\text{branch/jal}} &= \text{PC}_{\text{EX}} + \text{imm}_{\text{EX}}, \\
    \text{Target}_{\text{jalr}} &= (\text{rs1}_{\text{EX}} + \text{imm}_{\text{EX}}) \ \& \ \sim 1.
    \end{align}
    Taken control transfers trigger a pipeline redirection, squashing the younger instructions in IF and ID.
    
    \item \textbf{Stage 4: Memory Access and Write-Back (MEM/WB)}:
    Combines data memory access and register file write-back into a unified terminal stage. For load and store instructions, the stage drives \texttt{io.dmem.addr}, \texttt{io.dmem.writeData}, \texttt{io.dmem.funct3}, and read/write strobes. Load data delivered by the memory bus is multiplexed with computational ALU results, upper immediates (\texttt{LUI}), and PC offsets (\texttt{AUIPC}, \texttt{JAL}, \texttt{JALR}) to generate the final write-back operand \texttt{wbData}, which commits synchronously to the register file at the end of the clock cycle.
\end{enumerate}

\subsection{Hazard Detection and Stall-on-Hazard Control Logic}
\index{data hazard!RAW stall}\index{hazard detection unit!boolean equations}

Data hazards arise when an instruction in the decode stage requires an operand that has not yet been committed to the architectural register file by an earlier instruction in the pipeline. Because this (intentionally) naively pipelined datapath does not implement full inter-stage execution bypass forwarding multiplexers, the processor handles data hazards by stalling: holding the dependent instruction in the decode stage until the producing instruction reaches the write-back stage.

\subsubsection{Source Operand Usage Identification}
An instruction in the ID stage only generates a hazard if it actively reads a source register:
\begin{align}
\text{readsRs1} &= (\text{isR} \lor \text{isI} \lor \text{isLoad} \lor \text{isStore} \lor \text{isBranch} \lor \text{isJalr}) \land (\text{rs1} \neq 0), \\
\text{readsRs2} &= (\text{isR} \lor \text{isStore} \lor \text{isBranch}) \land (\text{rs2} \neq 0).
\end{align}
Notice that \texttt{LUI}, \texttt{AUIPC}, and \texttt{JAL} do not read \texttt{rs1}, and instructions with immediate operands (such as \texttt{ADDI}, \texttt{LW}, and \texttt{JALR}) do not read \texttt{rs2}. Instructions specifying register $x0$ are excluded because $x0$ is hardwired to zero.

\subsubsection{Hazard Condition with Execute and Memory/Write-Back Stages}
In a pipeline without data forwarding, operands are read directly from the physical register storage array (\texttt{rs1Val = regFile.io.rs1\_data}). Because the register file updates synchronously on the rising clock edge at the end of the write-back cycle, a producing instruction's result is not available to the decode stage while that instruction is in the EX stage or the MEM/WB stage.

Therefore, the Hazard Detection Unit must detect RAW hazards across both stages:
\begin{align}
\text{exWillWrite}  &= \text{id\_ex.valid} \land \text{id\_ex.regWrite} \land (\text{id\_ex.rd} \neq 0), \\
\text{memWillWrite} &= \text{ex\_mem.valid} \land \text{ex\_mem.regWrite} \land (\text{ex\_mem.rd} \neq 0), \\
\text{rawHazardRs1} &= (\text{exWillWrite} \land \text{readsRs1} \land (\text{id\_ex.rd} == \text{d.rs1})) \lor \nonumber \\
                    &\quad (\text{memWillWrite} \land \text{readsRs1} \land (\text{ex\_mem.rd} == \text{d.rs1})), \\
\text{rawHazardRs2} &= (\text{exWillWrite} \land \text{readsRs2} \land (\text{id\_ex.rd} == \text{d.rs2})) \lor \nonumber \\
                    &\quad (\text{memWillWrite} \land \text{readsRs2} \land (\text{ex\_mem.rd} == \text{d.rs2})), \\
\text{stall}        &= \text{if\_id.valid} \land (\text{rawHazardRs1} \lor \text{rawHazardRs2}).
\end{align}

\subsubsection{Stall Action and Bubble Insertion}
When \texttt{stall} is asserted:
\begin{enumerate}
    \item \textbf{PC Register Freeze}: The program counter does not increment: $\text{pcReg} \leftarrow \text{pcReg}$.
    \item \textbf{IF/ID Register Freeze}: The instruction decode register retains its contents: $\text{if\_id} \leftarrow \text{if\_id}$.
    \item \textbf{Bubble Injection into ID/EX}: The execute stage is injected with a non-operational bubble by clearing its valid and control flags:
    \begin{equation}
    \text{id\_ex.valid} \leftarrow \text{false}, \quad \text{id\_ex.regWrite} \leftarrow \text{false}, \quad \text{id\_ex.memWrite} \leftarrow \text{false}.
    \end{equation}
\end{enumerate}

\subsubsection{Stall Latencies in the Absence of Forwarding}
In this baseline configuration without forwarding multiplexers:
\begin{itemize}
    \item \textbf{Distance-1 RAW Dependencies} (e.g., \texttt{ADD x1, x2, x3} immediately followed by \texttt{SUB x4, x1, x5}): 
    When \texttt{SUB} enters ID, \texttt{ADD} is in EX. \texttt{SUB} stalls for 1 cycle while \texttt{ADD} moves from EX to MEM/WB, and stalls for a second cycle while \texttt{ADD} is in MEM/WB. Thus, the stall penalty is exactly \textbf{2 clock cycles}.
    \item \textbf{Distance-2 RAW Dependencies} (e.g., \texttt{ADD x1, x2, x3}, an independent instruction, followed by \texttt{SUB x4, x1, x5}): 
    When \texttt{SUB} enters ID, \texttt{ADD} is in MEM/WB. \texttt{SUB} stalls for \textbf{1 clock cycle} while \texttt{ADD} completes writeback.
    \item \textbf{Distance-3 RAW Dependencies} (e.g., two independent instructions between producer and consumer): 
    When \texttt{SUB} enters ID, \texttt{ADD} has already retired and committed to the register storage. The stall penalty is \textbf{0 clock cycles}.
    \item \textbf{Load-Use Dependencies} (e.g., \texttt{LW x1, 0(x2)} followed by \texttt{ADD x3, x1, x4}):
    Because load data arrives in the MEM/WB stage, distance-1 load-use dependencies incur \textbf{2 stall cycles}.
\end{itemize}


\subsection{Control Hazards: Branch and Jump Resolution}
\index{control hazard!branch penalty}\index{pipeline flush!control transfer}

Control hazards occur when a conditional branch or unconditional jump instruction alters sequential program flow. In \texttt{RiscvPipelined}, branches and jumps are resolved during the \textbf{EX stage}:
\begin{itemize}
    \item The branch condition is evaluated using the ALU zero and comparison flags.
    \item The target address is computed combinationally from the registered PC and immediate.
\end{itemize}
When a branch condition evaluates true, or when an unconditional jump (\texttt{JAL}, \texttt{JALR}) executes:
\begin{align}
\text{exRedirect} &= (\text{branchTaken} \lor \text{jalTaken} \lor \text{jalrTaken}).
\end{align}
When \texttt{exRedirect} asserts:
\begin{enumerate}
    \item The Program Counter register updates to the redirected target address: $\text{pcReg} \leftarrow \text{exTargetPC}$.
    \item The \texttt{if\_id} register is flushed: $\text{if\_id.valid} \leftarrow \text{false}$.
    \item The \texttt{id\_ex} register is injected with a bubble: $\text{id\_ex.valid} \leftarrow \text{false}$.
\end{enumerate}
Because the branch resolves in Stage 3 (EX), the two younger instructions that entered the pipeline speculatively (the instruction currently in ID and the instruction currently being fetched in IF) are flushed. Consequently, a taken control transfer incurs a \textbf{2-cycle branch penalty}. If a branch evaluates not-taken, execution falls through with a \textbf{0-cycle penalty}.

Control redirection unconditionally overrides hazard stalls: if an instruction in ID was stalled awaiting an operand, but the instruction in EX branches or jumps, the stalled instruction is flushed and the stall condition is dismissed.

To obtain realistic silicon metrics, all physical implementations in this chapter target the ASAP7 7\,nm FinFET Predictive Process Design Kit (PDK) developed by Arizona State University in collaboration with ARM \cite{clark2016asap7}. ASAP7 models an advanced 7\,nm FinFET technology node with realistic lithographic design rules and physical parasitics:
\begin{itemize}
    \item \textbf{Standard-Cell Architecture}: We utilize the 7.5-track standard-cell library (\texttt{asap7sc7p5t\_28}) at the Regular $V_t$ (RVT) process corner, operating at nominal supply voltage $V_{dd} = 0.70\,\text{V}$ and junction temperature $T = 25^\circ\text{C}$ (Typical-Typical corner).
    \item \textbf{Timing Constraints and Driving Capacitance}: Static timing analysis is performed with an output capacitive load constraint of $C_{\text{load}} = 2.0\,\text{fF}$ applied across all primary outputs, reflecting typical local on-chip interconnect loading.
    \item \textbf{SRAM Memory Array Modeling}: In high-performance embedded SoCs, instruction and data memories are implemented as compiled SRAM macros rather than flip-flop arrays. For our timing closure, memory access latency is modeled with an unbuffered high-density FinFET SRAM access time of $T_{\text{sram}} = 0.500\,\text{ns}$ (500\,ps).

\end{itemize}

\subsubsection{Architectural Analysis of the RV32I Pipelined Speedup}

The synthesis and performance results of the \texttt{RV32I} baseline in ASAP7 7\,nm FinFET show:
\begin{enumerate}
    \item \textbf{The 4-Step Pipeline Delay Model}:
    In a processor implementation, instruction execution consists of four essential physical operations:
    \begin{itemize}
        \item \textbf{SRAM Fetch ($T_{\text{fetch}}$)}: The program counter updates, address is driven to instruction SRAM, and the 32-bit instruction word is retrieved. Modeled with a small standard 7\,nm FinFET SRAM macro ($T_{\text{sram}} = 0.500\,\text{ns}$), plus register clock-to-Q and setup, $T_{\text{fetch}} = \mathbf{0.550\,\text{ns}}$ (550\,ps).
        
        \item \textbf{Decode and Register Read ($T_{\text{decode}}$)}: The instruction decoder decodes opcodes and generates immediates ($0.209\,\text{ns}$), while the dual-read register file retrieves source register values $rs1$ and $rs2$ ($0.283\,\text{ns}$). With control steering, $T_{\text{decode}} = \mathbf{0.540\,\text{ns}}$ (540\,ps).
        
        \item \textbf{Execute ($T_{\text{execute}}$)}: The 32-bit ALU performs arithmetic, shifting, or comparison ($1.046\,\text{ns}$), followed by branch condition evaluation ($0.120\,\text{ns}$) and pipeline register setup, yielding $T_{\text{execute}} = \mathbf{1.363\,\text{ns}}$ (1,363\,ps). Crucially, the baseline ALU relies on a standard ripple-carry adder (RCA), which exhibits an isolated critical path propagation delay of $1.045\,\text{ns}$ in ASAP7 7\,nm FinFET. Notice that the ripple-carry adder alone has approximately $2\times$ the delay of any other pipeline stage in the entire processor ($1.045\,\text{ns}$ vs.\ $0.550\,\text{ns}$ for Fetch, $0.540\,\text{ns}$ for Decode, and $0.600\,\text{ns}$ for Write-Back). This slow adder represents the primary structural bottleneck unbalancing the pipeline.
        
        \item \textbf{SRAM Data Memory and Write-Back ($T_{\text{sram\_wb}}$)}: For load instructions, the memory address is presented to the data SRAM ($T_{\text{sram}} = 0.500\,\text{ns}$), the retrieved data is multiplexed with ALU and jump results ($0.080\,\text{ns}$), and routed to the register file write port ($0.020\,\text{ns}$ setup), totaling $T_{\text{sram\_wb}} = 0.600\,\text{ns}$ (600\,ps).
    \end{itemize}
    
    \item \textbf{FE Core Sum vs.\ Pipelined Core Max}:
    In the single-cycle Fetch-Execute (FE) processor, every instruction must traverse all four steps in series within a single clock cycle:
    \begin{align}
    T_{\text{clk, FE}} &= T_{\text{fetch}} + T_{\text{decode}} + T_{\text{execute}} + T_{\text{sram\_wb}} \nonumber \\
                       &= 0.550 + 0.540 + 1.363 + 0.600 = \mathbf{3.053\,\text{ns}} \quad (327.5\,\text{MHz}).
    \end{align}
    In the 4-stage pipelined processor, synchronous pipeline registers decouple the four steps into independent pipeline stages. The clock period is constrained only by the single longest pipeline step:
    \begin{align}
    T_{\text{clk, pipe}} &= \max\left(T_{\text{fetch}}, T_{\text{decode}}, T_{\text{execute}}, T_{\text{sram\_wb}}\right) \nonumber \\
                         &= \max(0.550, 0.540, 1.363, 0.600) = \mathbf{1.363\,\text{ns}} \quad (733.7\,\text{MHz}).
    \end{align}
    The clock period delta between the FE core and the pipelined core is therefore:
    \begin{equation}
    \Delta T = T_{\text{clk, FE}} - T_{\text{clk, pipe}} = 3.053\,\text{ns} - 1.363\,\text{ns} = \mathbf{1.690\,\text{ns}}.
    \end{equation}
    This reduction of $1.690\,\text{ns}$ represents the sum of the other three stages that are now overlapped across clock cycles, delivering a +124.0\% system frequency boost ($2.240\times$ frequency multiplier). However, the overall speedup is only about 20\%. We will now begin to enhance the pipeline performance.
\end{enumerate}

\section{Balancing the Pipeline: Selection and Integration of High-Performance Adders}\label{riscvAdderBalancing}
%*************************************************************************************
\index{pipeline balancing!adder optimization}\index{carry select adder!pipeline integration}

The critical path of the baseline 4-stage \texttt{RV32I} pipeline is overwhelmingly dominated by the Execute (EX) stage ($T_{\text{execute}} = 1.363\,\text{ns}$). More strikingly, the unoptimized 32-bit ripple-carry adder (RCA) embedded inside the baseline ALU accounts for $1.045\,\text{ns}$ of that latency---nearly \textbf{$2\times$ the delay of any other stage} in the entire processor ($T_{\text{fetch}} = 0.550\,\text{ns}$, $T_{\text{decode}} = 0.540\,\text{ns}$, and $T_{\text{sram\_wb}} = 0.600\,\text{ns}$). Because a synchronous pipeline can run no faster than its slowest stage, the slow ripple-carry adder acts as an anchor holding the clock frequency to $733.7\,\text{MHz}$, even though the remaining three-quarters of the machine are physically capable of clocking at $1.67\,\text{GHz}$ ($1 / 0.600\,\text{ns}$).

To eliminate this structural bottleneck, we select the high-performance adder identified in the empirical evaluation conducted in Chapter \ref{chap:perf_opt_logic} (Section \ref{sec:asap7_adders_synthesis}, Table \ref{tab:asap7_adders_comparison}). Among the 32-bit topologies evaluated in ASAP7 7\,nm FinFET technology (Ripple-Carry, Carry Lookahead, Brent-Kung, Kogge-Stone, and Carry-Select), the \textbf{Carry-Select Adder (CSelA)} achieves the lowest propagation delay: \textbf{519.83\,ps (0.520\,ns)}, delivering a \textbf{$2.01\times$ speedup} over the ripple-carry baseline and reaching a standalone frequency of \textbf{1.92\,GHz}. In deep-submicron FinFET standard cells, partitioning the 32-bit adder into 4-bit blocks allows speculative dual-carry chains ($C_{\text{in}} = 0$ and $C_{\text{in}} = 1$) to evaluate concurrently in under $120\,\text{ps}$. The block carry selection then ripples through an ultra-fast chain of transmission-gate multiplexers with an average delay of only $35\text{--}40\,\text{ps}$ per block, making it exceptionally fast at the 32-bit width. We therefore choose the Carry-Select Adder to replace the ripple-carry adder in our processor's execution unit.

\subsection{Integrating the High-Performance Adder in Chisel}
\index{Chisel!adder instantiation}

To integrate the Carry-Select Adder into the execution unit, the ALU's arithmetic subtraction and addition are routed through the dedicated adder module. In two's complement arithmetic, subtraction $A - B$ is computed as $A + \sim B + 1$, which is directly mapped to the adder's primary inputs and carry-in. 

Listing \ref{lst:chisel_csa_call} illustrates the revised execution stage design, showing only the high-performance adder invocation within the Chisel ALU.

\begin{chiselcode}[caption={Calling the high-performance Carry-Select Adder within the revised RISC-V ALU.},label={lst:chisel_csa_call}]
// Instantiating the 32-bit Carry-Select Adder within the revised ALU
val isSub = io.aluOp === AluOp.SUB
val adder = Module(new CarrySelectAdder(width = 32))
adder.io.a       := io.opA
adder.io.b       := Mux(isSub, ~io.opB, io.opB)
adder.io.carryIn := isSub
val addSubResult = adder.io.sum
\end{chiselcode}

By encapsulating the addition and subtraction inside the Carry-Select Adder, the ALU avoids generating CIRCT's default carry chains, replacing them with the optimized speculative block architecture.

\subsection{Impact on Pipeline Balancing and Clock Frequency}

\begin{itemize}
    \item \textbf{Adder Latency Delta}: $\Delta t_{\text{adder}} = 1.045\,\text{ns} - 0.520\,\text{ns} = \mathbf{-0.525\,\text{ns}}$ (a $50.3\%$ reduction in addition latency).

\section{Hardware Implementation and Benchmark Evaluation of Data Bypassing}\label{riscvBypassing}
\index{data bypassing}\index{forwarding unit}\index{hazard resolution!forwarding}\index{load-use hazard}

As demonstrated in Section \ref{riscvBenchmarks}, the unforwarded 4-stage pipeline suffers severe CPI inflation ($\text{CPI} = 1.63\text{--}1.93$) due to Read-After-Write (RAW) data dependencies. Because producing instructions do not commit their results to the architectural register file until the Memory/Write-Back (MEM/WB) stage, any consuming instruction in the Decode (ID) stage must stall for 2 clock cycles (for distance-1 dependencies) or 1 clock cycle (for distance-2 dependencies). Across real embedded workloads like Dhrystone and CoreMark, these stall cycles annihilate most of the frequency multiplier earned by pipelining, leaving an actual application speedup of only $1.16\times\text{--}1.27\times$.

To overcome this bottleneck, high-performance processors employ \textbf{data bypassing} (also known as \textbf{data forwarding}) \cite{patterson2017computer}. By capturing results as soon as they are computed and routing them directly to consuming stages over dedicated bypass multiplexers, dependencies can be satisfied immediately without waiting for register file writeback.

\subsection{Microarchitecture of the Forwarding Paths}
\index{forwarding paths}\index{distance-1 forwarding}\index{distance-2 forwarding}

In our 4-stage pipeline (IF, ID, EX, MEM/WB), data hazards arise from two temporal distances between the producing instruction and the consumer:
\begin{enumerate}
    \item \textbf{Distance-1 Hazards (MEM/WB $\to$ EX)}:
    The producing instruction has executed in EX and currently resides in the MEM/WB stage register (\texttt{ex\_mem}), while the consuming instruction is currently in the EX stage (\texttt{id\_ex}). In the unforwarded pipeline, this required a 2-cycle stall. 
    
    With forwarding, the result computed in EX is already available in the \texttt{ex\_mem} pipeline register. We construct bypass multiplexers at the inputs of the ALU, the branch comparator, and the \texttt{jalr} target adder. Whenever the instruction in MEM/WB will write to a non-zero destination register (\texttt{ex\_mem.regWrite} and $\texttt{ex\_mem.rd} \neq 0$) that matches the operand registers of the instruction in EX ($\texttt{ex\_mem.rd} == \texttt{id\_ex.rs1}$ or $\texttt{id\_ex.rs2}$), the forwarded value (\texttt{exMemFwdData}) replaces the operand read from the register file.
    
    The forwarded data depends on the instruction type:
    \begin{equation}
    \text{exMemFwdData} = 
    \begin{cases}
    \texttt{pc} + 4 & \text{if } \texttt{JAL} \text{ or } \texttt{JALR} \\
    \texttt{imm} & \text{if } \texttt{LUI} \\
    \texttt{pc} + \texttt{imm} & \text{if } \texttt{AUIPC} \\
    \texttt{aluResult} & \text{otherwise (arithmetic/logical/shift operations)}.
    \end{cases}
    \end{equation}
    Additionally, for store instructions (\texttt{SW}, \texttt{SH}, \texttt{SB}), if the stored data register \texttt{rs2} matches \texttt{ex\_mem.rd}, the forwarded value is routed directly into \texttt{ex\_mem.rs2Data}.
    
    \item \textbf{Distance-2 Hazards (WB $\to$ ID Register File Write-Through Bypass)}:
    The producing instruction is committing its writeback data (\texttt{wbData}) to the register file at the end of the MEM/WB stage, while the consuming instruction is in the ID stage reading its operands. If the register file reads synchronously or samples before write completion, the consumer reads stale data. 
    
    We eliminate this hazard by implementing an internal \textbf{write-through bypass} directly at the register file read outputs. If the writeback port is active ($\texttt{wbWen}$) and its destination matches either read address ($\texttt{wbRd} == \texttt{d.rs1}$ or $\texttt{wbRd} == \texttt{d.rs2}$ with $\texttt{wbRd} \neq 0$), \texttt{wbData} is multiplexed directly into \texttt{rs1Val} or \texttt{rs2Val}. This distance-2 hazard is resolved with \textbf{zero stall cycles}.
\end{enumerate}

\subsection{The Load-Use Hazard: The Single Irreducible Stall}
\index{load-use hazard!mechanics}\index{load-use delay}

Can data forwarding eliminate \textit{all} data hazard stalls? The answer is no: \textbf{Load-Use hazards} represent a fundamental physical barrier that no combinational forwarding network can resolve.

Consider a load instruction followed immediately by an instruction that consumes the loaded data:
\begin{lstlisting}[language=c]
lw   x1, 0(x2)     // Load word from memory into x1
addi x3, x1, 10    // Consume x1 immediately
\end{lstlisting}
When \texttt{lw} is in the EX stage, it computes the effective memory address ($\texttt{x2} + 0$). The actual data is not returned by the data memory until the end of the MEM stage! Meanwhile, \texttt{addi} is in the ID stage and will need \texttt{x1} as an ALU input when it enters the EX stage on the very next clock cycle. 

Because the memory data does not physically exist until the end of the MEM stage, forwarding it to the beginning of the EX stage would require transmitting information backward in time! Therefore, the Hazard Detection Unit must detect this condition:
\begin{equation}
\text{isLoadUseHazard} = \texttt{id\_ex.valid} \land \texttt{id\_ex.memRead} \land (\texttt{id\_ex.rd} \neq 0) \land \left((\text{readsRs1} \land \texttt{id\_ex.rd} == \texttt{d.rs1}) \lor (\text{readsRs2} \land \texttt{id\_ex.rd} == \texttt{d.rs2})\right).
\end{equation}
Upon detecting a Load-Use hazard, the hardware injects exactly \textbf{1 stall cycle} (freezing the PC and IF/ID pipeline registers while inserting a bubble/NOP into ID/EX). On the subsequent cycle, the loaded data is in the MEM/WB stage and is forwarded directly into the EX stage via the distance-1 forwarding network. Thus, load-use latency is reduced from 2 stall cycles down to just 1 stall cycle, while all other RAW dependencies incur 0 stalls!

\subsection{Chisel Implementation of Bypassing}
\index{Chisel!forwarding unit implementation}

Listing \ref{lst:chisel_forwarding_unit} shows the complete Chisel implementation of the forwarding multiplexers and revised hazard detection logic integrated into \texttt{RiscvPipelined.scala}.

\begin{chiselcode}[caption={Chisel implementation of distance-1 forwarding, distance-2 write-through bypass, and load-use hazard detection in \texttt{RiscvPipelined.scala}.},label={lst:chisel_forwarding_unit}]
// ========================================================
// STAGE 3: EXECUTE (EX) & FORWARDING UNIT (MEM/WB -> EX)
// ========================================================
val exMemWillWrite = ex_mem.valid && ex_mem.regWrite && (ex_mem.rd =/= 0.U)
val exMemFwdData = MuxCase(ex_mem.aluResult, Seq(
  (ex_mem.isJal || ex_mem.isJalr) -> (ex_mem.pc + 4.U),
  ex_mem.isLui                    -> ex_mem.imm,
  ex_mem.isAuipc                  -> (ex_mem.pc + ex_mem.imm)
))

val forwardRs1 = enableForwarding.B && exMemWillWrite && (ex_mem.rd === id_ex.rs1) && (id_ex.rs1 =/= 0.U)
val forwardRs2 = enableForwarding.B && exMemWillWrite && (ex_mem.rd === id_ex.rs2) && (id_ex.rs2 =/= 0.U)

val exRs1 = Mux(forwardRs1, exMemFwdData, id_ex.rs1Data)
val exRs2 = Mux(forwardRs2, exMemFwdData, id_ex.rs2Data)

alu.io.opA := exRs1
alu.io.opB := Mux(id_ex.aluSrc, id_ex.imm, exRs2)

// ========================================================
// STAGE 2: DECODE (ID) & WRITE-THROUGH BYPASS (WB -> ID)
// ========================================================
val wbBypassRs1 = enableForwarding.B && wbWen && (wbRd === d.rs1) && (d.rs1 =/= 0.U)
val wbBypassRs2 = enableForwarding.B && wbWen && (wbRd === d.rs2) && (d.rs2 =/= 0.U)
val rs1Val = Mux(wbBypassRs1, wbData, regFile.io.rs1_data)
val rs2Val = Mux(wbBypassRs2, wbData, regFile.io.rs2_data)

// ========================================================
// REVISED HAZARD DETECTION UNIT: LOAD-USE ONLY
// ========================================================
val isLoadUseHazard = id_ex.valid && id_ex.memRead && (id_ex.rd =/= 0.U) &&
                      ((readsRs1 && (id_ex.rd === d.rs1)) || (readsRs2 && (id_ex.rd === d.rs2)))

val stall = if_id.valid && Mux(enableForwarding.B, isLoadUseHazard, rawHazardRs1 || rawHazardRs2)
\end{chiselcode}

\section{Hardware Multiplication (Zmmul): The Pipeline Balancing Dilemma and Pipelined Datapath}\label{riscvHardwareMultiplier}\label{riscvZmmulCaseStudy}\label{riscvPipelinedMultiplier}
\index{Zmmul extension!microarchitectural case study}\index{pipeline balancing!multiplier bottleneck}\index{Amdahl's law!clock period unbalancing}\index{pipelined multiplier!single-stream acceleration}\index{multiply-accumulate (MAC)!zero-stall execution}

Having established the baseline performance of the 4-stage \texttt{RV32I} pipeline and the necessity of data bypassing, we now examine what happens when hardware multiplication is added. In scientific computing, machine learning, and digital signal processing, multiplication is ubiquitous. Implementing multiplication in software via shift-and-add routines (\texttt{\_\_mulsi3}) requires roughly 35 instructions per multiply, bloating code size and consuming significant execution cycles. 

To accelerate multiplication, the RISC-V standard defines the \texttt{Zmmul} extension, introducing four 32-bit multiplication instructions: \texttt{MUL} (lower 32 bits), \texttt{MULH} (upper 32 bits, signed $\times$ signed), \texttt{MULHSU} (upper 32 bits, signed $\times$ unsigned), and \texttt{MULHU} (upper 32 bits, unsigned $\times$ unsigned).

The comparative synthesis data reveals the dramatic consequences of pipeline unbalancing:
\begin{enumerate}
    \item \textbf{Annihilation of the Balanced Pipeline Frequency}:
    In the balanced \texttt{RV32I} core using the Carry-Select Adder (CSelA), all four stages require $\approx 0.54\text{--}0.60\,\text{ns}$, enabling the 4-stage pipeline to achieve an operating clock frequency of \textbf{1.67\,GHz} ($T_{\text{clk}} = 0.600\,\text{ns}$)---a \textbf{$3.82\times$ frequency multiplier} over the single-cycle baseline.
    
    However, when the unpipelined combinational multiplier is added to the execution stage, the Execute stage delay expands to $T_{\text{execute}} = \max(T_{\text{alu}}, T_{\text{mmul}}) = 2.462\,\text{ns}$ (dominated by the $2.148\,\text{ns}$ multiplier logic array plus multiplexer routing and register setup times). Because the entire synchronous pipeline is throttled by its slowest stage:
    \begin{equation}
    T_{\text{clk, pipe}} = \max(T_{\text{fetch}}, T_{\text{decode}}, T_{\text{mmul}}, T_{\text{sram\_wb}}) = \max(0.550, 0.540, 2.462, 0.600) = \mathbf{2.462\,\text{ns}}.
    \end{equation}
    The operating clock frequency of the processor collapses from \textbf{1.67\,GHz down to 406.2\,MHz}---a devastating \textbf{$-75.6\%$ frequency collapse} (a $4.10\times$ increase in clock period)!
    
    \item \textbf{Amdahl's Law and the Multiplier Breakeven Threshold}:
    This catastrophic frequency penalty exposes a critical system-level question: \textit{Under what conditions does adding an unpipelined hardware multiplier actually improve execution time over pure software multiplication?}
    
    Consider an application composed of $M$ multiplication operations and $O$ other general-purpose operations.
    \begin{itemize}
        \item On the balanced pure \texttt{RV32I} core ($T_{\text{clk}} = 0.600\,\text{ns}$), each multiplication is performed by the software routine \texttt{\_\_mulsi3} in $\approx 35$ instructions. Assuming baseline CPI, the software-multiply execution time is:
        \begin{equation}
        T_{\text{exec, soft}} = (O + 35M) \times \text{CPI} \times 0.600\,\text{ns}.
        \end{equation}
        \item On the unbalanced \texttt{RV32I\_Zmmul} core ($T_{\text{clk}} = 2.462\,\text{ns}$), each multiplication executes in 1 hardware instruction (\texttt{MUL}). However, \textit{every single instruction} now runs at the throttled $2.462\,\text{ns}$ clock period:
        \begin{equation}
        T_{\text{exec, hard}} = (O + 1M) \times \text{CPI} \times 2.462\,\text{ns}.
        \end{equation}
    \end{itemize}
    For the hardware multiplier to be beneficial ($T_{\text{exec, hard}} < T_{\text{exec, soft}}$):
    \begin{align}
    (O + M) \times 2.462 &< (O + 35M) \times 0.600, \\
    2.462\,O + 2.462\,M &< 0.600\,O + 21.000\,M, \\
    1.862\,O &< 18.538\,M \implies \frac{M}{O} > 0.1004.
    \end{align}
    Expressing this as the fraction of algorithmic multiplications $f_{\text{mul}} = \frac{M}{O + M}$:
    \begin{equation}
    f_{\text{mul}} > \frac{1.862}{18.538 + 1.862} = \frac{1.862}{20.400} \approx \mathbf{9.13\%}.
    \end{equation}
    Unless multiplications represent \textbf{more than 9.1\% of all algorithmic operations} (corresponding to $>77.8\%$ of dynamic instructions in the software-multiplication binary), \textbf{the core with the unpipelined hardware multiplier is slower than the pure RV32I core running software shift-and-add}! The $4.10\times$ clock penalty imposed on the remaining $90.9\%$ of instructions completely erases the algorithmic speedup of the hardware multiplier.
\end{enumerate}

\subsection{High-Performance Multipliers and Chisel Module Integration}
\index{Booth multiplier!Chisel integration}\index{multiplier!ASAP7 evaluation}

To investigate whether advanced multiplier topologies can resolve this bottleneck, we refer to the comprehensive physical synthesis evaluation conducted in Chapter \ref{chap:perf_opt_logic} (Section \ref{sec:high_performance_multipliers}, Table \ref{tab:ch15_asap7_multipliers}), where five 32-bit multiplier architectures were evaluated in ASAP7 7\,nm FinFET technology:
\begin{itemize}
    \item \textbf{Array Multiplier}: $1,967.86\,\text{ps}$ delay, $527.04\,\mu\text{m}^2$ area.
    \item \textbf{Radix-4 Modified Booth Multiplier}: $2,159.88\,\text{ps}$ delay, \textbf{464.45\,$\mu$m$^2$ area} ($-57.1\%$ area reduction).
    \item \textbf{Wallace Tree Multiplier}: $2,088.55\,\text{ps}$ delay, $627.77\,\mu\text{m}^2$ area.
    \item \textbf{Redundant Binary Multiplier (RBM)}: $2,245.91\,\text{ps}$ delay, $1,072.65\,\mu\text{m}^2$ area.
\end{itemize}
For standard-cell ASIC implementations, the \textbf{Radix-4 Modified Booth Multiplier} minimizes silicon area ($464.45\,\mu\text{m}^2$, saving 57.1\% area) while maintaining competitive latency. (In custom DSP layouts, the Redundant Binary Multiplier is selected for pitch-matched H-tree layout regularity).

However, as established in Chapter \ref{chap:perf_opt_logic}, \textbf{no single-cycle 32-bit multiplier can achieve a propagation delay under $\approx 1.97\text{--}2.25\,\text{ns}$ in standard cells}. To maintain high clock frequency without penalizing non-multiplication instructions, the multiplier must be pipelined.

\subsection{Single-Stream Acceleration: Two-Stage Pipelined Multiplier Datapath}
\index{pipelined multiplier!datapath}\index{intermediate pipeline registers}\index{zero-stall MAC}

In high-performance processor design, after stage delay balancing and general data forwarding are implemented, an essential microarchitectural technique within a single instruction stream is \textbf{pipelining complex execution units and utilizing inter-stage pipeline registers to hold intermediate unmerged results, coupled with specialized forwarding paths back to the execution stage}.

For compute-intensive digital signal processing (DSP) and machine learning workloads---most notably Finite Impulse Response (FIR) filtering, convolution, matrix-vector multiplication, and vector dot products---the execution profile is overwhelmingly dominated by back-to-back \textbf{Multiply-Accumulate (MAC)} instruction sequences:
\begin{lstlisting}[language=c]
// Canonical RISC-V FIR Filter Inner Loop
loop:
    lw   t0, 0(a7)     // Load input sample x[i]
    lw   t1, 0(a6)     // Load filter coefficient h[i]
    addi a6, a6, 4     // Advance coefficient pointer
    mul  t0, t1, t0    // Multiplication: t0 = x[i] * h[i]
    add  a5, t0, a5    // Accumulation (MAC): a5 += t0
    addi a7, a7, -4    // Decrement sample pointer
    bne  a6, a3, loop  // Loop termination test
\end{lstlisting}
In this canonical kernel, each multiplication (\texttt{mul}) is immediately followed by an accumulation (\texttt{add}) that consumes the product (\texttt{t0}) as its source operand.

To achieve an issue throughput approaching \textbf{1 instruction entering the pipeline per clock cycle} while operating at maximum clock frequency, we partition the hardware multiplier across two adjacent pipeline stages (EX and MEM/WB):
\begin{enumerate}
    \item \textbf{Stage 1: Multiplier Reduction in EX (\texttt{PipelinedMultiplierStage1})}:
    When a multiply instruction reaches EX, operands ($rs1$, $rs2$) are recoded using Radix-4 Booth logic into 17 partial products. A 6-level Carry-Save Adder (CSA) compressor tree reduces these 17 rows down to two unmerged 64-bit vectors: \texttt{sumOut} and \texttt{carryOut}. Crucially, \textit{no carry propagation occurs in EX} ($T_{\text{stage1}} \approx 0.61\,\text{ns}$).
    
    \item \textbf{Intermediate Pipeline Register Storage (\texttt{ex\_mem})}:
    At the rising clock edge, the inter-stage pipeline register \texttt{ex\_mem} captures the intermediate unmerged vectors:
    \begin{equation}
    \texttt{ex\_mem.mulSum} \leftarrow \texttt{mulStage1.sumOut}, \quad \texttt{ex\_mem.mulCarry} \leftarrow \texttt{mulStage1.carryOut}, \quad \texttt{ex\_mem.isMul} \leftarrow \texttt{id\_ex.isMul}.
    \end{equation}
    The intermediate pipeline register acts as temporary redundant storage, decoupling partial product reduction from final vector-merging addition.
    
    \item \textbf{Stage 2: Vector-Merging Addition in MEM/WB (\texttt{PipelinedMultiplierStage2})}:
    In the MEM/WB stage, a 64-bit vector-merging adder computes the final product:
    \begin{equation}
    \text{Product}[63:0] = \texttt{ex\_mem.mulSum} + \texttt{ex\_mem.mulCarry}.
    \end{equation}
    The multiplier output multiplexer slices bits $[31:0]$ (for \texttt{MUL}) or bits $[63:32]$ (for \texttt{MULH}, \texttt{MULHSU}, \texttt{MULHU}) to produce \texttt{mulStage2Result} ($T_{\text{stage2}} \approx 0.52\,\text{ns}$).
\end{enumerate}

\subsection{Forwarding Mechanics for Zero-Stall Multiply-Accumulate}
\index{forwarding!pipelined multiplier}\index{zero-stall MAC}

Now examine how instructions traverse this datapath during a back-to-back FIR/MAC operation:
\begin{itemize}
    \item \textbf{Cycle $k$}: \texttt{mul t0, t1, t0} is in ID; \texttt{add a5, t0, a5} is fetched in IF.
    \item \textbf{Cycle $k+1$}: \texttt{mul} enters EX. Stage 1 computes Booth PPG and the 6-level CSA tree into \texttt{mulSum} and \texttt{mulCarry}. \texttt{add} enters ID. Because \texttt{mul} is an arithmetic operation ($\texttt{id\_ex.memRead} == 0$), \textbf{no load-use hazard is detected}. The hazard unit asserts no stall ($\texttt{stall} == 0$), allowing \texttt{add} to advance directly into EX on the very next cycle!
    \item \textbf{Cycle $k+2$}: \texttt{mul} advances to MEM/WB. Stage 2 computes the final product \texttt{mulStage2Result}. Simultaneously, \texttt{add} enters EX. The forwarding unit detects $\texttt{ex\_mem.rd} == \texttt{id\_ex.rs1}$ (\texttt{t0}) and routes the completed product directly across the bypass bus to \texttt{alu.io.opA} in EX. The ALU computes the accumulation with \textbf{ZERO STALL CYCLES}!
    \item \textbf{Cycle $k+3$}: The next instruction in the inner loop enters EX, while \texttt{add} advances to MEM/WB.
\end{itemize}
Every single instruction in the compute sequence advances through the pipeline at \textbf{1 instruction entering the pipeline per clock cycle}!

\subsection{Chisel RTL Implementation}
\index{Chisel!pipelined multiplier}

Listing \ref{lst:chisel_pipelined_mul} shows the Chisel implementation of the pipelined multiplier integration, intermediate pipeline registers, and forwarding bypass in \texttt{RiscvPipelined.scala}.

\begin{chiselcode}[caption={Chisel implementation of the 2-stage pipelined multiplier, intermediate pipeline registers, and MEM/WB-to-EX forwarding in \texttt{RiscvPipelined.scala}.},label={lst:chisel_pipelined_mul}]
// ========================================================
// STAGE 3: EXECUTE (EX) - MULTIPLIER STAGE 1 (BOOTH + CSA)
// ========================================================
val mulStage1 = if (enableZmmul && enablePipelinedMul) 
  Some(Module(new PipelinedMultiplierStage1(width = xlen))) else None

if (mulStage1.isDefined) {
  mulStage1.get.io.a     := exRs1
  mulStage1.get.io.b     := Mux(id_ex.aluSrc, id_ex.imm, exRs2)
  mulStage1.get.io.mulOp := id_ex.aluOp
}

// Latch intermediate unmerged vectors into EX/MEM pipeline register
ex_mem.isMul    := id_ex.valid && id_ex.isMul
ex_mem.mulOp    := id_ex.aluOp
ex_mem.mulSum   := (if (mulStage1.isDefined) mulStage1.get.io.sumOut else 0.U)
ex_mem.mulCarry := (if (mulStage1.isDefined) mulStage1.get.io.carryOut else 0.U)

// ========================================================
// STAGE 4: MEM/WB - MULTIPLIER STAGE 2 (VECTOR-MERGING ADDER)
// ========================================================
val mulStage2 = if (enableZmmul && enablePipelinedMul) 
  Some(Module(new PipelinedMultiplierStage2(width = xlen))) else None

val mulStage2Result = WireDefault(0.U(xlen.W))
if (mulStage2.isDefined) {
  val m2 = mulStage2.get
  m2.io.sumIn   := ex_mem.mulSum
  m2.io.carryIn := ex_mem.mulCarry
  m2.io.mulOp   := ex_mem.mulOp
  mulStage2Result := m2.io.result
}

// Forward completed product directly into EX stage bypass network
val exMemFwdData = Wire(UInt(xlen.W))
if (enableZmmul && enablePipelinedMul) {
  exMemFwdData := Mux(ex_mem.isMul, mulStage2Result,
                  Mux(ex_mem.ctrl.memToReg, io.dmem.readData, ex_mem.aluResult))
} else {
  exMemFwdData := Mux(ex_mem.ctrl.memToReg, io.dmem.readData, ex_mem.aluResult)
}
\end{chiselcode}

\section{Control Hazard Elimination: Static BTFN and Dynamic Gshare Branch Prediction}\label{riscvBranchPrediction}
\index{branch prediction!static BTFN}\index{branch prediction!dynamic gshare}\index{branch target buffer (BTB)}\index{control hazard!elimination}

Having eliminated data hazards through full bypassing and pipelined execution units, we now confront the final remaining bottleneck in single-stream processor performance: \textbf{control hazards}.

\subsection{The Control Hazard Dilemma: Do Branches Complete Without Bubbles?}
\index{branch penalty!in 4-stage pipeline}\index{pipeline bubbles!taken branches}

To address the fundamental architectural question: \textit{Do branches complete on this 4-stage pipelined design without bubbles?}

The definitive answer is: \textbf{No, taken branches do not complete without bubbles in the baseline pipeline.}

In our 4-stage pipeline (\textsc{IF} $\to$ \textsc{ID} $\to$ \textsc{EX} $\to$ \textsc{MEM/WB}), branch condition evaluation and branch target calculation are performed in the \textsc{EX} stage:
\begin{align}
\text{Condition: } & \text{evaluates whether } \text{rs1} \mathrel{\mathbf{op}} \text{rs2} \quad (\texttt{BEQ}, \texttt{BNE}, \texttt{BLT}, \texttt{BGE}, \texttt{BLTU}, \texttt{BGEU}), \\
\text{Target Address: } & \text{Target} = \text{PC}_{\textsc{EX}} + \text{Imm}_{\textsc{EX}}.
\end{align}
By default, the Instruction Fetch (\textsc{IF}) stage fetches sequentially along the fall-through path ($\text{PC} + 4$). Consequently, the pipeline exhibits an asymmetric branch penalty:
\begin{enumerate}
    \item \textbf{Not-Taken Branches (0 Bubbles)}: When a branch condition evaluates false, the sequentially fetched instructions already advancing through \textsc{IF} and \textsc{ID} are correct. Execution proceeds without interruption: \textbf{0 stall cycles and 0 bubbles}.
    \item \textbf{Taken Branches (2 Bubbles)}: When a branch condition evaluates true in the \textsc{EX} stage, two younger instructions have already entered the pipeline:
    \begin{itemize}
        \item Instruction $i+1$ (currently residing in the \textsc{ID} stage, fetched when the branch was in \textsc{IF}),
        \item Instruction $i+2$ (currently being retrieved in the \textsc{IF} stage).
    \end{itemize}
    The \textsc{EX} stage must assert the pipeline flush signal (\texttt{exRedirect}), invalidating both \texttt{if\_id} and \texttt{id\_ex} pipeline registers. The program counter is redirected to $\text{Target}$, and the processor incurs an unavoidable \textbf{2-cycle branch penalty (2 bubbles)}.
\end{enumerate}

In tight numerical loops (such as FIR filters, matrix multiplication, and vector dot products), backwards loop branches are taken $>95\%$ of the time! Every single loop iteration pays a 2-bubble penalty. As a result, the CPI of a compute loop cannot fall below $1.25\text{--}1.35$ even with perfect ALU bypassing. To achieve true single-stream performance approaching 1 instruction per cycle ($\text{CPI} \to 1.0$), branches must be predicted and redirected in the \textbf{Instruction Fetch (\textsc{IF}) stage}, eliminating bubbles on taken branches.

\subsection{Static BTFN Branch Prediction with Branch Target Buffer}
\index{static branch prediction!BTFN}\index{BTFN!backward taken forward not taken}

The most widely deployed static branch prediction heuristic is \textbf{BTFN: Backward Taken, Forward Not-Taken}.

\subsubsection{Algorithmic Rationale}
In imperative software, loops are structured with a conditional branch at the bottom jumping backwards to the loop header:
\begin{equation}
\text{Target} < \text{PC} \implies \text{Loop Backwards Branch} \longrightarrow \textbf{Predict TAKEN}.
\end{equation}
Conversely, forward conditional branches ($\text{Target} \ge \text{PC}$) typically represent conditional error checks, null pointer validations, or exception handling that execute infrequently:
\begin{equation}
\text{Target} \ge \text{PC} \implies \text{Forward Conditional Branch} \longrightarrow \textbf{Predict NOT-TAKEN}.
\end{equation}
Unconditional jumps (\texttt{JAL}) are always taken.

\subsubsection{The Need for an IF-Stage Branch Target Buffer (BTB)}
\index{branch target buffer (BTB)!microarchitecture}
Static BTFN cannot operate simply by inspecting the branch offset in the instruction word, because instruction decoding does not occur until the \textsc{ID} stage! If the processor waited until \textsc{ID} to identify backward branches, it would still pay a 1-cycle bubble penalty.

To eliminate bubbles entirely (\textbf{0 bubbles}), the prediction and target calculation must occur combinationally in the \textbf{\textsc{IF} stage} using only the current $\text{PC}$. This requires a \textbf{Branch Target Buffer (BTB)}:
\begin{itemize}
    \item A cache-like structure of 32 direct-mapped entries in the \textsc{IF} stage, indexed by $\text{PC}[6:2]$.
    \item Each entry stores a valid bit (\texttt{btbValid}), a tag ($\text{PC}[31:7]$), a predicted target address (\texttt{btbTarget}), and a flag indicating whether the entry is an unconditional jump (\texttt{btbIsJal}).
    \item When $\text{PC}$ hits in the BTB:
    \begin{equation}
    \text{predTaken} = \text{btbHit} \land \bigl((\text{btbTarget} < \text{PC}) \lor \text{btbIsJal}\bigr).
    \end{equation}
    If \texttt{predTaken} is asserted, the next program counter is updated immediately to \texttt{btbTarget} for the very next clock cycle.
    \item The target instruction enters \textsc{IF} on cycle $t+1$, while the branch advances to \textsc{ID}. When the branch resolves in \textsc{EX} on cycle $t+2$, if the prediction was correct, \textbf{no pipeline flush occurs (\texttt{exRedirect = false})}. The target instruction is already in \textsc{EX}: \textbf{0 BUBBLES}!
\end{itemize}

\subsection{Dynamic Gshare Branch Prediction}
\index{dynamic branch prediction!gshare}\index{gshare predictor!Scott McFarling}

While static BTFN excels on simple backward loops, it exhibits fundamental limitations:
\begin{enumerate}
    \item It cannot adapt to data-dependent branches whose outcome varies dynamically at runtime.
    \item It always mispredicts the final loop exit, paying a 2-cycle penalty on every loop termination.
    \item It cannot exploit \textbf{branch correlation}---where the outcome of a branch depends on the outcomes of recently executed prior branches.
\end{enumerate}

To overcome these limitations, Scott McFarling (1993) introduced the \textbf{Gshare} branch predictor, a two-level adaptive predictor that hashes the branch address with a \textbf{Global History Register (GHR)}.

\subsubsection{Microarchitectural Structure}
As illustrated in Figure \ref{fig:gshare_arch}, Gshare consists of three tightly coupled structures:
\begin{enumerate}
    \item \textbf{Global History Register (GHR)}: An 8-bit shift register recording the actual direction ($1 = \text{Taken}$, $0 = \text{Not-Taken}$) of the last 8 committed branch instructions.
    \item \textbf{Pattern History Table (PHT)}: A table of $2^8 = 256$ two-bit saturating up/down counters. The states are defined as:
    \begin{itemize}
        \item \texttt{00} ($0$): Strongly Not-Taken,
        \item \texttt{01} ($1$): Weakly Not-Taken,
        \item \texttt{10} ($2$): Weakly Taken,
        \item \texttt{11} ($3$): Strongly Taken.
    \end{itemize}
    The most significant bit (MSB, bit 1) determines the prediction: $1 \implies \text{Taken}$, $0 \implies \text{Not-Taken}$. Two consecutive mispredictions are required to flip the prediction, preventing transient loop exits from corrupting steady-state behavior.
    \item \textbf{Gshare Hashing Function}: The index into the PHT is computed by bitwise XORing the branch PC with the global history:
    \begin{equation}
    \text{PHT\_Index} = \text{PC}[9:2] \oplus \text{GHR}[7:0].
    \end{equation}
    This hashing uniformly disperses branch instances across the 256 counter entries, reducing destructive aliasing between different branches while preserving correlation between consecutive branches.
    \item \textbf{Branch Target Buffer (BTB)}: As in BTFN, a 32-entry BTB supplies the predicted target address when the PHT counter predicts taken:
    \begin{equation}
    \text{predTaken} = \text{btbHit} \land \bigl(\text{PHT}[\text{PHT\_Index}][1] \lor \text{btbIsJal}\bigr).
    \end{equation}
\end{enumerate}

\subsection{Chisel Microarchitectural Implementation}
\index{Chisel!branch predictor implementation}\index{RiscvPipelined!branch prediction integration}

The branch predictor is implemented as a standalone, modular hardware module (\texttt{BranchPredictor.scala}) and integrated seamlessly into \texttt{RiscvPipelined.scala}.

Listing \ref{lst:branch_predictor_chisel} displays the core logic for both BTFN and Gshare prediction in Chisel:

\begin{chiselcode}[caption={Chisel implementation of the parameterized Branch Predictor supporting Static BTFN and Dynamic Gshare (scabook/riscv/BranchPredictor.scala).}, label={lst:branch_predictor_chisel}]
class BranchPredictor(
  val xlen: Int = 32,
  val predictorType: String = "none",
  val btbEntries: Int = 32,
  val historyWidth: Int = 8
) extends Module {
  val io = IO(new BranchPredictorIO(xlen, historyWidth))

  val normalizedType = predictorType.trim.toLowerCase

  if (normalizedType == "none") {
    io.predTaken   := false.B
    io.predTarget  := io.pc + 4.U
    io.predHistory := 0.U
  } else {
    // 32-entry Branch Target Buffer (BTB) in IF stage
    val indexBits = log2Ceil(btbEntries)
    val tagBits   = xlen - indexBits - 2

    val btbValid   = RegInit(VecInit(Seq.fill(btbEntries)(false.B)))
    val btbTags    = Reg(Vec(btbEntries, UInt(tagBits.W)))
    val btbTargets = Reg(Vec(btbEntries, UInt(xlen.W)))
    val btbIsJal   = RegInit(VecInit(Seq.fill(btbEntries)(false.B)))

    // IF stage query
    val ifIndex = io.pc(indexBits + 1, 2)
    val ifTag   = io.pc(xlen - 1, indexBits + 2)
    val btbHit  = btbValid(ifIndex) && (btbTags(ifIndex) === ifTag)
    val btbTarget = btbTargets(ifIndex)

    // EX stage update
    val updateIndex = io.updatePC(indexBits + 1, 2)
    val updateTag   = io.updatePC(xlen - 1, indexBits + 2)
    when(io.updateValid && io.actualTaken) {
      btbValid(updateIndex)   := true.B
      btbTags(updateIndex)    := updateTag
      btbTargets(updateIndex) := io.actualTarget
      btbIsJal(updateIndex)   := io.updateIsJal
    }

    if (normalizedType == "btfn") {
      // BTFN: Backward branches (target < pc) or JAL predicted TAKEN
      val isBackward = btbTarget < io.pc
      val isJal      = btbIsJal(ifIndex)
      val predTaken  = btbHit && (isBackward || isJal)

      io.predTaken   := predTaken
      io.predTarget  := Mux(predTaken, btbTarget, io.pc + 4.U)
      io.predHistory := 0.U
    } else {
      // GSHARE: 256-entry PHT indexed by PC XOR GHR
      val numPhtEntries = 1 << historyWidth
      val pht = RegInit(VecInit(Seq.fill(numPhtEntries)(2.U(2.W))))
      val ghr = RegInit(0.U(historyWidth.W))

      val pcHash    = io.pc(historyWidth + 1, 2)
      val phtIndex  = pcHash ^ ghr
      val counter   = pht(phtIndex)
      val dirTaken  = counter(1) // MSB = 1 -> Taken
      val isJal     = btbIsJal(ifIndex)
      val predTaken = btbHit && (dirTaken || isJal)

      io.predTaken   := predTaken
      io.predTarget  := Mux(predTaken, btbTarget, io.pc + 4.U)
      io.predHistory := ghr

      // PHT and GHR update upon branch commitment in EX
      val updateHash     = io.updatePC(historyWidth + 1, 2)
      val updatePhtIndex = updateHash ^ io.prevHistory
      when(io.updateValid && io.updateIsBr) {
        val currCnt = pht(updatePhtIndex)
        when(io.actualTaken) {
          pht(updatePhtIndex) := Mux(currCnt === 3.U, 3.U, currCnt + 1.U)
        }.otherwise {
          pht(updatePhtIndex) := Mux(currCnt === 0.U, 0.U, currCnt - 1.U)
        }
        ghr := Cat(ghr(historyWidth - 2, 0), io.actualTaken.asUInt)
      }
    }
  }
}
\end{chiselcode}

In the 4-stage pipeline (\texttt{RiscvPipelined.scala}), the Execute stage detects mispredictions by comparing actual branch resolution against the speculative prediction carried down the pipeline registers (\texttt{id\_ex.predTaken}, \texttt{id\_ex.predTarget}):
\begin{chiselcode}[caption={Misprediction detection and recovery logic in the Execute stage (scabook/riscv/RiscvPipelined.scala).}, label={lst:riscv_mispredict_chisel}]
  // Misprediction detection in EX:
  // If predicted outcome and target match actual execution: 0 FLUSH (0 BUBBLES)!
  val isBranch = id_ex.valid && id_ex.branch
  val branchMispredicted = isBranch && (
    (branchTaken =/= id_ex.predTaken) ||
    (branchTaken && (id_ex.predTarget =/= branchTarget))
  )
  val branchRecoveryPC = Mux(branchTaken, branchTarget, id_ex.pc + 4.U)

  val isJal = id_ex.valid && id_ex.isJal
  val jalMispredicted = isJal && (!id_ex.predTaken || (id_ex.predTarget =/= jalTarget))
  val jalrRedirect = id_ex.valid && id_ex.isJalr

  val exRedirect = branchMispredicted || jalMispredicted || jalrRedirect
  val exTargetPC = Mux(jalrRedirect, jalrTarget,
                   Mux(jalMispredicted, jalTarget,
                       branchRecoveryPC))
\end{chiselcode}

\subsection{Why Ideal Pipeline Speedup is Inaccessible in Practice}\label{riscvIdealSpeedupLimits}
\index{pipeline speedup!theoretical vs actual}\index{pipeline balancing!physical impediments}\index{stage delay quantization}\index{clock overhead}

In introductory computer architecture, pipelining an $N$-stage processor is frequently described as achieving an ideal speedup of:
\begin{equation}
S_{\text{ideal}} = N.
\end{equation}
For our 4-stage pipeline ($N = 4$), naive theory predicts a $4.00\times$ application speedup over the single-cycle core. In physical hardware, having systematically applied the full suite of single-instruction-stream microarchitectural techniques across this chapter---balancing stage delays to $\approx 0.60\text{--}0.65\,\text{ns}$ using Carry-Select Addition (CSelA), implementing distance-1 and distance-2 data bypassing, partitioning the hardware multiplier into a 2-stage pipelined datapath, and suppressing control hazard bubbles via dynamic Gshare branch prediction---the operating clock frequency scales from $436.7\,\text{MHz}$ ($2.290\,\text{ns}$) up to $1,538.5\,\text{MHz}$ ($0.650\,\text{ns}$), achieving a physical frequency multiplier of $\mathbf{3.52\times}$ ($3.82\times$ on pure RV32I without branch prediction).

Simultaneously, as demonstrated in Table \ref{tab:riscv_bp_benchmark_grand_summary}, these microarchitectural techniques drive execution cycles per instruction (CPI) down to near-unity: $\mathbf{\text{CPI} = 1.05}$ on the compute-intensive DSP kernels, $\mathbf{\text{CPI} = 1.09}$ on EEMBC CoreMark 1.0, and $\mathbf{\text{CPI} = 1.14}$ on Dhrystone 2.1. Consequently, the realized application speedup in physical 7\,nm FinFET silicon reaches $\mathbf{3.08\times}$ on Dhrystone, $\mathbf{3.22\times}$ on CoreMark, and $\mathbf{3.35\times\text{--}3.36\times}$ on the DSP workload!

While these measured speedups represent a major microarchitectural achievement---capturing over $80\text{--}84\%$ of theoretical maximum scalar throughput in physical standard cells---they do not reach the naive $4.00\times$ theoretical asymptote. 

The actual speedup of a pipelined processor over a single-cycle implementation is governed by the classic processor performance equation:
\begin{equation}
\text{Speedup} = \frac{\text{Time}_{\text{single}}}{\text{Time}_{\text{pipe}}} = \frac{I \times \text{CPI}_{\text{single}} \times T_{\text{clk, single}}}{I \times \text{CPI}_{\text{pipe}} \times T_{\text{clk, pipe}}} = \left(\frac{\text{CPI}_{\text{single}}}{\text{CPI}_{\text{pipe}}}\right) \times \left(\frac{T_{\text{clk, single}}}{T_{\text{clk, pipe}}}\right).
\end{equation}
For an $N$-stage pipeline, achieving $S = N = 4.00$ requires two simultaneous, ideal conditions:
\begin{enumerate}
    \item \textbf{Perfect Frequency Scaling}: $T_{\text{clk, pipe}} = \frac{1}{N} T_{\text{clk, single}}$ (i.e., exactly $4.00\times$ frequency multiplier).
    \item \textbf{Perfect CPI Invariance}: $\text{CPI}_{\text{pipe}} = \text{CPI}_{\text{single}} = 1.000$.
\end{enumerate}
In physical hardware, two fundamental real-world mechanisms account for the gap between the naive $4.00\times$ ceiling and the realized $3.08\times\text{--}3.36\times$ application speedups:

\subsubsection{Sequential Register Overhead and Clock Quantization}
\index{pipeline register overhead}\index{setup time}\index{clock-to-Q delay}
Combinational logic cannot be partitioned into fractional gate delays with infinite granularity. Furthermore, every physical pipeline stage boundary requires sequential state storage (D flip-flops in standard cells), which introduces clocking overhead into every clock cycle:
\begin{equation}
T_{\text{stage}} = T_{\text{comb}} + t_{\text{setup}} + t_{\text{cq}} + t_{\text{skew}}.
\end{equation}
In the ASAP7 7\,nm FinFET standard cell library:
\begin{itemize}
    \item Flip-flop setup time: $t_{\text{setup}} \approx 15\,\text{ps}$.
    \item Clock-to-Q propagation delay: $t_{\text{cq}} \approx 25\,\text{ps}$.
    \item Clock distribution skew and jitter margin: $t_{\text{skew}} \approx 15\,\text{ps}$.
\end{itemize}
This introduces an unshrinkable sequential overhead of $T_{\text{reg\_overhead}} \approx 55\,\text{ps}$ at each stage boundary. Across our 4-stage pipeline, over $200\,\text{ps}$ of cumulative cycle delay is consumed solely by sequential flip-flop overhead. This overhead represents dead time during which zero combinational logic work is evaluated, setting the physical upper bound on frequency scaling at $3.52\times\text{--}3.82\times$ rather than $4.00\times$.

\subsubsection{Residual Hazard Penalties and CPI Floors}
\index{hazard penalties}\index{load-use hazard}\index{CPI floor}
In a single-cycle processor, data dependencies and control flow transfers are resolved combinationally within the single clock cycle in which the instruction executes ($\text{CPI}_{\text{single}} \equiv 1.000$).

In the baseline pipelined processor without forwarding, Read-After-Write (RAW) data hazard stalls and taken branch flushes inflate CPI to $1.76\text{--}1.93$, eroding nearly half of the frequency advantage ($\text{Speedup} = 1.98\times\text{--}2.17\times$).

By implementing full data bypassing, 2-stage multiplier pipelining, and dynamic Gshare branch prediction, we eliminated over $89\%$ of all pipeline stalls. However, pushing CPI all the way down to $1.000$ in physical hardware is prevented by three residual, irreducible constraints:
\begin{enumerate}
    \item \textbf{Irreducible Load-Use Stalls}: When an instruction immediately consumes the value loaded by an antecedent memory load (\texttt{lw a0, 0(sp)} followed by \texttt{addi a0, a0, 1}), the data from the SRAM read port is not available until the end of Stage 4 (MEM/WB). The consumer in Stage 3 (EX) must stall for exactly 1 clock cycle regardless of bypassing. On CoreMark, load-use dependencies account for 27,915 unavoidable stall cycles.
    \item \textbf{Indirect Jump Address Generation (\texttt{JALR})}: Unlike direct branches and jumps whose targets are computed as static PC offsets in IF, indirect subroutine returns (\texttt{jalr x0, 0(ra)}) and function pointers depend on register values evaluated in EX. When \texttt{JALR} redirects control, two speculatively fetched instructions in IF and ID must be flushed, inserting 2 bubble cycles.
    \item \textbf{Residual Branch Mispredictions}: Although the 256-entry Gshare predictor achieves an impressive $92.7\%$ prediction accuracy on complex control flow, the remaining $7.3\%$ mispredicted branches incur a 2-cycle recovery flush. On CoreMark, this contributes 21,518 bubble cycles.
\end{enumerate}

Combining physical frequency scaling with empirical CPI yields the precise measured speedup on CoreMark:
\begin{equation}
\text{Speedup}_{\text{CoreMark, Gshare}} = \left(\frac{1.000}{1.094}\right) \times \left(\frac{2.290\,\text{ns}}{0.650\,\text{ns}}\right) = 0.914 \times 3.523 = \mathbf{3.22\times},
\end{equation}
and on the compute-bound DSP workload:
\begin{equation}
\text{Speedup}_{\text{DSP, Gshare}} = \left(\frac{1.000}{1.050}\right) \times \left(\frac{2.290\,\text{ns}}{0.650\,\text{ns}}\right) = 0.952 \times 3.523 = \mathbf{3.35\times}.
\end{equation}
These empirical findings demonstrate that while sequential flip-flop overhead and residual structural/hazard stalls prevent reaching naive theoretical ceilings, an optimized 4-stage pipeline operating at $\text{CPI} \approx 1.05\text{--}1.09$ achieves over $80\%$ of ideal performance in physical silicon.


\section{The Role of the Compiler in Processor Efficiency: Optimization Levels, Hazards, and Dynamic Execution}\label{riscvCompilerStudy}
\index{compiler!optimization levels and processor efficiency}
\index{microarchitecture!compiler interaction}

Having developed the architectural techniques for a single scalar instruction stream---pipelining the datapath, balancing adder and multiplier stages, implementing data forwarding, and deploying dynamic branch prediction---we have driven the cycles per instruction (CPI) of the 4-stage RV32I core down to near-unity ($\text{CPI} \approx 1.09$). However, processor performance is not determined by hardware microarchitecture alone. It is governed by the classic Iron Law of Processor Performance:
\begin{equation}
T_{\text{exec}} = \text{Instruction Count } (I) \times \text{Cycles Per Instruction } (\text{CPI}) \times \text{Clock Period } (T_{\text{clk}}).
\end{equation}
While physical pipelining minimizes the clock period $T_{\text{clk}}$ and microarchitectural bypassing and branch prediction minimize $\text{CPI}$, the compiler toolchain exerts sovereign control over the dynamic instruction count $I$ and the instruction mix. 

Before transitioning from a scalar pipeline to a superscalar multi-issue architecture, this section investigates the interplay between compiler optimization flags, static code generation, pipeline hazard dynamics, and dynamic execution efficiency across all five processor configurations developed in this chapter.

\subsection{Compiler Toolchain Discovery: The Baseline Configuration}
Inspection of the bare-metal benchmark build harness (\texttt{core\_portme.h} and the \texttt{.comment} metadata of compiled ELF binaries) reveals that the existing baseline Dhrystone and CoreMark binaries were compiled using the modern LLVM/Clang toolchain:
\begin{itemize}
    \item \textbf{Compiler}: \texttt{Ubuntu clang version 21.1.8 (6ubuntu1)} with \texttt{LLVM LLD 21.1.8}.
    \item \textbf{Target Architecture}: \texttt{riscv32-unknown-elf}, \texttt{march=rv32i}, \texttt{mabi=ilp32}.
    \item \textbf{Baseline Flags}: \texttt{-O1 -march=rv32i -mabi=ilp32 -ffreestanding -fno-builtin -nostdlib -fuse-ld=lld -T benchmarks/bench.ld}.
\end{itemize}
The baseline was explicitly set to \texttt{-O1}, representing basic linear optimization. To evaluate the full spectrum of compiler influence, we generated freestanding standalone binaries across ten optimization configurations: \texttt{-O0}, \texttt{-O1}, \texttt{-O2}, \texttt{-O3}, \texttt{-O4}, \texttt{-O5}, \texttt{-Os}, \texttt{-Oz}, \texttt{-Ofast}, and an extreme \texttt{ridiculous} optimization suite.

\subsection{Taxonomy of Compiler Optimization Levels in Modern Clang/LLVM}
The compilation options impact the generated code structure as follows:
\begin{enumerate}
    \item \textbf{\texttt{-O0} (Unoptimized Baseline)}:
    Register allocation for local variables is disabled. Every local variable and intermediate expression is allocated to a dedicated stack frame slot in memory. Consequently, every arithmetic operation is preceded by stack loads (\texttt{lw}) and followed by stack stores (\texttt{sw}), flooding the pipeline with memory traffic.
    
    \item \textbf{\texttt{-O1} (Basic Optimization)}:
    Enables global register allocation, basic block merging, constant folding, and dead-code elimination. Variables reside in the 32 general-purpose registers rather than on the stack, dramatically reducing load/store instructions.
    
    \item \textbf{\texttt{-O2} (Production Optimization)}:
    Enables global common subexpression elimination (CSE), loop-invariant code motion (LICM), peephole optimization, and static instruction scheduling designed to interleave independent instructions.
    
    \item \textbf{\texttt{-O3} (Aggressive Optimization)}:
    Enables aggressive function inlining, predictive loop unrolling, and vectorization analysis. Loop bounds and bodies are transformed to maximize execution throughput at the expense of moderate code size growth.
    
    \item \textbf{\texttt{-O4} and \texttt{-O5} (Clang Aliases)}:
    In modern Clang/LLVM, levels above \texttt{-O3} do not exist as distinct optimization passes. Invoking \texttt{-O4} triggers a compiler warning (\texttt{warning: -O4 is equivalent to -O3 [-Wdeprecated]}), while \texttt{-O5} emits \texttt{warning: optimization level '-O5' is not supported; using '-O3' instead}. Exact MD5 cryptographic checksum analysis confirms that the binaries generated under \texttt{-O3}, \texttt{-O4}, and \texttt{-O5} are \textbf{100.000\% bit-for-bit identical} (MD5 checksum: \texttt{7b4e53a5511b5e49...} on CoreMark).
    
    \item \textbf{\texttt{-Ofast} (Fast Math)}:
    Enables all \texttt{-O3} optimizations along with non-standard, fast floating-point arithmetic (\texttt{-ffast-math}). Because both CoreMark and Dhrystone are pure integer/pointer benchmarks without floating-point operations, \texttt{-Ofast} produces \textbf{identical machine code to \texttt{-O3}}.
    
    \item \textbf{\texttt{-Os} and \texttt{-Oz} (Code Size Minimization)}:
    \texttt{-Os} optimizes for minimum code size while maintaining execution speed. \texttt{-Oz} pushes code density to the absolute extreme: inlining is disabled, common tail sequences are merged into shared helper subroutines, and loop bodies are strictly preserved rather than unrolled.
    
    \item \textbf{\texttt{ridiculous} (Extreme Inlining and Loop Unrolling)}:
    To test the absolute limits of compiler aggression on RISC-V, we evaluated a specialized high-performance flag combination:
    \begin{lstlisting}[language=bash]
clang -O3 -flto -funroll-loops -fomit-frame-pointer \
      -mllvm -inline-threshold=2000 -mllvm -unroll-threshold=2000 ...
    \end{lstlisting}
    This forces Link-Time Optimization (LTO) across all compilation units, aggressively inlines nested call graphs, and fully unrolls major loop kernels.
\end{enumerate}

    At \texttt{-O0}, memory instructions (Loads + Stores) account for \textbf{50.7\%} of the entire CoreMark binary and \textbf{47.9\%} of Dhrystone. Because registers are not allocated to hold intermediate values, the compiler generates back-to-back \texttt{sw} and \texttt{lw} operations around every single arithmetic instruction. When optimization is enabled (\texttt{-O1} to \texttt{-O3}), register allocation slashes memory instructions down to $\sim 28\%$, allowing register-to-register ALU instructions to dominate ($59\text{--}65\%$).
    
    \item \textbf{The Code-Density Paradox of \texttt{-Oz}}:
    \texttt{-Oz} achieves the absolute smallest static footprint: CoreMark text shrinks by \textbf{31.1\%} ($12,792\,\text{B} \to 8,812\,\text{B}$) and Dhrystone shrinks by \textbf{24.3\%} ($3,085\,\text{B} \to 2,336\,\text{B}$). However, to achieve this compactness, the compiler aggressively outlines repeated code into small functions, causing jump instructions (\texttt{jal}/\texttt{jalr}) to jump from $7.4\%$ up to $10.9\%$ in CoreMark. As shown below, this static density comes at severe dynamic runtime cost!
    
    \item \textbf{Binary Explosion under \texttt{ridiculous} Optimization}:
    Forcing loop unrolling and function inlining expands CoreMark text by \textbf{$5.1\times$} ($11,976\,\text{B} \to 61,116\,\text{B}$, with static instructions expanding from $2,655$ to $15,199$) and Dhrystone text by \textbf{$4.7\times$} ($2,993\,\text{B} \to 14,028\,\text{B}$). Loop branches are replaced with straight-line replicated ALU instructions, lowering branch instructions from $4.4\%$ down to $1.4\%$.
\end{enumerate}

\subsection{Microarchitectural Analysis: Why the Compiler Cannot Fix an Unforwarded Pipeline}
The empirical results in Tables \ref{tab:compiler_dynamic_coremark} and \ref{tab:compiler_dynamic_dhrystone} reveal four fundamental lessons in computer engineering:

\begin{enumerate}
    \item \textbf{The Software Isolation of Pipeline Stalls}:
    A common misconception is that a sufficiently sophisticated compiler can eliminate pipeline stalls via instruction scheduling. The data decisively refutes this: on the \texttt{4-Stage NoFwd} core, the CPI remains stubbornly anchored at $\mathbf{1.88\text{--}1.90}$ across \texttt{-O1}, \texttt{-O2}, \texttt{-O3}, and \texttt{ridiculous}! Because basic blocks in integer C programs typically contain only 4 to 6 instructions with dense register dependencies, the compiler runs out of independent instructions to schedule into the 2-cycle hazard delay slots. The unforwarded core suffers \textbf{over 506,000 RAW stalls} regardless of compiler aggression. Pipeline stalls are a hardware defect that software cannot schedule away.
    
    \item \textbf{Data Bypassing as the Great Equalizer}:
    Hardware data bypassing slashes CoreMark data stalls by \textbf{94.6\%} (from 517,244 down to 27,915 stalls at \texttt{-O1}), leaving only irreducible Load-Use stalls. This drops the CPI from $1.88$ to $1.32\text{--}1.33$ across all optimization levels.
    
    \item \textbf{Branch Prediction Accuracy Across Optimization Levels}:
    Static BTFN branch prediction reduces CoreMark branch mispredictions by $76.6\%$ (from 97,308 down to 22,764). Dynamic Gshare prediction cuts mispredictions by \textbf{88.9\%} (down to 10,759 mispredictions out of 147,627 dynamic branches, an overall prediction accuracy of \textbf{92.7\%}). This eliminates over 173,000 branch flush bubbles, bringing CoreMark CPI down to \textbf{1.09}.
    
    \item \textbf{The Runtime Cost of Extreme Code Size Optimization (\texttt{-Oz})}:
    While \texttt{-Oz} successfully minimizes code size to 8.8\,KB, it causes dynamic instruction count to expand by \textbf{+11.2\%} on CoreMark ($859,290 \to 955,942$) and by \textbf{+199.7\%} on Dhrystone ($10,212 \to 30,605$). Total execution time on the Gshare core increases from $614.1\,\mu\text{s}$ (\texttt{-O3}) to $681.5\,\mu\text{s}$ (\texttt{-Oz}), demonstrating the universal trade-off between memory footprint and execution latency.
\end{enumerate}

\subsection{The Scalar Asymptote: Reaching the Asymptotic Scalar Limit}
Notice the effective CPI achieved on the \texttt{4-Stage Gshare} core across all optimized variants:
\begin{equation}
\text{CPI}_{\text{CoreMark, O1}} = 1.09, \quad \text{CPI}_{\text{CoreMark, O2}} = 1.10, \quad \text{CPI}_{\text{CoreMark, O3}} = 1.10, \quad \text{CPI}_{\text{CoreMark, ridic}} = 1.10.
\end{equation}
In a single-issue scalar processor, the theoretical maximum instruction throughput is strictly bounded by:
\begin{equation}
\text{IPC}_{\text{max}} = 1.00 \quad \iff \quad \text{CPI}_{\text{min}} = 1.00.
\end{equation}
An achieved CPI of $1.094$ corresponds to an issue throughput of $\text{IPC} = 0.914$ instructions per cycle. In other words, \textbf{the 4-stage RV32I core with bypassing and Gshare branch prediction is operating at 91.4\% of theoretical maximum scalar throughput}!

The residual $8.6\%$ overhead consists of physical constraints inherent to scalar execution:
\begin{itemize}
    \item True load-use data stalls (1 cycle when an instruction immediately consumes data loaded from memory).
    \item Indirect jump redirects (\texttt{JALR} targets must be computed in EX, incurring 2 bubbles).
    \item The remaining $7.3\%$ branch mispredictions.
\end{itemize}
We have reached the physical and algorithmic performance ceiling of a single instruction stream.


\section{Advanced Pipeline Partitioning: Superpipelining and Logic Retiming}\label{riscvSuperpipelining}
\index{superpipelining}\index{pipeline retiming}\index{logic migration across stage boundaries}

Throughout this chapter, our 4-stage pipeline balanced the primary pipeline stages to $\approx 0.55\text{--}0.65\,\text{ns}$ ($1.54\text{--}1.67\,\text{GHz}$) in ASAP7 7\,nm FinFET technology. When operating within a single scalar instruction stream, further frequency scaling requires deeper microarchitectural transformations beyond stage-level balancing:
\begin{enumerate}
    \item \textbf{Sub-Stage Partitioning (Superpipelining)}:
    Advanced processors split each of the four physical stages in half, transforming the 4-stage pipeline into an 8-stage superpipelined machine where each sub-stage has a target latency of only $\approx 0.28\text{--}0.30\,\text{ns}$:
    \begin{itemize}
        \item \textbf{Stage 1: Fetch (IF)} is partitioned into:
        \begin{itemize}
            \item \textbf{IF1 (Next-PC Generation and Branch Prediction)}: Evaluates branch target buffer (BTB) lookups, branch prediction tables, and next sequential address computation ($0.25\,\text{ns}$).
            \item \textbf{IF2 (Instruction SRAM Access)}: Synchronous memory access into high-density SRAM arrays and instruction latching ($0.30\,\text{ns}$).
        \end{itemize}
        \item \textbf{Stage 2: Decode (ID)} is partitioned into:
        \begin{itemize}
            \item \textbf{ID1 (Instruction Decode and Hazard Detection)}: Instruction opcode decoding, immediate extraction/sign-extension, and dependency detection ($0.26\,\text{ns}$).
            \item \textbf{ID2 (Register File Operand Read)}: Multi-port SRAM register file read and operand steering ($0.28\,\text{ns}$).
        \end{itemize}
        \item \textbf{Stage 3: Execute (EX)} is partitioned into:
        \begin{itemize}
            \item \textbf{EX1 (Operand Pre-Processing and Early Arithmetic)}: Bypass operand selection multiplexing and preliminary speculative carry/sum tree generation ($0.28\,\text{ns}$).
            \item \textbf{EX2 (Final Addition and Branch Resolution)}: Final carry-propagate addition, barrel shifter completion, and zero/sign condition comparison ($0.30\,\text{ns}$).
        \end{itemize}
        \item \textbf{Stage 4: Memory Access and Write-Back (MEM/WB)} is partitioned into:
        \begin{itemize}
            \item \textbf{MEM (Data Memory Access)}: Synchronous read/write access to the data SRAM array ($0.30\,\text{ns}$).
            \item \textbf{WB (Write-Back Commit)}: Write-back multiplexing and synchronous commit into the architectural register file ($0.25\,\text{ns}$).
        \end{itemize}
    \end{itemize}
    In ASAP7 7\,nm FinFET technology, this 8-stage superpipelined organization achieves an operating clock period of under $0.30\,\text{ns}$, unlocking operating clock frequencies exceeding \textbf{3.3\,GHz}.
    
    \item \textbf{Pipeline Balancing via Logic Migration and Register Retiming}:
    In addition to sub-stage splitting, microarchitects balance uneven pipelines by \textbf{moving combinational logic across pipeline register boundaries} (a technique known as \textit{register retiming} or \textit{logic migration}):
    \begin{itemize}
        \item \textbf{Moving Effective Address Calculation to ID}: In architectures with base+displacement addressing (\texttt{lw rd, imm(rs1)}), moving the address generation addition into the Decode stage (forming a dedicated Address Generation Unit, AGU) allows the Memory stage to initiate SRAM access immediately at the start of the next cycle.
        \item \textbf{Moving Branch Comparison to WB}: Alternatively, deferring branch condition evaluation to a later stage or moving branch target address calculation forward into the IF buffer balances the computational load between stages.
        \item \textbf{Pre-decoding in the Fetch Buffer}: Placing lightweight pre-decode logic inside the instruction fetch buffer can pre-extract register specifiers ($rs1, rs2, rd$) and immediate formats before instructions enter the formal Decode stage, shifting delay backwards into available timing slack.
    \end{itemize}
\end{enumerate}



\section{Memory Hierarchy and Cache Design: Bridging the Memory Wall with Caching}\label{riscvCaching}
\index{cache memory}\index{memory hierarchy}\index{memory wall}\index{L1 cache}\index{DDR-5 DRAM}\index{write-back cache}\index{set-associativity}

Throughout the preceding sections of this chapter, all microarchitectural optimizations---carry-select adder balancing, ALU and multiplier pipelining, full data bypassing, static BTFN, dynamic Gshare branch prediction, and compiler optimizations---were evaluated under the simplifying assumption of an \textbf{ideal flat memory}. In this idealized model, every instruction fetch from instruction memory and every load/store operation to data memory completes instantaneously in exactly one clock cycle ($1\,T_{\text{clk}}$), presenting zero memory stall bubbles to the datapath.

In physical computing systems, however, this assumption is fundamentally decoupled from silicon reality. While modern processor datapaths operating in 7\,nm FinFET technology run at gigahertz clock frequencies (e.g., $1.538\,\text{GHz}$, $T_{\text{clk}} = 0.650\,\text{ns}$), the physical distance and capacitive loading required to route signals off-chip to main memory (such as DDR-5 SDRAM) create a latency disparity spanning hundreds of processor clock cycles. This growing disparity between processor core cycle times and off-chip memory access latency is known as the \textbf{Memory Wall}.

To bridge this memory wall, computer architects introduce a \textbf{memory hierarchy} consisting of high-speed on-chip \textbf{caches}. In this section, we take our highest-performing single-issue scalar core---the \textbf{4-Stage RV32I\_Zmmul core with CSelA balancing, Pipemul, full bypassing, and Dynamic Gshare Branch Prediction}---and integrate parameterized on-chip Level-1 Instruction (I-Cache) and Data (D-Cache) memories. We evaluate the system against a realistic DDR-5 main memory subsystem, isolate the microarchitectural behavior of instruction and data caches across capacities and set-associativities, synthesize the design in ASAP7 7\,nm FinFET technology to assess physical timing and silicon area, and analyze multi-level cache hierarchies for complex embedded workloads.

\subsection{The Memory Wall and Main Memory Latency in Modern Systems}
\index{memory wall!DDR-5 DRAM latency}\index{miss penalty}\index{Amdahl's law!memory wall}

In modern computing systems, main memory is implemented using Dynamic Random-Access Memory (DRAM). In current-generation DDR-5 SDRAM architectures (e.g., DDR5-4800 to DDR5-6400), an off-chip memory transaction requires:
\begin{enumerate}
    \item Command arbitration and queuing within the on-chip memory controller.
    \item Physical PHY layer serialization and transmission across the printed circuit board (PCB) traces.
    \item DRAM row activation ($t_{\text{RCD}}$, typically $14\text{--}16\,\text{ns}$).
    \item Column access strobe latency ($t_{\text{CAS}}$ or $t_{\text{CL}}$, typically $14\text{--}16\,\text{ns}$).
    \item Data burst transmission and on-die termination across the 64-bit/32-bit channel ($t_{\text{burst}}$).
    \item Memory controller de-serialization and internal bus return to the processor core.
\end{enumerate}
In typical desktop, server, and high-performance embedded systems, the total round-trip latency to retrieve a cache line from DDR-5 DRAM is approximately $65\,\text{ns}$.

At our processor core's operating frequency of $1.538\,\text{GHz}$ ($T_{\text{clk}} = 0.650\,\text{ns}$ in ASAP7 7\,nm FinFET), this off-chip memory latency translates to a staggering penalty:
\begin{equation}\label{eq:riscv_dram_latency}
P_{\text{mem}} = \frac{T_{\text{DDR-5}}}{T_{\text{clk}}} = \frac{65.0\,\text{ns}}{0.650\,\text{ns}} = 100 \text{ processor clock cycles}.
\end{equation}

When an instruction or data reference misses in the on-chip cache and must be fetched from DDR-5 DRAM, the processor core is stalled for $100$ clock cycles. The effective Clock Cycles per Instruction ($\text{CPI}_{\text{effective}}$) of the system is governed by the memory stall equation:
\begin{equation}\label{eq:riscv_cpi_memory}
\text{CPI}_{\text{effective}} = \text{CPI}_{\text{base}} + \left(\frac{\text{Misses}_{\text{I}}}{I} \times P_{\text{mem}}\right) + \left(\frac{\text{Misses}_{\text{D}}}{I} \times P_{\text{mem}}\right),
\end{equation}
where $\text{CPI}_{\text{base}}$ is the baseline execution CPI under ideal single-cycle memory (e.g., $1.094$ for CoreMark with Gshare prediction), $I$ is the total dynamic instruction count, and $\text{Misses}_{\text{I}}$ and $\text{Misses}_{\text{D}}$ denote the total misses incurred by instruction fetch and data memory operations, respectively. Defining the standard metric \textbf{Misses Per Kilo-Instruction} ($\text{MPKI}$):
\begin{equation}
\text{MPKI} = \frac{\text{Misses}}{I} \times 1000,
\end{equation}
Equation \ref{eq:riscv_cpi_memory} simplifies to:
\begin{equation}\label{eq:riscv_cpi_mpki}
\text{CPI}_{\text{effective}} = \text{CPI}_{\text{base}} + \left(\frac{\text{MPKI}_{\text{I}} + \text{MPKI}_{\text{D}}}{1000}\right) \times P_{\text{mem}}.
\end{equation}

\subsubsection{The Catastrophic Cost of Uncached Execution}
Consider what happens if a high-performance $1.54\,\text{GHz}$ processor is connected directly to DDR-5 main memory without an on-chip cache:
\begin{itemize}
    \item Every instruction fetch requires access to main memory: $\frac{\text{Misses}_{\text{I}}}{I} = 1.00 \implies \text{MPKI}_{\text{I}} = 1000$.
    \item In a typical RISC-V program where $25\%$ of instructions are loads or stores: $\frac{\text{Misses}_{\text{D}}}{I} = 0.25 \implies \text{MPKI}_{\text{D}} = 250$.
\end{itemize}
Substituting into Equation \ref{eq:riscv_cpi_mpki} with $P_{\text{mem}} = 100$:
\begin{equation}
\text{CPI}_{\text{uncached}} = 1.094 + (1.00 \times 100) + (0.25 \times 100) = 1.094 + 100 + 25 = 126.094.
\end{equation}
The processor's instruction execution rate collapses by two orders of magnitude:
\begin{equation}
\text{Throughput}_{\text{uncached}} = \frac{1.538 \times 10^9}{126.094} = 12.2\,\text{MIPS} \quad \text{vs.} \quad \frac{1.538 \times 10^9}{1.094} = 1,405.8\,\text{MIPS}.
\end{equation}
Over $\mathbf{99.1\%}$ of the processor's compute capability is completely wasted waiting for memory transfers! This mathematical reality demonstrates that high clock frequency is meaningless without a highly optimized on-chip cache hierarchy.

The cache architecture is parameterized along the following key dimensions:
\begin{enumerate}
    \item \textbf{Line (Block) Size ($L$)}: We fix the cache line size to $L = 32\,\text{bytes}$ ($256$ bits, or $8 \times 32$-bit words). A 32-byte line size amortizes the 100-cycle DDR-5 latency across 8 consecutive instruction fetches or data references, exploiting spatial locality.
    \item \textbf{Cache Capacity ($C$)}: The total data storage capacity sweeps from $512\,\text{bytes}$ to $32\,\text{KB}$.
    \item \textbf{Set-Associativity ($W$)}: We evaluate Direct-Mapped ($1$-way), $2$-way set-associative, and $4$-way set-associative configurations.
\end{enumerate}

\subsubsection{Address Partitioning and Bit Allocation}

\begin{equation}
\underbrace{A[31 : 5 + s]}_{\text{Tag: } t = 27 - s \text{ bits}} \quad \Big\Vert \quad \underbrace{A[4 + s : 5]}_{\text{Index: } s \text{ bits}} \quad \Big\Vert \quad \underbrace{A[4 : 2]}_{\text{Word: } 3 \text{ bits}} \quad \Big\Vert \quad \underbrace{A[1 : 0]}_{\text{Byte: } 2 \text{ bits}}
\end{equation}
where the number of sets $S = 2^s$ is determined by:
\begin{equation}
S = \frac{C}{W \times L} = \frac{C}{W \times 32}.
\end{equation}

\subsubsection{Victim Replacement and Write Policies}
\begin{itemize}
    \item \textbf{Replacement Policy}: In 2-way set-associative caches, an exact 1-bit per-set Least Recently Used (\textbf{LRU}) register tracks which way was referenced least recently. In 4-way set-associative caches, we implement a 3-bit \textbf{Tree-Pseudo-LRU (Tree-PLRU)} state machine per set, which approximates true LRU with minimal gate overhead.
    \item \textbf{Write Policy for L1 Data Cache}: We implement a \textbf{Write-Back with Write-Allocate} policy. When a store hits in the D-cache, data is updated in the SRAM array and a \textit{dirty bit} associated with that cache block is asserted, avoiding expensive bus writes to main memory. When a store misses, the 32-byte cache line is fetched from memory into the cache (\textit{write-allocate}), modified, and marked dirty. Only when a dirty block is evicted to make room for a new refill does the cache write the dirty line back to main memory.
\end{itemize}

\subsection{Chisel RTL Implementation: \texttt{L1Cache} and \texttt{RiscvCachedPipelined}}
\index{Chisel!L1 cache}\index{Chisel!pipeline freeze logic}

The hardware implementation is factored into two reusable, parameterized Chisel modules:
\begin{enumerate}
    \item \texttt{L1Cache.scala}: A synthesizable cache module implementing parallel tag comparison, 1-hot data multiplexing, pseudo-LRU replacement, and a 5-state memory refill/writeback finite state machine (FSM).
    \item \texttt{RiscvCachedPipelined.scala}: The complete 4-stage pipelined processor core integrating the balanced CSelA ALU, pipelined multiplier, Gshare branch predictor, L1 I-Cache, L1 D-Cache, and non-blocking pipeline freeze logic.
\end{enumerate}

Listing \ref{lst:chisel_l1_cache} shows the core tag comparison, hit detection, and refill FSM in \texttt{L1Cache.scala}.

\begin{chiselcode}[caption={Chisel implementation of the parameterized \texttt{L1Cache} module showing tag checking, hit multiplexing, and refill FSM.},label={lst:chisel_l1_cache}]
class L1Cache(val totalBytes: Int = 4096, val ways: Int = 2,
              val lineBytes: Int = 32, val isDcache: Boolean = false) 
    extends Module {
  val io = IO(new Bundle {
    val req      = Input(Valid(new CacheCpuReq(32, 32)))
    val resp     = Output(Valid(new CacheCpuResp(32)))
    val stall    = Output(Bool())
    val memReq   = Output(Valid(new CacheMemReq(32, lineBytes * 8)))
    val memResp  = Input(Valid(new CacheMemResp(lineBytes * 8)))
  })

  // Synchronous Tag and Data Arrays
  val tagArrays  = Seq.fill(ways)(SyncReadMem(numSets, UInt(tagBits.W)))
  val dataArrays = Seq.fill(ways)(SyncReadMem(numSets, Vec(wordsPerLine, UInt(32.W))))
  val validBits  = RegInit(VecInit(Seq.fill(ways)(VecInit(Seq.fill(numSets)(false.B)))))
  val dirtyBits  = RegInit(VecInit(Seq.fill(ways)(VecInit(Seq.fill(numSets)(false.B)))))

  // Parallel Tag Comparison & Hit Detection
  val wayHits = Wire(Vec(ways, Bool()))
  for (w <- 0 until ways) {
    wayHits(w) := validBits(w)(reqIndex) && (tagArrays(w).read(reqIndex) === reqTag)
  }
  val isHit  = wayHits.asUInt.orR && io.req.valid && (state === sIdle)
  val hitWay = PriorityEncoder(wayHits)

  // 1-Hot Data Multiplexing
  val selectedData = Mux1H(wayHits, dataArrays.map(_.read(reqIndex)))
  io.resp.bits.readData := selectedData(reqWordIdx)
  io.resp.bits.hit      := isHit
  io.resp.valid         := isHit

  // Miss Handling & Refill FSM
  switch(state) {
    is(sIdle) {
      when(io.req.valid && !isHit) {
        io.stall := true.B
        state    := Mux(victimDirty, sWritebackReq, sRefillReq)
      }
    }
    is(sRefillReq) {
      io.stall := true.B; io.memReq.valid := true.B
      io.memReq.bits.addr := Cat(reqTag, reqIndex, 0.U(offsetBits.W))
      when(io.memReq.ready) { state := sRefillWait }
    }
    is(sRefillWait) {
      io.stall := true.B
      when(io.memResp.valid) {
        tagArrays(victimWay).write(reqIndex, reqTag)
        dataArrays(victimWay).write(reqIndex, refillWords)
        validBits(victimWay)(reqIndex) := true.B
        state := sIdle
      }
    }
  }
}
\end{chiselcode}

\subsubsection{Pipeline Freeze Logic on Cache Misses}
Integrating caches into a pipelined processor requires precise pipeline stall management:
\begin{itemize}
    \item \textbf{Instruction Cache Miss (\texttt{icacheStall})}: When an instruction fetch misses in the L1 I-Cache, the Fetch stage cannot supply an instruction. The pipeline freezes the Program Counter register (\texttt{pcReg}) and the IF/ID pipeline register, while injecting a bubble (\texttt{valid := false.B}) into the ID/EX register. All downstream instructions in Execute and Memory/Write-Back continue execution normally until completion.
    \item \textbf{Data Cache Miss (\texttt{dcacheStall})}: When a load or store instruction misses in the L1 D-Cache, the entire upstream pipeline must freeze. The PC, IF/ID, ID/EX, and EX/MEM registers are hold-latched, preserving their architectural state. Once the 100-cycle DDR-5 refill transaction completes, the cache updates its arrays, delivers the requested data word to the EX/MEM stage, and unfreezes the pipeline.
\end{itemize}

\subsubsection{Key Architectural Insights from the Instruction Cache Sweep}
\begin{enumerate}
    \item \textbf{The Power of Associativity at Small Capacities}: At $512\,\text{bytes}$, a direct-mapped cache suffers from severe \textit{conflict misses} between the active loops in CoreMark, yielding $19,277$ misses and an effective CPI of $3.298$. Doubling the associativity to $2$-way slashes misses to $6,325$ (a $\mathbf{67.2\%}$ reduction!), dropping CPI from $3.298$ to $1.817$. Expanding to $4$-way reduces misses further to $4,610$ ($\text{CPI} = 1.621$).
    \item \textbf{The Working Set Knee}: At $4\,\text{KB}$ with $2$-way associativity, CoreMark incurs only $287$ misses across $874,891$ instructions ($\text{MPKI} = 0.33$). The effective CPI is $1.127$---recovering $\mathbf{97.1\%}$ of ideal single-cycle memory throughput!
    \item \textbf{The Compulsory Miss Floor}: Beyond $16\,\text{KB}$, the miss count flattens at exactly $247$ misses ($\text{MPKI} = 0.28$, $\text{CPI} = 1.123$). These are \textit{compulsory (cold) misses} incurred when each 32-byte cache block is referenced for the very first time. No amount of additional cache capacity can eliminate these compulsory misses.
    \item \textbf{Dhrystone Behavior}: Dhrystone's core execution loop is extremely compact. At $1\,\text{KB}$, the entire benchmark code fits inside the cache, reaching the compulsory floor of $42$ misses ($\text{CPI} = 1.447$).
\end{enumerate}

\subsubsection{Key Architectural Insights from the Data Cache Sweep}
\begin{enumerate}
    \item \textbf{Thrashing in Direct-Mapped Data Caches}: In Dhrystone 2.1, a direct-mapped $512\,\text{B}$ or $1\,\text{KB}$ D-cache exhibits severe thrashing ($\text{CPI} = 3.957$ and $3.682$). \end{enumerate}


\subsection{Symmetric Harvard L1 Cache Evaluation: Sizing $I = D$ and Associativity Scaling}\label{riscvSymmetricCacheStudy}
\index{Harvard cache!symmetric sweep}\index{cache associativity!CPI impact}\index{combined cache stalls}

In Sections \ref{riscvIcacheStudy} and \ref{riscvDcacheStudy}, the Instruction Cache and Data Cache were characterized independently under an isolated profiling methodology (assuming the alternate cache was infinite). While isolation is essential for identifying the precise working set boundaries and miss mechanisms of instruction fetch versus memory operands, physical systems deploy both caches simultaneously against the memory subsystem. Because on-chip SRAM real estate is budgeted across the entire die, microarchitects commonly balance the Level-1 memory subsystem by provisioning symmetrically sized instruction and data caches:
\begin{equation}
C_{\text{I}} = C_{\text{D}}.
\end{equation}

When both caches operate concurrently in our 4-stage pipelined processor core (\texttt{RiscvCachedPipelined}), memory stalls from instruction fetch misses and data load/store misses serialize across the in-order pipeline. The cumulative execution cycles and final effective CPI are governed by:
\begin{equation}\label{eq:riscv_combined_cycles}
\text{Cycles}_{\text{total}} = \text{Cycles}_{\text{base}} + \text{Stalls}_{\text{I}} + \text{Stalls}_{\text{D}},
\end{equation}
\begin{equation}\label{eq:riscv_combined_cpi}
\text{CPI}_{\text{final}} = \frac{\text{Cycles}_{\text{total}}}{I} = \text{CPI}_{\text{base}} + \left(\frac{\text{MPKI}_{\text{I}} + \text{MPKI}_{\text{D}}}{1000}\right) \times P_{\text{mem}},
\end{equation}
where $P_{\text{mem}} = 100$ processor clock cycles ($65.0\,\text{ns}$ round-trip latency to DDR-5 DRAM at $1.538\,\text{GHz}$).

To establish the overall system trade-offs, we sweep symmetrical cache capacities from $512\,\text{B}$ to $32\,\text{KB}$ per cache (yielding an aggregate on-chip L1 SRAM capacity of $1\,\text{KB}$ to $64\,\text{KB}$) across $1$-way (direct-mapped), $2$-way, and $4$-way set-associativities. \subsubsection{Key Architectural Insights from the Combined Symmetric Study}
\begin{enumerate}
    \item \textbf{The Direct-Mapped Performance Cliff}: At $512\,\text{B}$ per cache, direct-mapped execution severely degrades processor performance. CoreMark CPI degrades to $\mathbf{3.822}$ ($3.5\times$ worse than ideal memory) because simultaneous I-cache conflict misses and D-cache collisions inject over $2.38\times 10^6$ stall cycles into the pipeline. On Dhrystone, conflict misses between the execution loop and stack/global structures push CPI to an extreme $\mathbf{4.810}$ ($4.2\times$ slowdown vs.\ ideal).
    \item \textbf{The Enormous ROI of 2-Way Associativity}: Moving from direct-mapped to $2$-way set-associativity at $1\,\text{KB} + 1\,\text{KB}$ delivers the largest single performance leap in the memory subsystem. On CoreMark, $2$-way associativity slashes total memory stalls from $546,400$ down to $109,200$ (an $\mathbf{80.0\%}$ reduction in stall bubbles!), collapsing final CPI from $\mathbf{1.719}$ to $\mathbf{1.219}$. On Dhrystone, $2$-way associativity plunges final CPI from $\mathbf{3.986}$ down to $\mathbf{1.584}$ (a $\mathbf{60.3\%}$ drop in total execution cycles!).
    \item \textbf{Diminishing Returns of 4-Way Associativity}: Expanding associativity beyond $2$-way to $4$-way yields marginal additional gains on these workloads. At $1\,\text{KB}$, $4$-way brings CoreMark CPI from $1.219$ to $1.216$ ($<0.3\%$ improvement), while requiring twice as many tag comparators, wider hit priority encoders, and more complex multiplexing logic.
    \item \textbf{The Optimal Design Point ($4\,\text{KB} + 4\,\text{KB}$, 2-Way)}: Provisioning a \textbf{4\,KB 2-way I-cache and 4\,KB 2-way D-cache} represents the clear architectural sweet spot. On CoreMark, this configuration achieves $\mathbf{\text{CPI} = 1.137}$---operating within $\mathbf{3.9\%}$ of theoretical ideal flat memory! On Dhrystone, it reaches the compulsory miss floor ($\text{CPI} = 1.570$).
    \item \textbf{The Compulsory Miss Floor ($16\,\text{KB} + 16\,\text{KB}$)}: At $16\,\text{KB}$ per cache ($32\,\text{KB}$ total L1 SRAM), all conflict and capacity misses are eliminated. Both benchmarks hit their irreducible compulsory miss floors ($\text{CPI} = 1.133$ for CoreMark, $\text{CPI} = 1.570$ for Dhrystone), where every remaining stall cycle is strictly due to initial cold refills from DDR-5 DRAM.
\end{enumerate}


\subsection{Multi-Level Cache Hierarchy: L1 and L2 Caching for the Embench-IoT Suite}\label{riscvL2Hierarchy}
\index{multi-level cache}\index{L2 cache}\index{Embench-IoT!cache evaluation}

While compact benchmarks like Dhrystone and CoreMark fit comfortably within small 4\,KB Level-1 caches, modern embedded applications frequently exhibit substantially larger code footprints and complex dynamic data structures. To demonstrate the necessity of a \textbf{multi-level cache hierarchy}, we evaluate the 19-workload \textbf{Embench-IoT} benchmark suite.

In Embench-IoT, workloads such as:
\begin{itemize}
    \item \texttt{picojpeg}: Baseline JPEG image decompressor (working footprint $>24\,\text{KB}$).
    \item \texttt{qrduino}: QR-code scanner and Reed-Solomon polynomial decoder ($>32\,\text{KB}$).
    \item \texttt{nsichneu}: Huge Petri net finite-state machine with thousands of state transitions ($>48\,\text{KB}$).
    \item \texttt{sglib-combined}: Broad collection of generic data structure algorithms (hash tables, red-black trees, quicksort, dynamic arrays) ($>18\,\text{KB}$).
\end{itemize}
routinely exceed the capacity of Level-1 caches.

\subsubsection{The L1-Only Thrashing Problem on Embench-IoT}
When a core with only 4\,KB L1 I-Cache and 4\,KB L1 D-Cache executes these workloads directly against 100-cycle DDR-5 main memory, the system experiences continuous capacity misses. As shown in Table \ref{tab:riscv_embench_l2}, the geometric mean CPI across the 19 Embench-IoT kernels explodes from an ideal $\text{CPI}_{\text{base}} = 1.12$ to an effective \textbf{$\text{CPI} = 4.82$}! On \texttt{nsichneu}, CPI reaches an intolerable \textbf{$8.12$}, rendering the processor essentially idle for $86\%$ of its execution cycles.

\subsubsection{Architectural Organization of the Level-2 Cache}
To mitigate this bottleneck, we introduce an on-chip \textbf{Unified Level-2 Cache (L2 Cache)}:
\begin{itemize}
    \item \textbf{Unified Organization}: Holds both instructions and data lines, dynamically adapting capacity to the instruction-heavy or data-heavy needs of the active application.
    \item \textbf{L2 Hit Latency ($P_{\text{L2}}$)}: $10$ processor clock cycles ($6.5\,\text{ns}$ in ASAP7 7\,nm FinFET).
    \item \textbf{L2 Associativity}: 8-way set-associative with pseudo-LRU replacement to eliminate conflict misses.
    \item \textbf{L2 Capacities Evaluated}: $64\,\text{KB}$, $128\,\text{KB}$, and $256\,\text{KB}$.
\end{itemize}

When an L1 cache misses, it queries the on-chip L2 cache. If the L2 cache hits, the 32-byte line is refilled into L1 with only a \textbf{10-cycle penalty} rather than a 100-cycle penalty! Only when the access misses in both L1 and L2 does the request propagate off-chip to DDR-5 DRAM ($100$ cycles). The effective memory stall equation becomes:
\begin{equation}
\text{Stall Cycles} = \text{Misses}_{\text{L1}} \times P_{\text{L2}} + \text{Misses}_{\text{L2}} \times P_{\text{mem}}.
\end{equation}

\section{Hardware Implementation of the Pipelined Processor}\label{riscvPipelined}
\index{RISC-V!pipelined implementation}\index{pipelining!4-stage hazard detection and stall}\index{hazard detection unit}\index{pipeline stall}

While the single-cycle processor developed in Section \ref{riscvArch} executes each instruction in a single clock cycle ($\text{CPI} = 1.0$), its operating clock frequency is fundamentally constrained by the cumulative propagation delay across all combinational subsystems within a single clock period:
\begin{equation}
T_{\text{clock, single}} \ge T_{\text{fetch}} + T_{\text{decode}} + T_{\text{ALU}} + T_{\text{dmem}} + T_{\text{wb}} + T_{\text{setup}}.
\end{equation}
In advanced physical processes, this monolithic combinational path limits clock frequencies. To improve computational throughput, this section develops a 4-stage pipelined implementation of the base \texttt{RV32I} processor, designated \texttt{RiscvPipelined} (and explores its extension to \texttt{RV32I\_Zmmul}). Reusing the core pipeline concepts of \textbf{PipeNyte}, the datapath divides execution into four sequential synchronous stages separated by explicit pipeline registers, incorporating an active \textbf{Hazard Detection Unit} that stalls instruction issue upon detecting data dependencies and flushes speculative instructions upon branch resolution. Per system design requirements, the core operates directly against unbuffered memory buses without cache hierarchies.

\subsection{Microarchitectural Organization of the 4-Stage Pipeline}
\index{pipelining!microarchitectural stages}\index{PipeNyte!4-stage architecture}

The 4-stage pipeline partitions the Fetch-Execute cycle into four balanced operational stages (Figure \ref{fig:riscv_4stage_pipeline}):
\begin{enumerate}
    \item \textbf{Stage 1: Instruction Fetch (IF)}:
    Maintains the architectural Program Counter register (\texttt{pcReg}). Drives the unbuffered instruction memory bus (\texttt{io.imem.addr}) and latches the incoming 32-bit instruction word into the \texttt{if\_id} pipeline register. Under normal sequential execution, the PC increments by 4 ($\text{PC} \leftarrow \text{PC} + 4$). When a control transfer (branch or jump) resolves taken in the EX stage, the PC updates to the target address, and the \texttt{if\_id} register is flushed. When a data hazard stall is signaled by the ID stage, the PC and \texttt{if\_id} register are frozen.
    
    \item \textbf{Stage 2: Instruction Decode and Operand Fetch (ID)}:
    Decodes the instruction latched in \texttt{if\_id} using \texttt{RiscvDecoder}, generates sign-extended immediates via \texttt{RiscvImmGen}, and accesses the architectural register file (\texttt{RiscvRegFile}). In this baseline implementation, \textbf{no forwarding} is implemented (operands are read directly from the register storage array). All data dependencies are resolved strictly by stalling until writeback commits.
    
    The ID stage houses the \textbf{Hazard Detection Unit}. If an instruction in ID reads a register targeted by an in-flight instruction currently in either the EX stage (distance-1 dependency) or the MEM/WB stage (distance-2 dependency), the hazard detection unit asserts a pipeline stall.
    
    \item \textbf{Stage 3: Execute (EX)}:
    Executes arithmetic, logical, and shift operations via the 32-bit executive ALU (\texttt{RiscvALU}), with optional support for the standard \texttt{Zmmul} multiplication extension. The EX stage evaluates branch conditions (\texttt{BEQ}, \texttt{BNE}, \texttt{BLT}, \texttt{BGE}, \texttt{BLTU}, \texttt{BGEU}) and calculates branch/jump target addresses:
    \begin{align}
    \text{Target}_{\text{branch/jal}} &= \text{PC}_{\text{EX}} + \text{imm}_{\text{EX}}, \\
    \text{Target}_{\text{jalr}} &= (\text{rs1}_{\text{EX}} + \text{imm}_{\text{EX}}) \ \& \ \sim 1.
    \end{align}
    Taken control transfers trigger a pipeline redirection, squashing the younger instructions in IF and ID.
    
    \item \textbf{Stage 4: Memory Access and Write-Back (MEM/WB)}:
    Combines data memory access and register file write-back into a unified terminal stage. For load and store instructions, the stage drives \texttt{io.dmem.addr}, \texttt{io.dmem.writeData}, \texttt{io.dmem.funct3}, and read/write strobes. Load data delivered by the memory bus is multiplexed with computational ALU results, upper immediates (\texttt{LUI}), and PC offsets (\texttt{AUIPC}, \texttt{JAL}, \texttt{JALR}) to generate the final write-back operand \texttt{wbData}, which commits synchronously to the register file at the end of the clock cycle.
\end{enumerate}

\subsection{Hazard Detection and Stall-on-Hazard Control Logic}
\index{data hazard!RAW stall}\index{hazard detection unit!boolean equations}

Data hazards arise when an instruction in the decode stage requires an operand that has not yet been committed to the architectural register file by an earlier instruction in the pipeline. Because the datapath does not implement full inter-stage execution bypass forwarding multiplexers, the processor handles data hazards by \textbf{stalling}: holding the dependent instruction in the decode stage until the producing instruction reaches the write-back stage.

\subsubsection{Source Operand Usage Identification}
An instruction in the ID stage only generates a hazard if it actively reads a source register:
\begin{align}
\text{readsRs1} &= (\text{isR} \lor \text{isI} \lor \text{isLoad} \lor \text{isStore} \lor \text{isBranch} \lor \text{isJalr}) \land (\text{rs1} \neq 0), \\
\text{readsRs2} &= (\text{isR} \lor \text{isStore} \lor \text{isBranch}) \land (\text{rs2} \neq 0).
\end{align}
Notice that \texttt{LUI}, \texttt{AUIPC}, and \texttt{JAL} do not read \texttt{rs1}, and instructions with immediate operands (such as \texttt{ADDI}, \texttt{LW}, and \texttt{JALR}) do not read \texttt{rs2}. Instructions specifying register $x0$ are excluded because $x0$ is hardwired to zero.

\subsubsection{Hazard Condition with Execute and Memory/Write-Back Stages}
In a pipeline without data forwarding, operands are read directly from the physical register storage array (\texttt{rs1Val = regFile.io.rs1\_data}). Because the register file updates synchronously on the rising clock edge at the end of the write-back cycle, a producing instruction's result is not available to the decode stage while that instruction is in the EX stage or the MEM/WB stage.

Therefore, the Hazard Detection Unit must detect RAW hazards across both stages:
\begin{align}
\text{exWillWrite}  &= \text{id\_ex.valid} \land \text{id\_ex.regWrite} \land (\text{id\_ex.rd} \neq 0), \\
\text{memWillWrite} &= \text{ex\_mem.valid} \land \text{ex\_mem.regWrite} \land (\text{ex\_mem.rd} \neq 0), \\
\text{rawHazardRs1} &= (\text{exWillWrite} \land \text{readsRs1} \land (\text{id\_ex.rd} == \text{d.rs1})) \lor \nonumber \\
                    &\quad (\text{memWillWrite} \land \text{readsRs1} \land (\text{ex\_mem.rd} == \text{d.rs1})), \\
\text{rawHazardRs2} &= (\text{exWillWrite} \land \text{readsRs2} \land (\text{id\_ex.rd} == \text{d.rs2})) \lor \nonumber \\
                    &\quad (\text{memWillWrite} \land \text{readsRs2} \land (\text{ex\_mem.rd} == \text{d.rs2})), \\
\text{stall}        &= \text{if\_id.valid} \land (\text{rawHazardRs1} \lor \text{rawHazardRs2}).
\end{align}

\subsubsection{Stall Action and Bubble Insertion}
When \texttt{stall} is asserted:
\begin{enumerate}
    \item \textbf{PC Register Freeze}: The program counter does not increment: $\text{pcReg} \leftarrow \text{pcReg}$.
    \item \textbf{IF/ID Register Freeze}: The instruction decode register retains its contents: $\text{if\_id} \leftarrow \text{if\_id}$.
    \item \textbf{Bubble Injection into ID/EX}: The execute stage is injected with a non-operational bubble by clearing its valid and control flags:
    \begin{equation}
    \text{id\_ex.valid} \leftarrow \text{false}, \quad \text{id\_ex.regWrite} \leftarrow \text{false}, \quad \text{id\_ex.memWrite} \leftarrow \text{false}.
    \end{equation}
\end{enumerate}

\subsubsection{Stall Latencies in the Absence of Forwarding}
In this baseline configuration without forwarding multiplexers:
\begin{itemize}
    \item \textbf{Distance-1 RAW Dependencies} (e.g., \texttt{ADD x1, x2, x3} immediately followed by \texttt{SUB x4, x1, x5}): 
    When \texttt{SUB} enters ID, \texttt{ADD} is in EX. \texttt{SUB} stalls for 1 cycle while \texttt{ADD} moves from EX to MEM/WB, and stalls for a second cycle while \texttt{ADD} is in MEM/WB. Thus, the stall penalty is exactly \textbf{2 clock cycles}.
    \item \textbf{Distance-2 RAW Dependencies} (e.g., \texttt{ADD x1, x2, x3}, an independent instruction, followed by \texttt{SUB x4, x1, x5}): 
    When \texttt{SUB} enters ID, \texttt{ADD} is in MEM/WB. \texttt{SUB} stalls for \textbf{1 clock cycle} while \texttt{ADD} completes writeback.
    \item \textbf{Distance-3 RAW Dependencies} (e.g., two independent instructions between producer and consumer): 
    When \texttt{SUB} enters ID, \texttt{ADD} has already retired and committed to the register storage. The stall penalty is \textbf{0 clock cycles}.
    \item \textbf{Load-Use Dependencies} (e.g., \texttt{LW x1, 0(x2)} followed by \texttt{ADD x3, x1, x4}):
    Because load data arrives in the MEM/WB stage, distance-1 load-use dependencies incur \textbf{2 stall cycles}.
\end{itemize}
While these interlocks simplify the datapath by eliminating bypass multiplexers and comparator networks, they impose significant CPI penalties on code with dense register dependencies, as quantified in subsequent benchmark sections.

\subsection{Control Hazards: Branch and Jump Resolution}
\index{control hazard!branch penalty}\index{pipeline flush!control transfer}

Control hazards occur when a conditional branch or unconditional jump instruction alters sequential program flow. In \texttt{RiscvPipelined}, branches and jumps are resolved during the \textbf{EX stage}:
\begin{itemize}
    \item The branch condition is evaluated using the ALU zero and comparison flags.
    \item The target address is computed combinationally from the registered PC and immediate.
\end{itemize}
When a branch condition evaluates true, or when an unconditional jump (\texttt{JAL}, \texttt{JALR}) executes:
\begin{align}
\text{exRedirect} &= (\text{branchTaken} \lor \text{jalTaken} \lor \text{jalrTaken}).
\end{align}
When \texttt{exRedirect} asserts:
\begin{enumerate}
    \item The Program Counter register updates to the redirected target address: $\text{pcReg} \leftarrow \text{exTargetPC}$.
    \item The \texttt{if\_id} register is flushed: $\text{if\_id.valid} \leftarrow \text{false}$.
    \item The \texttt{id\_ex} register is injected with a bubble: $\text{id\_ex.valid} \leftarrow \text{false}$.
\end{enumerate}
Because the branch resolves in Stage 3 (EX), the two younger instructions that entered the pipeline speculatively (the instruction currently in ID and the instruction currently being fetched in IF) are flushed. Consequently, a taken control transfer incurs a \textbf{2-cycle branch penalty}. If a branch evaluates not-taken, execution falls through with a \textbf{0-cycle penalty}.

Control redirection unconditionally overrides hazard stalls: if an instruction in ID was stalled awaiting an operand, but the instruction in EX branches or jumps, the stalled instruction is flushed and the stall condition is dismissed.


\section{Performance Evaluation and ASIC Physical Design of the RV32I Pipeline}\label{riscvPerformance}
\index{performance evaluation!pure RV32I}\index{ASIC synthesis!ASAP7 7nm}\index{ASAP7!7nm predictive PDK standard cell synthesis}

To establish a rigorous baseline for pipelined processor design, the unpipelined (\texttt{RiscvFetchExecute}) and 4-stage pipelined (\texttt{RiscvPipelined}) processors were first configured in the pure, baseline \texttt{RV32I} architecture (with hardware multiplication disabled, \texttt{enableZmmul = false}) and without data forwarding. Both designs were subjected to three evaluation workflows:
\begin{enumerate}
    \item Architectural conformance verification against the official RISC-V \texttt{RV32I} test suite.
    \item Cycle-accurate execution of a real Digital Signal Processing (DSP) benchmark application.
    \item Full standard-cell ASIC synthesis targeting the advanced \textbf{ASAP7 7\,nm FinFET Predictive PDK} (\texttt{asap7sc7p5t\_28}).
\end{enumerate}

\begin{enumerate}
    \item A \textbf{16-point 4-tap Finite Impulse Response (FIR) filter}:
    \begin{equation}
    y[i] = \sum_{k=0}^{3} x[i-k] \cdot h[k], \quad i \in [3, 15].

\subsubsection{Architectural Analysis of the RV32I Pipelined Speedup}

The synthesis and performance results of the pure \texttt{RV32I} baseline in ASAP7 7\,nm FinFET illustrate fundamental computer architecture principles:
\begin{enumerate}
    \item \textbf{The 4-Step Pipeline Delay Model}:
    In a processor implementation, instruction execution consists of four essential physical operations:
    \begin{itemize}
        \item \textbf{SRAM Fetch ($T_{\text{fetch}}$)}: The program counter updates, address is driven to instruction SRAM, and the 32-bit instruction word is retrieved. Modeled with a small standard 7\,nm FinFET SRAM macro ($T_{\text{sram}} = 0.500\,\text{ns}$), plus register clock-to-Q and setup, $T_{\text{fetch}} = \mathbf{0.550\,\text{ns}}$ (550\,ps).
        \item \textbf{Decode and Register Read ($T_{\text{decode}}$)}: The instruction decoder decodes opcodes and generates immediates ($0.209\,\text{ns}$), while the dual-read register file retrieves source register values $rs1$ and $rs2$ ($0.283\,\text{ns}$). With control steering, $T_{\text{decode}} = \mathbf{0.540\,\text{ns}}$ (540\,ps).
        \item \textbf{Execute ($T_{\text{execute}}$)}: The 32-bit ALU performs arithmetic, shifting, or comparison ($1.046\,\text{ns}$), followed by branch condition evaluation ($0.120\,\text{ns}$) and pipeline register setup, yielding $T_{\text{execute}} = \mathbf{1.363\,\text{ns}}$ (1,363\,ps). Crucially, the baseline ALU relies on a standard ripple-carry adder (RCA), which exhibits an isolated critical path propagation delay of $1.045\,\text{ns}$ in ASAP7 7\,nm FinFET. Notice that \textbf{the ripple-carry adder alone has approximately $2\times$ the delay of any other pipeline stage in the entire processor} ($1.045\,\text{ns}$ vs.\ $0.550\,\text{ns}$ for Fetch, $0.540\,\text{ns}$ for Decode, and $0.600\,\text{ns}$ for Write-Back). This slow adder represents the primary structural bottleneck unbalancing the pipeline.
        \item \textbf{SRAM Data Memory and Write-Back ($T_{\text{sram\_wb}}$)}: For load instructions, the memory address is presented to the data SRAM ($T_{\text{sram}} = 0.500\,\text{ns}$), the retrieved data is multiplexed with ALU and jump results ($0.080\,\text{ns}$), and routed to the register file write port ($0.020\,\text{ns}$ setup), totaling $T_{\text{sram\_wb}} = \mathbf{0.600\,\text{ns}}$ (600\,ps).
    \end{itemize}
    
    \item \textbf{FE Core Sum vs.\ Pipelined Core Max}:
    In the \textbf{single-cycle Fetch-Execute (FE) processor}, every instruction must traverse all four steps in series within a single clock cycle:
    \begin{equation}
    T_{\text{clk, FE}} = T_{\text{fetch}} + T_{\text{decode}} + T_{\text{execute}} + T_{\text{sram\_wb}} = 0.550 + 0.540 + 1.363 + 0.600 = \mathbf{3.053\,\text{ns}} \quad (327.5\,\text{MHz}).
    \end{equation}
    In the \textbf{4-stage pipelined processor}, synchronous pipeline registers decouple the four steps into independent pipeline stages. The clock period is constrained only by the single longest pipeline step:
    \begin{equation}
    T_{\text{clk, pipe}} = \max\left(T_{\text{fetch}}, T_{\text{decode}}, T_{\text{execute}}, T_{\text{sram\_wb}}\right) = \max(0.550, 0.540, 1.363, 0.600) = \mathbf{1.363\,\text{ns}} \quad (733.7\,\text{MHz}).
    \end{equation}
    The clock period delta between the FE core and the pipelined core is therefore:
    \begin{equation}
    \Delta T = T_{\text{clk, FE}} - T_{\text{clk, pipe}} = 3.053\,\text{ns} - 1.363\,\text{ns} = \mathbf{1.690\,\text{ns}}.
    \end{equation}
    This reduction of $1.690\,\text{ns}$ represents the sum of the other three stages that are now overlapped across clock cycles, delivering a \textbf{+124.0\% system frequency boost} ($2.240\times$ frequency multiplier).
    
    \item \textbf{The Impact of Omitting Data Forwarding}:
    Despite the $2.240\times$ system clock frequency advantage, the 4-stage pipeline's CPI increases from 1.00 to 1.93 (+93.1\% execution cycles) due to frequent 2-cycle and 1-cycle stalls on RAW hazards in the software multiply loop.
    \begin{equation}
    \text{Speedup} = \frac{T_{\text{exec, FE}}}{T_{\text{exec, pipe}}} = \frac{6,511 \times 3.053\,\text{ns}}{12,575 \times 1.363\,\text{ns}} = \frac{19,878\,\text{ns}}{17,140\,\text{ns}} = \mathbf{1.16\times}.
    \end{equation}
    Because hazard stalls consume more than half of the $2.24\times$ frequency advantage, the pipelined processor runs only $16\%$ faster ($1.16\times$) on this workload. This benchmark demonstrates that while pipelining successfully overlaps SRAM latency and decouples stage delays, data forwarding is essential to eliminate stall bubbles and achieve full pipeline potential.
\end{enumerate}


\section{Balancing the Pipeline: Synthesis and Selection of High-Performance Adders}\label{riscvAdderBalancing}
\index{pipeline balancing!adder optimization}\index{adders!ASAP7 7nm synthesis}\index{carry select adder!pipeline integration}\index{parallel prefix adders}

As established in Section \ref{riscvPerformance}, the critical path of the 4-stage \texttt{RV32I} pipeline is overwhelmingly dominated by the Execute (EX) stage ($T_{\text{execute}} = 1.363\,\text{ns}$). More strikingly, the unoptimized 32-bit ripple-carry adder (RCA) embedded inside the baseline ALU accounts for $1.045\,\text{ns}$ of that latency—nearly \textbf{$2\times$ the delay of any other stage} in the entire processor ($T_{\text{fetch}} = 0.550\,\text{ns}$, $T_{\text{decode}} = 0.540\,\text{ns}$, and $T_{\text{sram\_wb}} = 0.600\,\text{ns}$). Because a synchronous pipeline can run no faster than its slowest stage, the slow ripple-carry adder acts as an anchor holding the clock frequency to $733.7\,\text{MHz}$, even though the remaining three-quarters of the machine are physically capable of clocking at $1.67\,\text{GHz}$ ($1 / 0.600\,\text{ns}$).

To eliminate this structural bottleneck, we turn to the high-performance adder topologies analyzed in Chapter \ref{chap:perf_opt_logic} (Section \ref{sec:high_performance_adders}). In this section, we synthesize the major 32-bit adder architectures to physical gate-level netlists using the identical \textbf{ASAP7 7\,nm FinFET Predictive PDK} library, evaluate their delay-area trade-offs, select the optimal design to balance the pipeline, and integrate it into the Chisel execution unit.

\subsection{Physical ASIC Synthesis of Chapter \ref{chap:perf_opt_logic} Adders on ASAP7 7\,nm FinFET}

Five 32-bit adder topologies described in Chapter \ref{chap:perf_opt_logic} were implemented in parameterized Chisel RTL, verified with complete functional test suites covering corner cases, maximum carry propagations, and random vectors, and generated into SystemVerilog netlists:
\begin{enumerate}
    \item \textbf{Ripple-Carry Adder (RCA)}: Baseline $O(N)$ linear carry-propagation chain composed of 32 cascaded full adders (Section \ref{lect1}).
    \item \textbf{Carry Lookahead Adder (CLA)}: Hierarchical two-level block lookahead adder grouping bits into 4-bit lookahead blocks with lookahead carry generators (Section \ref{sec:high_performance_adders}).
    \item \textbf{Brent-Kung Parallel Prefix Adder (BKA)}: A 9-level parallel prefix tree designed to minimize total cell count and routing density with a maximum fan-out of 2 \cite{brent1982regular}.
    \item \textbf{Kogge-Stone Parallel Prefix Adder (KSA)}: A 5-level ($\lceil \log_2 32 \rceil$) parallel prefix tree designed for minimum logic depth with uniform fan-out of 2 \cite{kogge1973parallel} (Section \ref{sec:kogge-stone-adder}).
    \item \textbf{Carry Select Adder (CSA)}: Speculative block adder partitioning 32 bits into 4-bit blocks where dual ripple chains compute speculative sums for $C_{\text{in}} = 0$ and $C_{\text{in}} = 1$ in parallel, multiplexed by incoming block carries (Section \ref{sec:high_performance_adders}).
\end{enumerate}

\subsection{Architectural Analysis and Selecting the Optimal Adder}

The empirical synthesis results reveal several critical insights into deep-submicron arithmetic design:
\begin{enumerate}
    \item \textbf{The Ripple-Carry Bottleneck Confirmed}: The ripple-carry adder achieves a propagation delay of $1,045.43\,\text{ps}$ ($1.045\,\text{ns}$). The critical path consists of 31 cascaded majority and inverter stages (\texttt{MAJx2\_ASAP7\_75t\_R}), confirming that the $O(N)$ carry chain is directly responsible for the $1.363\,\text{ns}$ Execute stage bottleneck in the core.
    \item \textbf{Hierarchical CLA Limitations}: While the 4-bit block CLA reduces delay to $987.99\,\text{ps}$, it offers only a modest $6\%$ speedup. In static CMOS standard cells, the complex multi-input AND-OR trees required for lookahead logic suffer from fan-in stacking and internal node capacitance, diluting the theoretical logarithmic advantage.
    \item \textbf{Parallel Prefix Trade-offs}: The parallel prefix trees yield substantial latency reductions: Brent-Kung reaches $836.25\,\text{ps}$ ($1.25\times$ faster) while maintaining a compact $14.83\,\mu\text{m}^2$ footprint. Kogge-Stone further cuts latency to $712.57\,\text{ps}$ ($1.47\times$ faster, $1.40\,\text{GHz}$) by maintaining minimum logic depth ($5$ prefix stages), albeit with higher cell count (190 cells) and dense inter-stage routing.
    \item \textbf{Superiority of Carry Select in 32-bit Standard Cells}: The \textbf{Carry Select Adder (CSA)} achieves the absolute lowest propagation delay of all architectures evaluated: \textbf{519.83\,ps (0.520\,ns)}, delivering a \textbf{$2.01\times$ speedup} over the ripple-carry baseline and reaching a standalone frequency of \textbf{1.92\,GHz}.
    
    In 32-bit standard cells, partitioning the adder into 4-bit blocks allows the speculative carry chains to settle in parallel in under $120\,\text{ps}$. The arriving carries then ripple through a linear chain of transmission-gate and static multiplexers (\texttt{NAND2}, \texttt{MAJI}), each introducing an average gate delay of only $\approx 35\text{--}40\,\text{ps}$. Because 2:1 multiplexers are among the fastest and most highly optimized primitives in modern FinFET standard-cell libraries, the carry-select topology decisively outperforms tree structures at the 32-bit operand width.
\end{enumerate}

Consequently, we select the \textbf{Carry Select Adder} as the optimal high-speed replacement for the slow ripple-carry adder in our RISC-V execution unit.

\subsection{Integrating the High-Performance Adder in Chisel}
\index{Chisel!adder instantiation}

To integrate the Carry Select Adder into the execution unit, the ALU's arithmetic subtraction and addition are routed through the dedicated adder module. In two's complement arithmetic, subtraction $A - B$ is computed as $A + \sim B + 1$, which is directly mapped to the adder's primary inputs and carry-in. 

Listing \ref{lst:chisel_csa_call} illustrates the revised execution stage design, showing only the high-performance adder invocation within the Chisel ALU.

\begin{chiselcode}[caption={Calling the high-performance Carry Select Adder within the revised RISC-V ALU.},label={lst:chisel_csa_call}]
// Instantiating the 32-bit Carry-Select Adder within the revised ALU
val isSub = io.aluOp === AluOp.SUB
val adder = Module(new CarrySelectAdder(width = 32))
adder.io.a       := io.opA
adder.io.b       := Mux(isSub, ~io.opB, io.opB)
adder.io.carryIn := isSub
val addSubResult = adder.io.sum
\end{chiselcode}

By encapsulating the addition and subtraction inside the Carry Select Adder, the ALU avoids generating CIRCT's default carry chains, replacing them with the optimized speculative block architecture.

\subsection{Impact on Pipeline Balancing and Clock Frequency}

\section{Microarchitectural Case Study: Hardware Multiplication (Zmmul) and the Pipeline Balancing Dilemma}\label{riscvZmmulCaseStudy}
\index{Zmmul extension!microarchitectural case study}\index{pipeline balancing!multiplier bottleneck}\index{Amdahl's law!clock period unbalancing}

Having established the baseline performance of the 4-stage \texttt{RV32I} pipeline, we now examine what happens when hardware multiplication is added. In scientific computing, machine learning, and digital signal processing, multiplication is ubiquitous. Implementing multiplication in software via shift-and-add requires roughly 35 instructions per multiply, bloating code size and consuming significant execution cycles. 

To accelerate multiplication, the RISC-V standard defines the \texttt{Zmmul} extension, introducing four 32-bit multiplication instructions: \texttt{MUL} (lower 32 bits), \texttt{MULH} (upper 32 bits, signed $\times$ signed), \texttt{MULHSU} (upper 32 bits, signed $\times$ unsigned), and \texttt{MULHU} (upper 32 bits, unsigned $\times$ unsigned).

A naive microarchitectural approach is to simply integrate a $32 \times 32$ combinational multiplier directly into the execution stage ALU (\texttt{RiscvALU}). However, this case study reveals how an unpipelined complex execution unit catastrophically destroys pipeline stage balancing.

\end{enumerate}

\subsection{Benchmark Performance: Algorithmic Gain vs.\ Pipeline Inefficiency}
\index{benchmark!hardware multiply}\index{algorithmic speedup vs microarchitectural speedup}

To evaluate the algorithmic benefit of hardware multiplication, the DSP benchmark application was recompiled targeting \texttt{rv32i\_zmmul} with optimization flag \texttt{-O1}:
\begin{itemize}
    \item \textbf{Instruction Count Reduction}:
    Replacing software shift-and-add subroutines with single hardware \texttt{MUL} instructions slashes dynamic instruction count from 6,511 to 804 instructions---an \textbf{8.1$\times$ reduction in instructions executed}!
    
    \item \textbf{Pipelined Cycle Performance}:
    On the 4-stage pipeline, the 804 instructions execute in 1,308 clock cycles ($\text{CPI} = 1.63$). Hazard stalls and branch flushes account for 504 cycles.
    
    \item \textbf{Execution Time Comparison}:
    Under the 4-step pipeline delay model:
    \begin{itemize}
        \item Single-Cycle \texttt{RV32I\_Zmmul}: $804 \times 4.152\,\text{ns} = 3,338\,\text{ns}$ ($3.34\,\mu\text{s}$).
        \item 4-Stage Pipelined \texttt{RV32I\_Zmmul}: $1,308 \times 2.462\,\text{ns} = 3,220\,\text{ns}$ ($3.22\,\mu\text{s}$).
        \item Pipelined Speedup: $3,338\,\text{ns} / 3,220\,\text{ns} = \mathbf{1.04\times}$.
    \end{itemize}
\end{itemize}

Notice the critical distinction:
\begin{itemize}
    \item In pure \texttt{RV32I}, the pipeline stages are relatively well balanced, enabling the system speedup to reach \textbf{1.16$\times$} despite lacking data forwarding.
    \item In \texttt{RV32I\_Zmmul}, the unpipelined multiplier unbalances the pipeline, reducing pipelined speedup to \textbf{1.04$\times$}.
    \item Although the application runs $5.32\times$ faster in absolute wall-clock time with hardware multiplication ($3,220\,\text{ns}$ vs.\ $17,140\,\text{ns}$), this speedup is almost entirely \textit{algorithmic} (8.1$\times$ fewer instructions). The \textit{microarchitectural efficiency} of pipelining was severely compromised by the unpipelined multiplier bottleneck.
\end{itemize}

Although automated standard-cell synthesis incurs logic overhead for dual-rail $(x^+, x^-)$ sign-magnitude encoding and initial RB partial product mapping, the RBM possesses unique architectural strengths:
    \begin{itemize}
        \item \textbf{Strictly Constant-Time Carry-Free Addition}: Each Redundant Binary Adder (RBA) cell adds two digits in $O(1)$ constant time by inspecting the lower adjacent position condition ($p_{i-1} = (x_{i-1} + y_{i-1} > 0)$), completely preventing carry propagation across bit positions.
        \item \textbf{Perfect Binary Reduction Regularity}: The RBM arranges reduction as a strictly balanced binary tree ($2 \to 1$ at every node) of depth $\lceil \log_2 N \rceil = 5$ levels.
        \item \textbf{DSP Datapath Superiority}: In custom and semi-custom digital signal processor (DSP) design (such as the high-performance multithreaded Sandblaster DSP architecture), wire layout regularity is paramount. Unlike Wallace trees with unpredictable wiring lengths, the RBM's binary tree reduction maps directly onto modular, uniform bit-slices with pitch-matched cell abutment. This eliminates wiring hot-spots and crosstalk, making RBM architectures highly attractive for multi-GHz DSP engines where multiply-accumulate (MAC) throughput dictates overall performance.
    \end{itemize}
\end{enumerate}

(In a high-throughput DSP coprocessor where custom pitch-matched layout is available, the Redundant Binary Multiplier would be selected for its layout regularity and modularity).

\subsection{Architectural Solutions: Restoring Pipeline Balance}
\index{pipeline balancing!architectural solutions}\index{multi-cycle multiplier}\index{pipelined multiplier}

The synthesis evaluation in Table \ref{tab:asap7_multipliers_comparison} reveals a fundamental physical reality: **no single-cycle 32-bit multiplier can achieve a propagation delay under $\approx 1.96\text{--}2.25\,\text{ns}$ in standard cells**. 

Recall from Section \ref{riscvAdderBalancing} that integrating the Carry Select Adder balanced all four pipeline stages to $\approx 0.54\text{--}0.60\,\text{ns}$ ($1.67\,\text{GHz}$):
\begin{equation}
T_{\text{fetch}} = 0.550\,\text{ns}, \quad T_{\text{decode}} = 0.540\,\text{ns}, \quad T_{\text{execute (CSA)}} = 0.600\,\text{ns}, \quad T_{\text{sram\_wb}} = 0.600\,\text{ns}.
\end{equation}
If any single-cycle combinational multiplier ($t_{\text{mul}} \approx 1.97\text{--}2.16\,\text{ns}$) is placed directly into the EX stage, the EX stage delay expands to $t_{\text{mul}} + t_{\text{mux}} + t_{\text{setup}} \approx 2.46\,\text{ns}$, causing the operating frequency to collapse from $1.67\,\text{GHz}$ down to $406.2\,\text{MHz}$ (a massive $75.7\%$ frequency penalty for all instructions!).

This case study illustrates \textbf{Amdahl's Law applied to pipeline cycle time}:
\begin{equation}
T_{\text{clk}} = \max\left(T_{\text{IF}}, T_{\text{ID}}, T_{\text{EX}}, T_{\text{MEM}}\right) + T_{\text{overhead}}.
\end{equation}
When one stage is $4\times$ slower than the rest, improving or subdividing the other stages yields diminishing returns.

How do production computer architects resolve this dilemma to retain the high operating frequency of pure \texttt{RV32I} while providing hardware multiplication?
\begin{enumerate}
    \item \textbf{Multi-Cycle Execution Unit}:
    Rather than forcing the entire processor to run at a sluggish $2.462\,\text{ns}$ clock period to accommodate the multiplier, the execution unit operates the multiplier as a multi-cycle iterative unit taking 3 to 4 cycles. 
    
    When a non-multiplying ALU instruction enters EX, it completes in a single fast clock cycle ($0.600\,\text{ns}$, $1.67\,\text{GHz}$). When a \texttt{MUL} instruction enters EX, the Hazard Detection Unit asserts a temporary pipeline stall for 3 cycles while the multiplier computes. Because multiplications typically represent only 5--10\% of instructions in general-purpose workloads, running 90\% of instructions at 1.67\,GHz with occasional 3-cycle stalls yields vastly superior overall execution time compared to throttling the entire core at 406.2\,MHz.
    
    \item \textbf{Internally Pipelined Multiplier}:
    In high-performance processors, the multiplier logic array itself is partitioned into multiple synchronous pipeline stages separated by internal pipeline registers:
    \begin{itemize}
        \item \textbf{Stage 1}: Radix-4 Booth recoding and partial product generation ($\approx 0.50\,\text{ns}$).
        \item \textbf{Stage 2}: Upper carry-save or redundant binary reduction levels ($\approx 0.52\,\text{ns}$).
        \item \textbf{Stage 3}: Lower reduction levels down to 2 vectors ($\approx 0.52\,\text{ns}$).
        \item \textbf{Stage 4}: Final Carry-Propagate Addition using a Carry Select Adder ($\approx 0.52\,\text{ns}$).
    \end{itemize}
    By inserting pipeline registers within the multiplier, each sub-stage delay is bounded to $\le 0.55\,\text{ns}$, perfectly matching the $0.600\,\text{ns}$ clock period of the balanced core! The processor operates at the full **1.67 GHz** clock frequency ($2.27\times$ faster than the unoptimized baseline), sustaining a multiplier throughput of 1 instruction per cycle with a latency of 4 cycles.
\end{enumerate}

\subsection{Why Ideal Pipeline Speedup is Inaccessible in Practice}
\index{pipeline speedup!theoretical vs actual}\index{pipeline balancing!physical impediments}\index{stage delay quantization}\index{clock overhead}

A common observation among novice computer architects is that a pipelined processor runs ``only a tiny bit faster'' than a single-cycle core (e.g., $1.16\times\text{--}1.27\times$), far below the ideal theoretical $N$-fold speedup. In introductory textbooks, pipelining an $N$-stage processor is frequently described as achieving a theoretical speedup of:
\begin{equation}
S_{\text{ideal}} = N.
\end{equation}
For our 4-stage pipeline ($N = 4$), naive theory predicts a $4.0\times$ speedup. Yet, as demonstrated in Table \ref{tab:riscv_all_benchmarks}, the measured speedup in physical 7\,nm silicon is between $1.04\times$ and $1.27\times$.

Why is ideal pipeline speedup impossible to achieve in physical silicon? The actual speedup of a pipelined processor over a single-cycle implementation is governed by the classic processor performance equation:
\begin{equation}
\text{Speedup} = \frac{\text{Time}_{\text{single}}}{\text{Time}_{\text{pipe}}} = \frac{I \times \text{CPI}_{\text{single}} \times T_{\text{clk, single}}}{I \times \text{CPI}_{\text{pipe}} \times T_{\text{clk, pipe}}} = \left(\frac{\text{CPI}_{\text{single}}}{\text{CPI}_{\text{pipe}}}\right) \times \left(\frac{T_{\text{clk, single}}}{T_{\text{clk, pipe}}}\right).
\end{equation}
For an $N$-stage pipeline, achieving $S = N$ requires two simultaneous conditions:
\begin{enumerate}
    \item \textbf{Perfect CPI Invariance}: $\text{CPI}_{\text{pipe}} = \text{CPI}_{\text{single}} = 1.00$.
    \item \textbf{Perfect Frequency Scaling}: $T_{\text{clk, pipe}} = \frac{1}{N} T_{\text{clk, single}}$.
\end{enumerate}
In physical hardware, three fundamental physical barriers guarantee that neither condition can ever be met:

\subsubsection{1. Stage Delay Quantization and Imbalance}
\index{pipeline balancing!delay quantization}\index{Amdahl's Law!for clock periods}
Combinational logic cannot be sliced arbitrarily like a fluid. Logic circuits are constructed from discrete boolean primitives: multiplexers, adders, decoders, shifters, and comparator trees. In our pure \texttt{RV32I} core:
\begin{itemize}
    \item The four physical pipeline steps have differing atomic delays in ASAP7 7\,nm FinFET:
    \begin{itemize}
        \item Step 1: SRAM Fetch ($T_{\text{fetch}} = 0.550\,\text{ns}$).
        \item Step 2: Decode and Register Read ($T_{\text{decode}} = 0.540\,\text{ns}$).
        \item Step 3: Execute ($T_{\text{execute}} = 1.363\,\text{ns}$, dominated by the 32-bit ALU, adder, barrel shifter, and branch comparator).
        \item Step 4: SRAM Data Memory and Write-Back ($T_{\text{sram\_wb}} = 0.600\,\text{ns}$).
    \end{itemize}
    \item In the single-cycle Fetch-Execute (FE) core, the clock period must encompass the sum of all four steps:
    \begin{equation}
    T_{\text{clk, FE}} = 0.550 + 0.540 + 1.363 + 0.600 = \mathbf{3.053\,\text{ns}} \quad (327.5\,\text{MHz}).
    \end{equation}
    \item In the 4-stage pipelined core, synchronous registers decouple the four steps into independent pipeline stages, so the clock period is constrained by the maximum step delay:
    \begin{equation}
    T_{\text{clk, pipe}} = \max(0.550, 0.540, 1.363, 0.600) = \mathbf{1.363\,\text{ns}} \quad (733.7\,\text{MHz}).
    \end{equation}
    \item The frequency improvement achieved by pipelining is:
    \begin{equation}
    \frac{T_{\text{clk, FE}}}{T_{\text{clk, pipe}}} = \frac{3.053\,\text{ns}}{1.363\,\text{ns}} = \mathbf{2.240\times} \quad (\text{a } +124.0\% \text{ frequency gain}).
    \end{equation}
\end{itemize}
While $2.240\times$ is a substantial frequency improvement, it is significantly below the theoretical $4.0\times$ limit!

As noted by experienced computer designers, \textbf{it is exceedingly difficult to perfectly balance pipeline stages in practice}. The atomic nature of major arithmetic blocks (such as the 32-bit ALU in the EX stage) creates an irreducible bottleneck ($1.363\,\text{ns}$), whereas the fetch, decode, and writeback steps each require only $\approx 0.54\text{--}0.60\,\text{ns}$. In particular, the unoptimized baseline ALU synthesizes with an isolated 32-bit ripple-carry adder requiring $1.045\,\text{ns}$. It is clear that \textbf{the ripple-carry adder alone has approximately $2\times$ the delay of any other complete pipeline stage} ($0.54\text{--}0.60\,\text{ns}$), serving as the primary anchor that prevents higher clock frequencies. Stage delay imbalance alone annihilates $(4.0 - 2.24) / 4.0 = \mathbf{44.0\%}$ of the theoretical 4-fold speedup before a single instruction has executed!

\subsubsection{2. Sequential Register Overhead}
\index{pipeline register overhead}\index{setup time}\index{clock-to-Q delay}
Every pipeline stage boundary requires sequential state storage (D flip-flops in standard cells):
\begin{equation}
T_{\text{stage}} = T_{\text{comb}} + t_{\text{setup}} + t_{\text{cq}} + t_{\text{skew}}.
\end{equation}
In the ASAP7 7\,nm FinFET standard cell library:
\begin{itemize}
    \item Flip-flop setup time: $t_{\text{setup}} \approx 15\,\text{ps}$.
    \item Clock-to-Q propagation delay: $t_{\text{cq}} \approx 25\,\text{ps}$.
    \item Clock distribution skew and jitter margin: $t_{\text{skew}} \approx 15\,\text{ps}$.
\end{itemize}
This introduces an unshrinkable sequential overhead of $T_{\text{reg\_overhead}} \approx 55\,\text{ps}$ at \textit{every stage boundary}. Over a 4-stage pipeline, over $200\,\text{ps}$ of cumulative delay is consumed solely by registers. This overhead represents a dead penalty that performs zero computational work, directly diminishing the achievable clock frequency.

\subsubsection{3. Hazard-Induced CPI Expansion (in the Absence of Forwarding)}
\index{hazard penalties}\index{CPI expansion}\index{forwarding!necessity}
In a single-cycle processor, data dependencies and branch decisions are resolved combinationally within the same clock period in which the instruction executes:
\begin{equation}
\text{CPI}_{\text{single}} \equiv 1.00.
\end{equation}
In a pipelined processor without forwarding, instructions execute concurrently across time. When an instruction in the Decode stage depends on a value being computed in Execute or Memory/Write-Back, the Hazard Detection Unit must inject 2 stall cycles (for distance-1 dependencies) or 1 stall cycle (for distance-2 dependencies). Furthermore, when a branch or jump condition is evaluated in the Execute stage, the two instructions fetched speculatively into IF and ID must be discarded, incurring a 2-cycle branch penalty.

Across real embedded workloads, this hazard overhead severely expands the effective CPI:
\begin{itemize}
    \item \textbf{Dhrystone 2.1}: $\text{CPI}_{\text{pipe}} = 1.76$ (+75.8\% cycle penalty).
    \item \textbf{CoreMark 1.0}: $\text{CPI}_{\text{pipe}} = 1.88$ (+87.8\% cycle penalty).
    \item \textbf{DSP Kernel (Soft Mul)}: $\text{CPI}_{\text{pipe}} = 1.93$ (+93.1\% cycle penalty).
\end{itemize}

Now observe what happens when we calculate the net application speedup:
\begin{equation}
\text{Speedup} = \left(\frac{1}{\text{CPI}_{\text{pipe}}}\right) \times \left(\frac{T_{\text{clk, FE}}}{T_{\text{clk, pipe}}}\right)
\end{equation}
\begin{itemize}
    \item \textbf{CoreMark 1.0}:
    \begin{equation}
    \text{Speedup}_{\text{CoreMark}} = \left(\frac{1}{1.878}\right) \times 2.240 = 0.532 \times 2.240 = \mathbf{1.19\times} \quad (+19.3\%).
    \end{equation}
    \item \textbf{Dhrystone 2.1}:
    \begin{equation}
    \text{Speedup}_{\text{Dhrystone}} = \left(\frac{1}{1.758}\right) \times 2.240 = 0.569 \times 2.240 = \mathbf{1.27\times} \quad (+27.4\%).
    \end{equation}
    \item \textbf{DSP Kernel (Soft Mul)}:
    \begin{equation}
    \text{Speedup}_{\text{DSP}} = \left(\frac{1}{1.931}\right) \times 2.240 = 0.518 \times 2.240 = \mathbf{1.16\times} \quad (+16.0\%).
    \end{equation}
\end{itemize}

This explains precisely why the pipelined processor runs ``only a tiny bit faster'' ($1.16\times\text{--}1.27\times$):
The $2.24\times$ frequency multiplier earned by overlapping the four pipeline steps is almost entirely eaten away by the $1.76\times\text{--}1.93\times$ CPI expansion caused by RAW hazard stalls and branch flushes!

This profound result provides the pedagogical foundation for the subsequent study of \textbf{data forwarding}: by adding bypass paths from EX and MEM/WB back to the ALU, the CPI penalty can be dramatically suppressed (driving CPI back toward 1.00), unlocking the full $2.24\times$ speedup made possible by pipelining.

\subsubsection{Why SPEC CPU Cannot Run on Bare-Metal Microcontrollers}
Students frequently inquire why standard desktop/server benchmarks such as \textbf{SPEC CPU} (SPEC CPU2006 or SPEC CPU2017) are not used to evaluate microcontroller cores like the baseline \texttt{RV32I} core developed in this chapter. 

SPEC CPU is designed exclusively for \textbf{application-class processors} (e.g., 64-bit x86-64, ARM Cortex-A, or RISC-V RV64GC) and requires an extensive underlying system software infrastructure:
\begin{enumerate}
    \item \textbf{Memory Management Unit (MMU)}: SPEC benchmarks rely heavily on virtual memory address spaces, demand paging, and memory protection provided by hardware page tables (e.g., RISC-V Sv39 or Sv48 MMUs). A bare-metal microcontroller core without an MMU cannot provide virtual memory.
    \item \textbf{Full Operating System}: SPEC workloads are full Unix/C++ applications requiring POSIX system calls (\texttt{fork}, \texttt{exec}, \texttt{mmap}, file I/O, threads) provided by a full Linux or BSD operating system.
    \item \textbf{Gigabyte Memory Capacity}: SPEC CPU2017 benchmarks require a minimum of 1 to 2\,GB of physical RAM to load their multi-megabyte reference datasets into memory. Microcontrollers typically operate with tens of kilobytes of SRAM.
    \item \textbf{Proprietary Licensing}: SPEC benchmarks are commercial software licensed by the Standard Performance Evaluation Corporation for several thousand dollars, preventing public redistribution or open academic inclusion.
\end{enumerate}

\subsubsection{The Embedded Benchmark Standards: Dhrystone, CoreMark, and Embench}
For microcontroller-class architectures (such as \texttt{RV32I}, ARM Cortex-M0/M3/M4, and MicroBlaze), the computer architecture community relies on lightweight, freestanding benchmark suites:
\begin{itemize}
    \item \textbf{Dhrystone 2.1}: Developed in 1984, Dhrystone is a synthetic integer benchmark that measures CPU throughput in terms of ``Dhrystones per second.'' Results are typically normalized to the VAX 11/780 (which scored 1,757 Dhrystones per second, defining 1 DMIPS):
    \begin{equation}
    \text{DMIPS/MHz} = \frac{10^6}{\text{Cycles per Dhrystone Run} \times 1,757}.
    \end{equation}
    Our single-cycle \texttt{RV32I} core scores $\mathbf{0.824\,\text{DMIPS/MHz}}$ ($\mathbf{269.9\,\text{DMIPS}}$ at operating frequency), while the 4-stage pipeline without forwarding scores $\mathbf{0.468\,\text{DMIPS/MHz}}$ ($\mathbf{343.4\,\text{DMIPS}}$ at operating frequency, reflecting its 1.76 CPI). Although historically widespread, Dhrystone has fallen out of modern favor because its tight loops can be disproportionately affected by compiler string inlining and dead-code elimination.
    
    \item \textbf{EEMBC CoreMark}: Developed by EEMBC to replace Dhrystone, CoreMark executes realistic algorithms (matrix manipulation, linked lists, state machines) specifically designed to prevent optimizing compilers from eliminating computation. Its self-checking CRC guarantees that every algorithmic step produces valid data. On our single-cycle \texttt{RV32I} core, CoreMark delivers $\mathbf{1.143\,\text{CoreMark/MHz}}$ ($\mathbf{374.3\,\text{CoreMarks}}$ at operating frequency), while the 4-stage pipeline delivers $\mathbf{0.608\,\text{CoreMark/MHz}}$ ($\mathbf{446.1\,\text{CoreMarks}}$ at operating frequency, reflecting its 1.88 CPI).
    
    \item \textbf{Embench-IoT}: Developed by the Free and Open Source Silicon (FOSSi) Foundation in collaboration with David Patterson, Embench is a modern, open-source suite of 19 real-world embedded programs (e.g., AES encryption, Huffman decoding, Minver, QR-code, Wic) designed specifically to provide a reproducible, open-source alternative to proprietary benchmarks for microcontroller-class RISC-V cores.
\end{itemize}


\section{Hardware Implementation and Benchmark Evaluation of Data Bypassing}\label{riscvBypassing}
\index{data bypassing}\index{forwarding unit}\index{hazard resolution!forwarding}\index{load-use hazard}

As demonstrated in Section \ref{riscvWorkloads}, the unforwarded 4-stage pipeline suffers severe CPI inflation ($\text{CPI} = 1.63\text{--}1.93$) due to Read-After-Write (RAW) data dependencies. Because producing instructions do not commit their results to the architectural register file until the Memory/Write-Back (MEM/WB) stage, any consuming instruction in the Decode (ID) stage must stall for 2 clock cycles (for distance-1 dependencies) or 1 clock cycle (for distance-2 dependencies). Across real embedded workloads like Dhrystone and CoreMark, these stall cycles annihilate most of the $2.24\times$ frequency multiplier earned by pipelining, leaving an actual application speedup of only $1.16\times\text{--}1.27\times$.

To overcome this bottleneck, high-performance processors employ \textbf{data bypassing} (also known as \textbf{data forwarding}) \cite{patterson2017computer}. By capturing results as soon as they are computed and routing them directly to consuming stages over dedicated bypass multiplexers, dependencies can be satisfied immediately without waiting for register file writeback.

\subsection{Microarchitecture of the Forwarding Paths}
\index{forwarding paths}\index{distance-1 forwarding}\index{distance-2 forwarding}

In our 4-stage pipeline (IF, ID, EX, MEM/WB), data hazards arise from two temporal distances between the producing instruction and the consumer:
\begin{enumerate}
    \item \textbf{Distance-1 Hazards (MEM/WB $\to$ EX)}:
    The producing instruction has executed in EX and currently resides in the MEM/WB stage register (\texttt{ex\_mem}), while the consuming instruction is currently in the EX stage (\texttt{id\_ex}). In the unforwarded pipeline, this required a 2-cycle stall. 
    
    With forwarding, the result computed in EX is already available in the \texttt{ex\_mem} pipeline register. We construct bypass multiplexers at the inputs of the ALU, the branch comparator, and the \texttt{jalr} target adder. Whenever the instruction in MEM/WB will write to a non-zero destination register (\texttt{ex\_mem.regWrite} and $\texttt{ex\_mem.rd} \neq 0$) that matches the operand registers of the instruction in EX ($\texttt{ex\_mem.rd} == \texttt{id\_ex.rs1}$ or $\texttt{id\_ex.rs2}$), the forwarded value (\texttt{exMemFwdData}) replaces the operand read from the register file.
    
    The forwarded data depends on the instruction type:
    \begin{equation}
    \text{exMemFwdData} = 
    \begin{cases}
    \texttt{pc} + 4 & \text{if } \texttt{JAL} \text{ or } \texttt{JALR} \\
    \texttt{imm} & \text{if } \texttt{LUI} \\
    \texttt{pc} + \texttt{imm} & \text{if } \texttt{AUIPC} \\
    \texttt{aluResult} & \text{otherwise (arithmetic/logical/shift operations)}.
    \end{cases}
    \end{equation}
    Additionally, for store instructions (\texttt{SW}, \texttt{SH}, \texttt{SB}), if the stored data register \texttt{rs2} matches \texttt{ex\_mem.rd}, the forwarded value is routed directly into \texttt{ex\_mem.rs2Data}.
    
    \item \textbf{Distance-2 Hazards (WB $\to$ ID Register File Write-Through Bypass)}:
    The producing instruction is committing its writeback data (\texttt{wbData}) to the register file at the end of the MEM/WB stage, while the consuming instruction is in the ID stage reading its operands. If the register file reads synchronously or samples before write completion, the consumer reads stale data. 
    
    We eliminate this hazard by implementing an internal \textbf{write-through bypass} directly at the register file read outputs. If the writeback port is active ($\texttt{wbWen}$) and its destination matches either read address ($\texttt{wbRd} == \texttt{d.rs1}$ or $\texttt{wbRd} == \texttt{d.rs2}$ with $\texttt{wbRd} \neq 0$), \texttt{wbData} is multiplexed directly into \texttt{rs1Val} or \texttt{rs2Val}. This distance-2 hazard is resolved with \textbf{zero stall cycles}.
\end{enumerate}

\subsection{The Load-Use Hazard: The Single Irreducible Stall}
\index{load-use hazard!mechanics}\index{load-use delay}

Can data forwarding eliminate \textit{all} data hazard stalls? The answer is no: \textbf{Load-Use hazards} represent a fundamental physical barrier that no combinational forwarding network can resolve.

Consider a load instruction followed immediately by an instruction that consumes the loaded data:
\begin{lstlisting}[language=c]
lw   x1, 0(x2)     // Load word from memory into x1
addi x3, x1, 10    // Consume x1 immediately
\end{lstlisting}
When \texttt{lw} is in the EX stage, it computes the effective memory address ($\texttt{x2} + 0$). The actual data is not returned by the data memory until the end of the MEM stage! Meanwhile, \texttt{addi} is in the ID stage and will need \texttt{x1} as an ALU input when it enters the EX stage on the very next clock cycle. 

Because the memory data does not physically exist until the end of the MEM stage, forwarding it to the beginning of the EX stage would require transmitting information backward in time! Therefore, the Hazard Detection Unit must detect this condition:
\begin{equation}
\text{isLoadUseHazard} = \texttt{id\_ex.valid} \land \texttt{id\_ex.memRead} \land (\texttt{id\_ex.rd} \neq 0) \land \left((\text{readsRs1} \land \texttt{id\_ex.rd} == \texttt{d.rs1}) \lor (\text{readsRs2} \land \texttt{id\_ex.rd} == \texttt{d.rs2})\right).
\end{equation}
Upon detecting a Load-Use hazard, the hardware injects exactly \textbf{1 stall cycle} (freezing the PC and IF/ID pipeline registers while inserting a bubble/NOP into ID/EX). On the subsequent cycle, the loaded data is in the MEM/WB stage and is forwarded directly into the EX stage via the distance-1 forwarding network. Thus, load-use latency is reduced from 2 stall cycles down to just 1 stall cycle, while all other RAW dependencies incur 0 stalls!

\subsection{Chisel Implementation of Bypassing}
\index{Chisel!forwarding unit implementation}

Listing \ref{lst:chisel_forwarding_unit} shows the complete Chisel implementation of the forwarding multiplexers and revised hazard detection logic integrated into \texttt{RiscvPipelined.scala}.

\begin{chiselcode}[caption={Chisel implementation of distance-1 forwarding, distance-2 write-through bypass, and load-use hazard detection in \texttt{RiscvPipelined.scala}.},label={lst:chisel_forwarding_unit}]
// ========================================================
// STAGE 3: EXECUTE (EX) & FORWARDING UNIT (MEM/WB -> EX)
// ========================================================
val exMemWillWrite = ex_mem.valid && ex_mem.regWrite && (ex_mem.rd =/= 0.U)
val exMemFwdData = MuxCase(ex_mem.aluResult, Seq(
  (ex_mem.isJal || ex_mem.isJalr) -> (ex_mem.pc + 4.U),
  ex_mem.isLui                    -> ex_mem.imm,
  ex_mem.isAuipc                  -> (ex_mem.pc + ex_mem.imm)
))

val forwardRs1 = enableForwarding.B && exMemWillWrite && (ex_mem.rd === id_ex.rs1) && (id_ex.rs1 =/= 0.U)
val forwardRs2 = enableForwarding.B && exMemWillWrite && (ex_mem.rd === id_ex.rs2) && (id_ex.rs2 =/= 0.U)

val exRs1 = Mux(forwardRs1, exMemFwdData, id_ex.rs1Data)
val exRs2 = Mux(forwardRs2, exMemFwdData, id_ex.rs2Data)

alu.io.opA := exRs1
alu.io.opB := Mux(id_ex.aluSrc, id_ex.imm, exRs2)

// ========================================================
// STAGE 2: DECODE (ID) & WRITE-THROUGH BYPASS (WB -> ID)
// ========================================================
val wbBypassRs1 = enableForwarding.B && wbWen && (wbRd === d.rs1) && (d.rs1 =/= 0.U)
val wbBypassRs2 = enableForwarding.B && wbWen && (wbRd === d.rs2) && (d.rs2 =/= 0.U)
val rs1Val = Mux(wbBypassRs1, wbData, regFile.io.rs1_data)
val rs2Val = Mux(wbBypassRs2, wbData, regFile.io.rs2_data)

// ========================================================
// REVISED HAZARD DETECTION UNIT: LOAD-USE ONLY
// ========================================================
val isLoadUseHazard = id_ex.valid && id_ex.memRead && (id_ex.rd =/= 0.U) &&
                      ((readsRs1 && (id_ex.rd === d.rs1)) || (readsRs2 && (id_ex.rd === d.rs2)))

val stall = if_id.valid && Mux(enableForwarding.B, isLoadUseHazard, rawHazardRs1 || rawHazardRs2)
\end{chiselcode}

\section{Single-Stream Acceleration: Pipelined Multiplier Datapath for FIR and MAC Kernels}\label{riscvPipelinedMultiplier}
\index{pipelined multiplier!single-stream acceleration}\index{multiply-accumulate (MAC)!zero-stall execution}\index{FIR filter!pipeline acceleration}\index{intermediate pipeline registers}\index{Booth multiplier!pipelined}

In high-performance processor design, after stage delay balancing and general data forwarding are implemented, the microarchitect is left with one final fundamental technique within a single instruction stream: \textbf{pipelining complex execution units and utilizing inter-stage pipeline registers to hold intermediate unmerged results, coupled with specialized forwarding paths back to the execution stage}.

For compute-intensive digital signal processing (DSP) and machine learning workloads---most notably Finite Impulse Response (FIR) filtering, convolution, matrix-vector multiplication, and vector dot products---the execution profile is overwhelmingly dominated by back-to-back \textbf{Multiply-Accumulate (MAC)} instruction sequences:
\begin{lstlisting}[language=c]
// Canonical RISC-V FIR Filter Inner Loop
loop:
    lw   t0, 0(a7)     // Load input sample x[i]
    lw   t1, 0(a6)     // Load filter coefficient h[i]
    addi a6, a6, 4     // Advance coefficient pointer
    mul  t0, t1, t0    // Multiplication: t0 = x[i] * h[i]
    add  a5, t0, a5    // Accumulation (MAC): a5 += t0
    addi a7, a7, -4    // Decrement sample pointer
    bne  a6, a3, loop  // Loop termination test
\end{lstlisting}

In this canonical kernel, each multiplication (\texttt{mul}) is immediately followed by an accumulation (\texttt{add}) that consumes the product (\texttt{t0}) as its source operand. 

In Section \ref{riscvZmmulCaseStudy}, we discovered that embedding a monolithic combinational multiplier directly inside the ALU wrecks pipeline stage balancing: the EX stage latency balloons to $2.462\,\text{ns}$, dragging the operating clock frequency of the entire core down from $733.7\,\text{MHz}$ to $406.2\,\text{MHz}$ (a $-44.6\%$ frequency collapse). Conversely, implementing the multiplier as a traditional multi-cycle iterative execution unit requires freezing the pipeline for 3 to 4 stall cycles per multiply, severely degrading throughput in MAC-dense loops.

How can a single-issue processor core achieve an issue throughput approaching \textbf{1 instruction entering the pipeline per clock cycle} on FIR and MAC algorithms while maintaining the full $733.7\,\text{MHz}$ ($1.363\,\text{ns}$) operating clock frequency?

The solution lies in \textbf{pipelining the multiplier across the existing processor pipeline stages} (EX and MEM/WB), passing intermediate unmerged carry-save vectors through the pipeline registers, and forwarding the merged product directly back into the EX stage for the subsequent accumulation.

\subsection{Two-Stage Multiplier Partitioning and Intermediate Pipeline Registers}
\index{carry-save reduction!intermediate registers}\index{vector-merging adder!MEM/WB stage}

A 32-bit binary multiplier inherently performs three distinct arithmetic tasks:
\begin{enumerate}
    \item \textbf{Partial Product Generation (PPG)}: Generating 17 partial products via Radix-4 Booth recoding.
    \item \textbf{Carry-Save Reduction Tree}: Compressing the 17 partial products down to two 64-bit redundant vectors: a $Sum$ vector and a $Carry$ vector.
    \item \textbf{Vector-Merging Addition}: Performing a 64-bit carry-propagating addition ($Product = Sum + Carry$) and slicing the required 32-bit output.
\end{enumerate}

The critical insight is that \textbf{the Carry-Save Reduction Tree is completely carry-free}: every full adder (CSA cell) computes independent sum and carry outputs with zero horizontal propagation. Its delay is governed solely by tree depth:
\begin{equation}
T_{\text{tree}} = 6 \times T_{\text{CSA}} \approx 6 \times 65\,\text{ps} \approx 0.390\,\text{ns}.
\end{equation}
Together with Radix-4 Booth recoding and operand muxing ($\approx 0.220\,\text{ns}$), the entire Stage 1 logic requires only $\approx \mathbf{0.610\,\text{ns}}$ in ASAP7 7\,nm FinFET.

Conversely, the \textbf{Vector-Merging Addition} requires full carry propagation across 64 bit positions. Using a fast parallel-prefix or carry-select architecture, this final addition requires $\approx \mathbf{0.520\,\text{ns}}$ in ASAP7 7\,nm FinFET.

Notice the remarkable symmetry: both halves of the multiplier naturally require $\approx 0.52\text{--}0.61\,\text{ns}$, which perfectly matches the baseline stage delays of our 4-stage pipeline ($T_{\text{fetch}} = 0.550\,\text{ns}$, $T_{\text{decode}} = 0.540\,\text{ns}$, $T_{\text{sram\_wb}} = 0.600\,\text{ns}$)!

Therefore, we partition the hardware multiplier across two adjacent pipeline stages:
\begin{itemize}
    \item \textbf{Stage 1: Multiplier Reduction in EX (\texttt{PipelinedMultiplierStage1})}:
    When a multiply instruction (\texttt{MUL}, \texttt{MULH}, \texttt{MULHSU}, \texttt{MULHU}) reaches EX, the 32-bit operands ($rs1$, $rs2$) are recoded using Radix-4 Booth logic into 17 signed partial products. A 6-level Carry-Save Adder (CSA) compressor tree reduces these 17 rows down to two unmerged 64-bit vectors: \texttt{sumOut} ($64$ bits) and \texttt{carryOut} ($64$ bits). Crucially, \textit{no carry propagation occurs in EX}.
    
    \item \textbf{Intermediate Pipeline Register Storage (\texttt{ex\_mem})}:
    At the rising clock edge, the inter-stage pipeline register \texttt{ex\_mem} captures the intermediate unmerged vectors along with operation metadata:
    \begin{equation}
    \texttt{ex\_mem.mulSum} \leftarrow \texttt{mulStage1.sumOut}, \quad \texttt{ex\_mem.mulCarry} \leftarrow \texttt{mulStage1.carryOut}, \quad \texttt{ex\_mem.isMul} \leftarrow \texttt{id\_ex.isMul}.
    \end{equation}
    The intermediate pipeline register acts as temporary redundant storage, completely decoupling partial product reduction from final vector-merging addition.
    
    \item \textbf{Stage 2: Vector-Merging Addition in MEM/WB (\texttt{PipelinedMultiplierStage2})}:
    In the MEM/WB stage, a 64-bit vector-merging adder computes the final sum:
    \begin{equation}
    \text{Product}[63:0] = \texttt{ex\_mem.mulSum} + \texttt{ex\_mem.mulCarry}.
    \end{equation}
    The multiplier output multiplexer slices either bits $[31:0]$ (for \texttt{MUL}) or bits $[63:32]$ (for \texttt{MULH}, \texttt{MULHSU}, \texttt{MULHU}) to produce \texttt{mulStage2Result}.
\end{itemize}

\subsection{Forwarding Mechanics for Zero-Stall Multiply-Accumulate}
\index{forwarding!pipelined multiplier}\index{zero-stall MAC}

Now examine how instructions traverse this datapath during a back-to-back FIR/MAC operation:
\begin{itemize}
    \item \textbf{Cycle $k$}:
    The instruction \texttt{mul t0, t1, t0} is decoded in ID. The accumulation instruction \texttt{add a5, t0, a5} is fetched in IF.
    
    \item \textbf{Cycle $k+1$}:
    \texttt{mul} enters the EX stage. Stage 1 generates the 17 Booth partial products and compresses them through the 6-level CSA tree into \texttt{mulSum} and \texttt{mulCarry}.
    
    Meanwhile, \texttt{add} enters the ID stage. The Hazard Detection Unit inspects the instruction in EX: because \texttt{mul} is an arithmetic instruction rather than a memory load ($\texttt{id\_ex.memRead} == 0$), \textbf{no load-use hazard is detected}. The hazard detection logic asserts no stall ($\texttt{stall} == 0$), allowing \texttt{add} to advance directly into EX on the very next cycle!
    
    \item \textbf{Cycle $k+2$}:
    \texttt{mul} advances to the MEM/WB stage. The intermediate vectors in \texttt{ex\_mem.mulSum} and \texttt{ex\_mem.mulCarry} are added by Stage 2 to produce \texttt{mulStage2Result}.
    
    Simultaneously, \texttt{add} enters the EX stage. It requires register \texttt{t0} ($rs1$). The forwarding unit detects:
    \begin{equation}
    \texttt{exMemWillWrite} \land (\texttt{ex\_mem.rd} == \texttt{id\_ex.rs1}) \quad (\text{both refer to register } \texttt{t0}).
    \end{equation}
    The forwarding multiplexer in the MEM/WB stage selects \texttt{mulStage2Result}:
    \begin{equation}
    \texttt{exMemFwdData} = \text{Mux}(\texttt{ex\_mem.isMul}, \ \texttt{mulStage2Result}, \ \dots).
    \end{equation}
    This completed product is routed directly across the bypass bus to \texttt{alu.io.opA} in the EX stage!
    
    The ALU computes the accumulation $\texttt{a5} + \texttt{t0}$ in EX during Cycle $k+2$ with \textbf{ZERO STALL CYCLES}!
    
    \item \textbf{Cycle $k+3$}:
    The next instruction in the inner loop (e.g., pointer increment \texttt{addi a7, a7, -4}) enters EX, while \texttt{add} advances to MEM/WB.
\end{itemize}

Every single instruction in the compute sequence advances through the pipeline at \textbf{1 instruction entering the pipeline per clock cycle}! The multiply latency of 2 cycles is completely hidden by pipelining Stage 1 in EX and Stage 2 in MEM/WB, while data forwarding eliminates any pipeline bubble between the product generation and its accumulation.

\section{Control Hazard Elimination: Static BTFN and Dynamic Gshare Branch Prediction}\label{riscvBranchPrediction}
\index{branch prediction!static BTFN}\index{branch prediction!dynamic gshare}\index{branch target buffer (BTB)}\index{control hazard!elimination}

Having eliminated data hazards through full bypassing and pipelined execution units, we now confront the final remaining bottleneck in single-stream processor performance: \textbf{control hazards}.

\subsection{The Control Hazard Dilemma: Do Branches Complete Without Bubbles?}
\index{branch penalty!in 4-stage pipeline}\index{pipeline bubbles!taken branches}

To address the fundamental architectural question: \textit{Do branches complete on this 4-stage pipelined design without bubbles?}

The definitive answer is: \textbf{No, taken branches do not complete without bubbles in the baseline pipeline.}

In our 4-stage pipeline (\textsc{IF} $\to$ \textsc{ID} $\to$ \textsc{EX} $\to$ \textsc{MEM/WB}), branch condition evaluation and branch target calculation are performed in the \textsc{EX} stage:
\begin{align}
\text{Condition: } & \text{evaluates whether } \text{rs1} \mathrel{\mathbf{op}} \text{rs2} \quad (\texttt{BEQ}, \texttt{BNE}, \texttt{BLT}, \texttt{BGE}, \texttt{BLTU}, \texttt{BGEU}), \\
\text{Target Address: } & \text{Target} = \text{PC}_{\textsc{EX}} + \text{Imm}_{\textsc{EX}}.
\end{align}
By default, the Instruction Fetch (\textsc{IF}) stage fetches sequentially along the fall-through path ($\text{PC} + 4$). Consequently, the pipeline exhibits an asymmetric branch penalty:
\begin{enumerate}
    \item \textbf{Not-Taken Branches (0 Bubbles)}: When a branch condition evaluates false, the sequentially fetched instructions already advancing through \textsc{IF} and \textsc{ID} are correct. Execution proceeds without interruption: \textbf{0 stall cycles and 0 bubbles}.
    \item \textbf{Taken Branches (2 Bubbles)}: When a branch condition evaluates true in the \textsc{EX} stage, two younger instructions have already entered the pipeline:
    \begin{itemize}
        \item Instruction $i+1$ (currently residing in the \textsc{ID} stage, fetched when the branch was in \textsc{IF}),
        \item Instruction $i+2$ (currently being retrieved in the \textsc{IF} stage).
    \end{itemize}
    The \textsc{EX} stage must assert the pipeline flush signal (\texttt{exRedirect}), invalidating both \texttt{if\_id} and \texttt{id\_ex} pipeline registers. The program counter is redirected to $\text{Target}$, and the processor incurs an unavoidable \textbf{2-cycle branch penalty (2 bubbles)}.
\end{enumerate}

In tight numerical loops (such as FIR filters, matrix multiplication, and vector dot products), backwards loop branches are taken $>95\%$ of the time! Every single loop iteration pays a 2-bubble penalty. As a result, the CPI of a compute loop cannot fall below $1.25\text{--}1.35$ even with perfect ALU bypassing. To achieve true single-stream performance approaching 1 instruction per cycle ($\text{CPI} \to 1.0$), branches must be predicted and redirected in the \textbf{Instruction Fetch (\textsc{IF}) stage}, eliminating bubbles on taken branches.

\subsection{Static BTFN Branch Prediction with Branch Target Buffer}
\index{static branch prediction!BTFN}\index{BTFN!backward taken forward not taken}

The most widely deployed static branch prediction heuristic is \textbf{BTFN: Backward Taken, Forward Not-Taken}.

\subsubsection{Algorithmic Rationale}
In imperative software, loops are structured with a conditional branch at the bottom jumping backwards to the loop header:
\begin{equation}
\text{Target} < \text{PC} \implies \text{Loop Backwards Branch} \longrightarrow \textbf{Predict TAKEN}.
\end{equation}
Conversely, forward conditional branches ($\text{Target} \ge \text{PC}$) typically represent conditional error checks, null pointer validations, or exception handling that execute infrequently:
\begin{equation}
\text{Target} \ge \text{PC} \implies \text{Forward Conditional Branch} \longrightarrow \textbf{Predict NOT-TAKEN}.
\end{equation}
Unconditional jumps (\texttt{JAL}) are always taken.

\subsubsection{The Need for an IF-Stage Branch Target Buffer (BTB)}
\index{branch target buffer (BTB)!microarchitecture}
Static BTFN cannot operate simply by inspecting the branch offset in the instruction word, because instruction decoding does not occur until the \textsc{ID} stage! If the processor waited until \textsc{ID} to identify backward branches, it would still pay a 1-cycle bubble penalty.

To eliminate bubbles entirely (\textbf{0 bubbles}), the prediction and target calculation must occur combinationally in the \textbf{\textsc{IF} stage} using only the current $\text{PC}$. This requires a \textbf{Branch Target Buffer (BTB)}:
\begin{itemize}
    \item A cache-like structure of 32 direct-mapped entries in the \textsc{IF} stage, indexed by $\text{PC}[6:2]$.
    \item Each entry stores a valid bit (\texttt{btbValid}), a tag ($\text{PC}[31:7]$), a predicted target address (\texttt{btbTarget}), and a flag indicating whether the entry is an unconditional jump (\texttt{btbIsJal}).
    \item When $\text{PC}$ hits in the BTB:
    \begin{equation}
    \text{predTaken} = \text{btbHit} \land \bigl((\text{btbTarget} < \text{PC}) \lor \text{btbIsJal}\bigr).
    \end{equation}
    If \texttt{predTaken} is asserted, the next program counter is updated immediately to \texttt{btbTarget} for the very next clock cycle.
    \item The target instruction enters \textsc{IF} on cycle $t+1$, while the branch advances to \textsc{ID}. When the branch resolves in \textsc{EX} on cycle $t+2$, if the prediction was correct, \textbf{no pipeline flush occurs (\texttt{exRedirect = false})}. The target instruction is already in \textsc{EX}: \textbf{0 BUBBLES}!
\end{itemize}

\subsection{Dynamic Gshare Branch Prediction}
\index{dynamic branch prediction!gshare}\index{gshare predictor!Scott McFarling}

While static BTFN excels on simple backward loops, it exhibits fundamental limitations:
\begin{enumerate}
    \item It cannot adapt to data-dependent branches whose outcome varies dynamically at runtime.
    \item It always mispredicts the final loop exit, paying a 2-cycle penalty on every loop termination.
    \item It cannot exploit \textbf{branch correlation}---where the outcome of a branch depends on the outcomes of recently executed prior branches.
\end{enumerate}

To overcome these limitations, Scott McFarling (1993) introduced the \textbf{Gshare} branch predictor, a two-level adaptive predictor that hashes the branch address with a \textbf{Global History Register (GHR)}.

\subsubsection{Microarchitectural Structure}
As illustrated in Figure \ref{fig:gshare_arch}, Gshare consists of three tightly coupled structures:
\begin{enumerate}
    \item \textbf{Global History Register (GHR)}: An 8-bit shift register recording the actual direction ($1 = \text{Taken}$, $0 = \text{Not-Taken}$) of the last 8 committed branch instructions.
    \item \textbf{Pattern History Table (PHT)}: A table of $2^8 = 256$ two-bit saturating up/down counters. The states are defined as:
    \begin{itemize}
        \item \texttt{00} ($0$): Strongly Not-Taken,
        \item \texttt{01} ($1$): Weakly Not-Taken,
        \item \texttt{10} ($2$): Weakly Taken,
        \item \texttt{11} ($3$): Strongly Taken.
    \end{itemize}
    The most significant bit (MSB, bit 1) determines the prediction: $1 \implies \text{Taken}$, $0 \implies \text{Not-Taken}$. Two consecutive mispredictions are required to flip the prediction, preventing transient loop exits from corrupting steady-state behavior.
    \item \textbf{Gshare Hashing Function}: The index into the PHT is computed by bitwise XORing the branch PC with the global history:
    \begin{equation}
    \text{PHT\_Index} = \text{PC}[9:2] \oplus \text{GHR}[7:0].
    \end{equation}
    This hashing uniformly disperses branch instances across the 256 counter entries, reducing destructive aliasing between different branches while preserving correlation between consecutive branches.
    \item \textbf{Branch Target Buffer (BTB)}: As in BTFN, a 32-entry BTB supplies the predicted target address when the PHT counter predicts taken:
    \begin{equation}
    \text{predTaken} = \text{btbHit} \land \bigl(\text{PHT}[\text{PHT\_Index}][1] \lor \text{btbIsJal}\bigr).
    \end{equation}
\end{enumerate}

\subsection{Chisel Microarchitectural Implementation}
\index{Chisel!branch predictor implementation}\index{RiscvPipelined!branch prediction integration}

The branch predictor is implemented as a standalone, modular hardware module (\texttt{BranchPredictor.scala}) and integrated seamlessly into \texttt{RiscvPipelined.scala}.

Listing \ref{lst:branch_predictor_chisel} displays the core logic for both BTFN and Gshare prediction in Chisel:

\begin{lstlisting}[language=scala, caption={Chisel implementation of the parameterized Branch Predictor supporting Static BTFN and Dynamic Gshare (scabook/riscv/BranchPredictor.scala).}, label={lst:branch_predictor_chisel}]
class BranchPredictor(
  val xlen: Int = 32,
  val predictorType: String = "none",
  val btbEntries: Int = 32,
  val historyWidth: Int = 8
) extends Module {
  val io = IO(new BranchPredictorIO(xlen, historyWidth))

  val normalizedType = predictorType.trim.toLowerCase

  if (normalizedType == "none") {
    io.predTaken   := false.B
    io.predTarget  := io.pc + 4.U
    io.predHistory := 0.U
  } else {
    // 32-entry Branch Target Buffer (BTB) in IF stage
    val indexBits = log2Ceil(btbEntries)
    val tagBits   = xlen - indexBits - 2

    val btbValid   = RegInit(VecInit(Seq.fill(btbEntries)(false.B)))
    val btbTags    = Reg(Vec(btbEntries, UInt(tagBits.W)))
    val btbTargets = Reg(Vec(btbEntries, UInt(xlen.W)))
    val btbIsJal   = RegInit(VecInit(Seq.fill(btbEntries)(false.B)))

    // IF stage query
    val ifIndex = io.pc(indexBits + 1, 2)
    val ifTag   = io.pc(xlen - 1, indexBits + 2)
    val btbHit  = btbValid(ifIndex) && (btbTags(ifIndex) === ifTag)
    val btbTarget = btbTargets(ifIndex)

    // EX stage update
    val updateIndex = io.updatePC(indexBits + 1, 2)
    val updateTag   = io.updatePC(xlen - 1, indexBits + 2)
    when(io.updateValid && io.actualTaken) {
      btbValid(updateIndex)   := true.B
      btbTags(updateIndex)    := updateTag
      btbTargets(updateIndex) := io.actualTarget
      btbIsJal(updateIndex)   := io.updateIsJal
    }

    if (normalizedType == "btfn") {
      // BTFN: Backward branches (target < pc) or JAL predicted TAKEN
      val isBackward = btbTarget < io.pc
      val isJal      = btbIsJal(ifIndex)
      val predTaken  = btbHit && (isBackward || isJal)

      io.predTaken   := predTaken
      io.predTarget  := Mux(predTaken, btbTarget, io.pc + 4.U)
      io.predHistory := 0.U
    } else {
      // GSHARE: 256-entry PHT indexed by PC XOR GHR
      val numPhtEntries = 1 << historyWidth
      val pht = RegInit(VecInit(Seq.fill(numPhtEntries)(2.U(2.W))))
      val ghr = RegInit(0.U(historyWidth.W))

      val pcHash    = io.pc(historyWidth + 1, 2)
      val phtIndex  = pcHash ^ ghr
      val counter   = pht(phtIndex)
      val dirTaken  = counter(1) // MSB = 1 -> Taken
      val isJal     = btbIsJal(ifIndex)
      val predTaken = btbHit && (dirTaken || isJal)

      io.predTaken   := predTaken
      io.predTarget  := Mux(predTaken, btbTarget, io.pc + 4.U)
      io.predHistory := ghr

      // PHT and GHR update upon branch commitment in EX
      val updateHash     = io.updatePC(historyWidth + 1, 2)
      val updatePhtIndex = updateHash ^ io.prevHistory
      when(io.updateValid && io.updateIsBr) {
        val currCnt = pht(updatePhtIndex)
        when(io.actualTaken) {
          pht(updatePhtIndex) := Mux(currCnt === 3.U, 3.U, currCnt + 1.U)
        }.otherwise {
          pht(updatePhtIndex) := Mux(currCnt === 0.U, 0.U, currCnt - 1.U)
        }
        ghr := Cat(ghr(historyWidth - 2, 0), io.actualTaken.asUInt)
      }
    }
  }
}
\end{lstlisting}

In the 4-stage pipeline (\texttt{RiscvPipelined.scala}), the Execute stage detects mispredictions by comparing actual branch resolution against the speculative prediction carried down the pipeline registers (\texttt{id\_ex.predTaken}, \texttt{id\_ex.predTarget}):
\begin{lstlisting}[language=scala, caption={Misprediction detection and recovery logic in the Execute stage (scabook/riscv/RiscvPipelined.scala).}, label={lst:riscv_mispredict_chisel}]
  // Misprediction detection in EX:
  // If predicted outcome and target match actual execution: 0 FLUSH (0 BUBBLES)!
  val isBranch = id_ex.valid && id_ex.branch
  val branchMispredicted = isBranch && (
    (branchTaken =/= id_ex.predTaken) ||
    (branchTaken && (id_ex.predTarget =/= branchTarget))
  )
  val branchRecoveryPC = Mux(branchTaken, branchTarget, id_ex.pc + 4.U)

  val isJal = id_ex.valid && id_ex.isJal
  val jalMispredicted = isJal && (!id_ex.predTaken || (id_ex.predTarget =/= jalTarget))
  val jalrRedirect = id_ex.valid && id_ex.isJalr

  val exRedirect = branchMispredicted || jalMispredicted || jalrRedirect
  val exTargetPC = Mux(jalrRedirect, jalrTarget,
                   Mux(jalMispredicted, jalTarget,
                       branchRecoveryPC))
\end{lstlisting}

\section{The Role of the Compiler in Processor Efficiency: Optimization Levels, Hazards, and Dynamic Execution}\label{riscvCompilerStudy}
\index{compiler!optimization levels and processor efficiency}
\index{microarchitecture!compiler interaction}

Having developed the architectural techniques for a single scalar instruction stream---pipelining the datapath, balancing adder and multiplier stages, implementing data forwarding, and deploying dynamic branch prediction---we have driven the cycles per instruction (CPI) of the 4-stage RV32I core down to near-unity ($\text{CPI} \approx 1.09$). However, processor performance is not determined by hardware microarchitecture alone. It is governed by the classic Iron Law of Processor Performance:
\begin{equation}
T_{\text{exec}} = \text{Instruction Count } (I) \times \text{Cycles Per Instruction } (\text{CPI}) \times \text{Clock Period } (T_{\text{clk}}).
\end{equation}
While physical pipelining minimizes the clock period $T_{\text{clk}}$ and microarchitectural bypassing and branch prediction minimize $\text{CPI}$, the compiler toolchain exerts sovereign control over the dynamic instruction count $I$ and the instruction mix. 

Before transitioning from a scalar pipeline to a superscalar multi-issue architecture, this section investigates the interplay between compiler optimization flags, static code generation, pipeline hazard dynamics, and dynamic execution efficiency across all five processor configurations developed in this chapter.

\subsection{Compiler Toolchain Discovery: The Baseline Configuration}
Inspection of the bare-metal benchmark build harness (\texttt{core\_portme.h} and the \texttt{.comment} metadata of compiled ELF binaries) reveals that the existing baseline Dhrystone and CoreMark binaries were compiled using the modern LLVM/Clang toolchain:
\begin{itemize}
    \item \textbf{Compiler}: \texttt{Ubuntu clang version 21.1.8 (6ubuntu1)} with \texttt{LLVM LLD 21.1.8}.
    \item \textbf{Target Architecture}: \texttt{riscv32-unknown-elf}, \texttt{march=rv32i}, \texttt{mabi=ilp32}.
    \item \textbf{Baseline Flags}: \texttt{-O1 -march=rv32i -mabi=ilp32 -ffreestanding -fno-builtin -nostdlib -fuse-ld=lld -T benchmarks/bench.ld}.
\end{itemize}
The baseline was explicitly set to \texttt{-O1}, representing basic linear optimization. To evaluate the full spectrum of compiler influence, we generated freestanding standalone binaries across ten optimization configurations: \texttt{-O0}, \texttt{-O1}, \texttt{-O2}, \texttt{-O3}, \texttt{-O4}, \texttt{-O5}, \texttt{-Os}, \texttt{-Oz}, \texttt{-Ofast}, and an extreme \texttt{ridiculous} optimization suite.

\subsection{Taxonomy of Compiler Optimization Levels in Modern Clang/LLVM}
The compilation options impact the generated code structure as follows:
\begin{enumerate}
    \item \textbf{\texttt{-O0} (Unoptimized Baseline)}:
    Register allocation for local variables is disabled. Every local variable and intermediate expression is allocated to a dedicated stack frame slot in memory. Consequently, every arithmetic operation is preceded by stack loads (\texttt{lw}) and followed by stack stores (\texttt{sw}), flooding the pipeline with memory traffic.
    
    \item \textbf{\texttt{-O1} (Basic Optimization)}:
    Enables global register allocation, basic block merging, constant folding, and dead-code elimination. Variables reside in the 32 general-purpose registers rather than on the stack, dramatically reducing load/store instructions.
    
    \item \textbf{\texttt{-O2} (Production Optimization)}:
    Enables global common subexpression elimination (CSE), loop-invariant code motion (LICM), peephole optimization, and static instruction scheduling designed to interleave independent instructions.
    
    \item \textbf{\texttt{-O3} (Aggressive Optimization)}:
    Enables aggressive function inlining, predictive loop unrolling, and vectorization analysis. Loop bounds and bodies are transformed to maximize execution throughput at the expense of moderate code size growth.
    
    \item \textbf{\texttt{-O4} and \texttt{-O5} (Clang Aliases)}:
    In modern Clang/LLVM, levels above \texttt{-O3} do not exist as distinct optimization passes. Invoking \texttt{-O4} triggers a compiler warning (\texttt{warning: -O4 is equivalent to -O3 [-Wdeprecated]}), while \texttt{-O5} emits \texttt{warning: optimization level '-O5' is not supported; using '-O3' instead}. Exact MD5 cryptographic checksum analysis confirms that the binaries generated under \texttt{-O3}, \texttt{-O4}, and \texttt{-O5} are \textbf{100.000\% bit-for-bit identical} (MD5 checksum: \texttt{7b4e53a5511b5e49...} on CoreMark).
    
    \item \textbf{\texttt{-Ofast} (Fast Math)}:
    Enables all \texttt{-O3} optimizations along with non-standard, fast floating-point arithmetic (\texttt{-ffast-math}). Because both CoreMark and Dhrystone are pure integer/pointer benchmarks without floating-point operations, \texttt{-Ofast} produces \textbf{identical machine code to \texttt{-O3}}.
    
    \item \textbf{\texttt{-Os} and \texttt{-Oz} (Code Size Minimization)}:
    \texttt{-Os} optimizes for minimum code size while maintaining execution speed. \texttt{-Oz} pushes code density to the absolute extreme: inlining is disabled, common tail sequences are merged into shared helper subroutines, and loop bodies are strictly preserved rather than unrolled.
    
    \item \textbf{\texttt{ridiculous} (Extreme Inlining and Loop Unrolling)}:
    To test the absolute limits of compiler aggression on RISC-V, we evaluated a specialized high-performance flag combination:
    \begin{lstlisting}[language=bash]
clang -O3 -flto -funroll-loops -fomit-frame-pointer \
      -mllvm -inline-threshold=2000 -mllvm -unroll-threshold=2000 ...
    \end{lstlisting}
    This forces Link-Time Optimization (LTO) across all compilation units, aggressively inlines nested call graphs, and fully unrolls major loop kernels.
\end{enumerate}

    \item \textbf{Memory Access Proliferation at \texttt{-O0}}:

Because registers are not allocated to hold intermediate values, the compiler generates back-to-back \texttt{sw} and \texttt{lw} operations around every single arithmetic instruction. When optimization is enabled (\texttt{-O1} to \texttt{-O3}), register allocation slashes memory instructions down to $\sim 28\%$, allowing register-to-register ALU instructions to dominate ($59\text{--}65\%$).
    
    \item \textbf{The Code-Density Paradox of \texttt{-Oz}}:
    \texttt{-Oz} achieves the absolute smallest static footprint: CoreMark text shrinks by \textbf{31.1\%} ($12,792\,\text{B} \to 8,812\,\text{B}$) and Dhrystone shrinks by \textbf{24.3\%} ($3,085\,\text{B} \to 2,336\,\text{B}$). However, to achieve this compactness, the compiler aggressively outlines repeated code into small functions, causing jump instructions (\texttt{jal}/\texttt{jalr}) to jump from $7.4\%$ up to $10.9\%$ in CoreMark. As shown below, this static density comes at severe dynamic runtime cost!
    
    \item \textbf{Binary Explosion under \texttt{ridiculous} Optimization}:
    Forcing loop unrolling and function inlining expands CoreMark text by \textbf{$5.1\times$} ($11,976\,\text{B} \to 61,116\,\text{B}$, with static instructions expanding from $2,655$ to $15,199$) and Dhrystone text by \textbf{$4.7\times$} ($2,993\,\text{B} \to 14,028\,\text{B}$). Loop branches are replaced with straight-line replicated ALU instructions, lowering branch instructions from $4.4\%$ down to $1.4\%$.
\end{enumerate}

\subsection{Microarchitectural Analysis: Why the Compiler Cannot Fix an Unforwarded Pipeline}
The empirical results in Tables \ref{tab:compiler_dynamic_coremark} and \ref{tab:compiler_dynamic_dhrystone} reveal four fundamental lessons in computer engineering:

\begin{enumerate}
    \item \textbf{The Software Isolation of Pipeline Stalls}:
    A common misconception is that a sufficiently sophisticated compiler can eliminate pipeline stalls via instruction scheduling. The data decisively refutes this: on the \texttt{4-Stage NoFwd} core, the CPI remains stubbornly anchored at $\mathbf{1.88\text{--}1.90}$ across \texttt{-O1}, \texttt{-O2}, \texttt{-O3}, and \texttt{ridiculous}! Because basic blocks in integer C programs typically contain only 4 to 6 instructions with dense register dependencies, the compiler runs out of independent instructions to schedule into the 2-cycle hazard delay slots. The unforwarded core suffers \textbf{over 506,000 RAW stalls} regardless of compiler aggression. Pipeline stalls are a hardware defect that software cannot schedule away.
    
    \item \textbf{Data Bypassing as the Great Equalizer}:
    Hardware data bypassing slashes CoreMark data stalls by \textbf{94.6\%} (from 517,244 down to 27,915 stalls at \texttt{-O1}), leaving only irreducible Load-Use stalls. This drops the CPI from $1.88$ to $1.32\text{--}1.33$ across all optimization levels.
    
    \item \textbf{Branch Prediction Accuracy Across Optimization Levels}:
    Static BTFN branch prediction reduces CoreMark branch mispredictions by $76.6\%$ (from 97,308 down to 22,764). Dynamic Gshare prediction cuts mispredictions by \textbf{88.9\%} (down to 10,759 mispredictions out of 147,627 dynamic branches, an overall prediction accuracy of \textbf{92.7\%}). This eliminates over 173,000 branch flush bubbles, bringing CoreMark CPI down to \textbf{1.09}.
    
    \item \textbf{The Runtime Cost of Extreme Code Size Optimization (\texttt{-Oz})}:
    While \texttt{-Oz} successfully minimizes code size to 8.8\,KB, it causes dynamic instruction count to expand by \textbf{+11.2\%} on CoreMark ($859,290 \to 955,942$) and by \textbf{+199.7\%} on Dhrystone ($10,212 \to 30,605$). Total execution time on the Gshare core increases from $1,287.7\,\mu\text{s}$ (\texttt{-O3}) to $1,429.0\,\mu\text{s}$ (\texttt{-Oz}), demonstrating the universal trade-off between memory footprint and execution latency.
\end{enumerate}

\subsection{The Scalar Asymptote: Reaching the Asymptotic Scalar Limit}
Notice the effective CPI achieved on the \texttt{4-Stage Gshare} core across all optimized variants:
\begin{equation}
\text{CPI}_{\text{CoreMark, O1}} = 1.09, \quad \text{CPI}_{\text{CoreMark, O2}} = 1.10, \quad \text{CPI}_{\text{CoreMark, O3}} = 1.10, \quad \text{CPI}_{\text{CoreMark, ridic}} = 1.10.
\end{equation}
In a single-issue scalar processor, the theoretical maximum instruction throughput is strictly bounded by:
\begin{equation}
\text{IPC}_{\text{max}} = 1.00 \quad \iff \quad \text{CPI}_{\text{min}} = 1.00.
\end{equation}
An achieved CPI of $1.094$ corresponds to an issue throughput of $\text{IPC} = 0.914$ instructions per cycle. In other words, \textbf{the 4-stage RV32I core with bypassing and Gshare branch prediction is operating at 91.4\% of theoretical maximum scalar throughput}!

The residual $8.6\%$ overhead consists of physical constraints inherent to scalar execution:
\begin{itemize}
    \item True load-use data stalls (1 cycle when an instruction immediately consumes data loaded from memory).
    \item Indirect jump redirects (\texttt{JALR} targets must be computed in EX, incurring 2 bubbles).
    \item The remaining $7.3\%$ branch mispredictions.
\end{itemize}
We have reached the physical and algorithmic performance ceiling of a single instruction stream.

\subsection{The Next Architectural Frontier: Dual-Issue Superscalar Execution}
To break through the fundamental $\text{CPI} = 1.00$ ($\text{IPC} = 1.00$) barrier, processor architecture must abandon the scalar single-issue paradigm and transition to \textbf{superscalar execution}.

In the next chapter, we will design and implement a \textbf{2-Way In-Order Dual-Issue Superscalar RV32I Processor Core} (\texttt{RiscvSuperscalar2Way}):
\begin{enumerate}
    \item \textbf{Dual Instruction Fetch}: The IF stage fetches 64 bits (two 32-bit instructions, $I_0$ and $I_1$) per clock cycle from instruction memory.
    \item \textbf{Parallel Dual Decode and Intra-Issue Dependency Checking}: The ID stage decodes $I_0$ and $I_1$ simultaneously and evaluates:
    \begin{itemize}
        \item Structural hazards: e.g., if only one data memory port exists, two simultaneous load/store instructions cannot co-issue.
        \item Intra-group RAW hazards: if $I_1$ reads the register written by $I_0$ ($I_1.rs1 == I_0.rd$ or $I_1.rs2 == I_0.rd$), $I_1$ cannot issue in parallel with $I_0$.
    \end{itemize}
    \item \textbf{Dual Execution and Multi-Ported Register Files}: When $I_0$ and $I_1$ are independent, both issue concurrently into parallel execution units (ALU0 and ALU1), writing back up to two results per cycle into a 4-read/2-write port register file.
\end{enumerate}
By issuing up to 2 instructions per cycle, a dual-issue superscalar core elevates peak throughput to $\mathbf{\text{IPC} = 2.00}$ ($\text{CPI} = 0.50$), unlocking a new dimension of performance on the exact same silicon technology.


\section{Summary}\label{riscvSummary}
\index{RISC-V!chapter summary}

This chapter presented the comprehensive architecture, microarchitectural implementation, formal verification, and physical ASIC design of the open standard RISC-V processor:
\begin{itemize}
    \item The RISC-V Instruction Set Architecture organizes execution around a clean 32-bit regular format with symmetric register source/destination fields, fixed opcode locations, and sign bits fixed at bit 31 across all formats.
    \item A single-cycle Harvard 5-OS processor core (\texttt{RiscvFetchExecute}) was implemented by modularly integrating library automata developed across prior chapters: \texttt{ProgramCounter}, \texttt{RiscvDecoder}, \texttt{RiscvImmGen}, \texttt{RiscvRegFile}, \texttt{RiscvALU}, and \texttt{RiscvDataMemory}.
    \item A 4-stage pipelined processor core (\texttt{RiscvPipelined}) was developed, partitioning the datapath into Instruction Fetch (IF), Instruction Decode (ID), Execute (EX), and Memory/Write-Back (MEM/WB) stages.
    \item An active Hazard Detection Unit was designed to detect Read-After-Write (RAW) data dependencies and stall the pipeline by freezing the PC and IF/ID registers while injecting bubbles into ID/EX. In our baseline processor without data forwarding, distance-1 RAW hazards incur a 2-cycle stall penalty and distance-2 RAW hazards incur a 1-cycle stall penalty until the producing instruction commits in the MEM/WB stage.
    \item Branch and jump conditions are evaluated in the EX stage, incurring a 2-cycle control hazard penalty on taken transfers while executing non-taken branches with zero cycle overhead.
    \item Both processor cores were verified against all official RISC-V architectural conformance test suites (38 RV32I suites and 4 Zmmul suites) using Chisel simulation, achieving a 100\% signature match against Spike golden references.
    \item Full physical synthesis targeting the predictive ASAP7 7\,nm FinFET standard cell library was conducted for the baseline \texttt{RV32I} and \texttt{RV32I\_Zmmul} cores. Under the 4-step pipeline delay model, the 4-stage pipelined \texttt{RV32I} reduced the clock period from $3.053\,\text{ns}$ (sum of 4 steps) to $1.363\,\text{ns}$ (max of 4 steps), delivering a $\Delta T = 1.690\,\text{ns}$ reduction and a +124.0\% clock frequency increase ($327.5\,\text{MHz} \to 733.7\,\text{MHz}$, a $2.24\times$ frequency multiplier).
    \item Comprehensive physical benchmark evaluation was performed across DSP kernels, Dhrystone 2.1 (20 runs), and EEMBC CoreMark 1.0 (1 iteration, 2K data footprint). The 4-stage pipeline achieved $100\%$ validation matching golden signatures, scoring $0.468\,\text{DMIPS/MHz}$ ($343.4\,\text{DMIPS}$ at operating frequency) and $0.608\,\text{CoreMark/MHz}$ ($446.1\,\text{CoreMarks}$ at operating frequency).
    \item Pipelining an $N$-stage processor was shown to be bounded in practice by three physical barriers: (1) stage delay quantization and imbalance (Amdahl's Law for clock periods, where atomic blocks like the 32-bit ALU restrict frequency scaling to $2.24\times$, far below the ideal $4.0\times$), (2) sequential flip-flop overhead ($t_{\text{setup}} + t_{\text{cq}} + t_{\text{skew}} \approx 55\,\text{ps}$ per stage in 7\,nm FinFET), and (3) hazard-induced CPI expansion ($\text{CPI} \approx 1.76\text{--}1.93$ without forwarding). Because the $2.24\times$ frequency multiplier is largely offset by the $\sim 1.8\times$ CPI expansion from stalls, the unforwarded pipelined processor runs ``only a tiny bit faster'' ($1.16\times\text{--}1.27\times$), demonstrating why data forwarding is crucial to harvest the full performance benefits of pipelining.
    \item Hardware data bypassing was implemented in Chisel, providing distance-1 forwarding (MEM/WB to EX) and distance-2 write-through bypassing (WB to ID). All ALU data dependencies are satisfied with zero stall cycles; only Load-Use hazards require a 1-cycle stall.
    \item Physical ASIC synthesis in ASAP7 7\,nm FinFET revealed that adding full data bypassing requires only +390 standard cells and expands core silicon area by \textbf{merely +2.7\%} ($1,128.16\,\mu\text{m}^2 \to 1,158.95\,\mu\text{m}^2$) with 0 additional flip-flops.
    \item On standard benchmarks, bypassing eliminated $>60\%$ of all pipeline stalls: CoreMark CPI dropped from 1.88 to 1.33 (yielding $1.69\times$ speedup over single-cycle, +41.8\% CoreMarks/MHz), and Dhrystone CPI dropped from 1.76 to 1.44 (yielding $1.55\times$ speedup, 418.5 DMIPS).
    \item Single-stream processor performance for Multiply-Accumulate (MAC) intensive workloads (FIR filters, convolution, vector dot products) was accelerated by pipelining the hardware multiplier across EX and MEM/WB. Stage 1 in EX computes Radix-4 Booth recoding and a 6-level CSA reduction tree to redundant carry-save vectors ($Sum$, $Carry$), which are captured in the inter-stage pipeline registers (\texttt{ex\_mem}). Stage 2 in MEM/WB performs vector-merging addition and forwards the product directly to EX operands via data bypassing. This microarchitecture eliminates all stalls between back-to-back \texttt{mul} and \texttt{add} instructions, sustaining an issue rate of 1 instruction entering the pipeline per clock cycle while restoring operating frequency to $733.7\,\text{MHz}$ ($1.363\,\text{ns}$).
    \item On the DSP hardware multiply benchmark, the pipelined multiplier core slashed execution time to $1,361.64\,\text{ns}$ ($1.36\,\mu\text{s}$), achieving a $\mathbf{2.45\times}$ speedup over the single-cycle core and a $\mathbf{1.81\times}$ speedup over the unpipelined multiplier pipeline, while surprisingly reducing full core silicon area by $-22.6\%$ ($2,235.55\,\mu\text{m}^2 \to 1,729.57\,\mu\text{m}^2$) due to standard cell drive-strength optimization.
    \item Control hazards in the 4-stage pipeline were eliminated through Static BTFN (Backward Taken, Forward Not-Taken) and Dynamic Gshare branch prediction. In the baseline pipeline, not-taken branches execute with 0 bubbles, but taken branches incur an unavoidable 2-cycle penalty (2 bubbles) due to EX-stage resolution, imposing an artificial CPI floor of $\sim 1.25\text{--}1.35$ on loop-intensive workloads.
    \item Static BTFN with a 32-entry Branch Target Buffer (BTB) in the IF stage predicts backward branches ($\text{Target} < \text{PC}$) and unconditional jumps (\texttt{JAL}) taken, eliminating bubbles on tight loops (0 bubbles). Dynamic Gshare combines an 8-bit Global History Register (GHR) XORed with branch PC to index a 256-entry Pattern History Table (PHT) of 2-bit saturating counters, adapting dynamically to correlated branches and loop exits.
    \item Standalone ASAP7 7\,nm FinFET synthesis demonstrated that both BTFN ($661.7\,\text{ps}$, $1.51\,\text{GHz}$) and Gshare ($523.1\,\text{ps}$, $1.91\,\text{GHz}$) operate with delay well below the $1.363\,\text{ns}$ critical path, adding less than $46\,\text{ps}$ to the full processor clock period while preserving operating frequency ($576\text{--}579\,\text{MHz}$).
    \item On empirical benchmarks, branch prediction slashed CPI on the DSP kernel from 1.35 to 1.05 ($2.14\times$ speedup over single-cycle), on Dhrystone 2.1 from 1.44 to 1.14 ($1.96\times$ speedup, 528.2 DMIPS), and on EEMBC CoreMark 1.0 from 1.33 to 1.09 ($2.05\times$ speedup, 766.3 CoreMarks). Across CoreMark, the combination of data bypassing and Gshare eliminated 89.3\% of all pipeline stalls.
    \item A taxonomy of computer architecture benchmarks was established: application-class benchmarks such as SPEC CPU2017 require virtual memory (MMU), a full POSIX OS (Linux), and gigabytes of RAM, rendering them physically inapplicable to bare-metal microcontroller-class cores. Microcontroller-class architectures rely on freestanding suites including Dhrystone, EEMBC CoreMark, and Embench-IoT.
    \item The interaction between compiler optimization levels and processor microarchitecture was systematically quantified across ten optimization configurations (\texttt{-O0}, \texttt{-O1}, \texttt{-O2}, \texttt{-O3}, \texttt{-O4}, \texttt{-O5}, \texttt{-Os}, \texttt{-Oz}, \texttt{-Ofast}, and \texttt{ridiculous} LTO/unrolling). In modern Clang 21, \texttt{-O4} and \texttt{-O5} are deprecated aliases for \texttt{-O3} (producing 100\% bit-for-bit identical binaries), while \texttt{-Ofast} on integer code is equivalent to \texttt{-O3}.
    \item Moving from unoptimized \texttt{-O0} to basic \texttt{-O1} slashes dynamic instruction count by $4.8\times$ on CoreMark ($4,204,574 \to 874,891$) by replacing stack spills with register allocation. However, compilers cannot schedule away RAW pipeline hazards: the unforwarded pipeline exhibits a persistently poor $\text{CPI} \approx 1.88\text{--}2.29$ across all compiler optimization levels.
    \item The code-size paradox of \texttt{-Oz} was demonstrated: while achieving the smallest static text footprint (8.8\,KB, a $-31\%$ reduction), \texttt{-Oz} increases dynamic instruction count by $+11.2\%$ on CoreMark and $+199.7\%$ on Dhrystone by converting inlined loops into outlined helper calls, increasing runtime latency. Conversely, extreme loop unrolling (\texttt{ridiculous}) expands text size by $5.1\times$ to 61.1\,KB, but retires the fewest dynamic instructions (829,488 on CoreMark).
    \item On the 4-stage pipeline with data bypassing and dynamic Gshare branch prediction, CoreMark achieves $\text{CPI} = 1.09\text{--}1.10$ ($\text{IPC} \approx 0.914$) across all optimized compiler variants, operating at \textbf{91.4\% of theoretical maximum scalar throughput}. Because a single-issue scalar core cannot exceed $\text{IPC} = 1.00$, this empirical limit establishes the imperative for \textbf{superscalar dual-issue execution} ($\text{IPC} \le 2.00$) explored in subsequent chapters.
\end{itemize}


\section{Problems}\label{riscvProblems}
\index{problems!RISC-V architecture and implementation}

\begin{problem}
Explain why the RISC-V instruction format places the sign bit of all immediate values in bit 31 ($\text{inst}[31]$) across all instruction formats (I, S, B, U, J). How does this design choice benefit hardware decoders?

\textbf{Solution}:
By fixing the immediate sign bit at $\text{inst}[31]$, the hardware immediate generator can immediately begin sign-extending the most significant bit across upper datapath wires (e.g., replicating $\text{inst}[31]$ into bits 31:12 or 31:20) concurrently with opcode decoding, before the instruction format is even identified. This reduces decoding latency and simplifies fan-out buffering.
$\diamond$
\end{problem}

\begin{problem}
In the implementation of \texttt{JALR}, the RISC-V specification dictates that the least significant bit of the computed target address must be forced to zero: $\text{target} = (\text{rs1} + \text{imm}) \ \& \ \sim 1$.
\begin{enumerate}
    \item What software purpose does this requirement serve?
    \item Where is this masking implemented in the \texttt{RiscvPipelined} processor?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Forcing bit 0 to 0 guarantees that control never transfers to an unaligned byte address that would cause an instruction-address-misaligned exception. It also enables software to use pointer arithmetic where low bits store tag flags, stripping the flag during return or indirect call.
    \item In \texttt{RiscvPipelined.scala}, the EX stage computes:
    \texttt{val jalrTarget = Cat((id\_ex.rs1Data + id\_ex.imm)(xlen - 1, 1), 0.U(1.W))}, explicitly forcing bit 0 to zero before routing to the next-PC multiplexer.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider the following sequence of instructions executing on the 4-stage \texttt{RiscvPipelined} processor:
\begin{lstlisting}[language=c]
add x1, x2, x3
sub x4, x1, x5
and x6, x1, x7
\end{lstlisting}
\begin{enumerate}
    \item Identify the data hazards present in this sequence.
    \item How many stall cycles are incurred between \texttt{add} and \texttt{sub} in the baseline pipeline without forwarding?
    \item How many stall cycles are incurred between \texttt{add} and \texttt{and} in the baseline pipeline without forwarding?
    \item How will data forwarding (bypass paths from EX and MEM/WB back to ID/EX) affect the execution of this sequence when introduced in later microarchitectures?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Both \texttt{sub} and \texttt{and} have a Read-After-Write (RAW) data hazard on register \texttt{x1} produced by \texttt{add}.
    \item In the baseline pipeline without forwarding, \texttt{add} computes its result in EX and writes it to the register file during MEM/WB. When \texttt{sub} enters the ID stage immediately following \texttt{add} (distance-1 dependency), \texttt{add} is in EX. The Hazard Detection Unit stalls \texttt{sub} for \textbf{2 clock cycles} (freezing PC and IF/ID while inserting bubbles into ID/EX) until \texttt{add} completes MEM/WB and updates \texttt{x1}.
    \item The instruction \texttt{and} has a distance-2 RAW dependency on \texttt{x1} from \texttt{add}. When \texttt{and} reaches the ID stage, because \texttt{sub} was stalled for 2 cycles, \texttt{add} has already committed to the register file. However, in an arbitrary program where a distance-2 instruction is separated from the producer by one independent instruction (with no prior stalls), the producer is in MEM/WB when the consumer is in ID, requiring \textbf{1 stall cycle} without forwarding.
    \item When data forwarding is introduced, bypass multiplexers forward the calculated result directly from the output of the EX stage (for distance-1) or the MEM/WB stage (for distance-2) to the ALU inputs. This completely eliminates both stall cycles, allowing back-to-back ALU execution at 0 stall cycles (1.0 CPI).
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
In the 4-stage pipeline, branch condition evaluation and target address generation are performed in the EX stage.
\begin{enumerate}
    \item What is the branch penalty (in clock cycles) when a conditional branch evaluates taken?
    \item What is the branch penalty when a conditional branch evaluates not-taken?
    \item If branches represent 20\% of all executed instructions in a program, and 60\% of branches are taken, what is the branch contribution to the overall CPI?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item When a branch is taken, the two instructions fetched speculatively into the IF and ID stages are flushed. Thus, the penalty is \textbf{2 clock cycles}.
    \item When a branch is not taken, execution falls through sequentially without flushing the pipeline. Thus, the penalty is \textbf{0 clock cycles}.
    \item Average branch penalty per instruction:
    \begin{equation}
    \text{CPI}_{\text{branch}} = 0.20 \times (0.60 \times 2 + 0.40 \times 0) = 0.20 \times 1.20 = 0.24 \ \text{cycles/instruction}.
    \end{equation}
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Compare the physical synthesis data of the pure \texttt{RV32I} core (Table \ref{tab:asap7_rv32i_synthesis}) with the \texttt{RV32I\_Zmmul} core (Table \ref{tab:riscv_grand_comparison}):
\begin{enumerate}
    \item In pure \texttt{RV32I}, pipelining increased the clock frequency by +124.0\% ($327.5\,\text{MHz} \to 733.7\,\text{MHz}$, a $2.24\times$ multiplier). Why did pipelining the \texttt{RV32I\_Zmmul} core only improve frequency by +68.7\% ($240.8\,\text{MHz} \to 406.2\,\text{MHz}$, a $1.69\times$ multiplier)?
    \item Calculate the silicon area overhead of adding the unpipelined multiplier to the 4-stage pipelined processor in ASAP7 7\,nm FinFET technology.
    \item State Amdahl's Law as it applies to pipeline stage delays and clock periods.
    \item Propose two microarchitectural techniques that would allow the processor to retain the high operating frequency of pure \texttt{RV32I} while providing hardware multiplication acceleration.
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item In pure \texttt{RV32I}, the four physical pipeline steps are relatively well balanced ($T_{\text{fetch}} = 0.550\,\text{ns}$, $T_{\text{decode}} = 0.540\,\text{ns}$, $T_{\text{execute}} = 1.363\,\text{ns}$, $T_{\text{sram\_wb}} = 0.600\,\text{ns}$). The single-cycle FE core requires the sum ($3.053\,\text{ns}$), while the pipelined core requires the max ($1.363\,\text{ns}$), yielding a $3.053 / 1.363 = 2.240\times$ frequency multiplier (+124.0\%). In \texttt{RV32I\_Zmmul}, the combinational $32 \times 32$ multiplier logic array requires $2.148\,\text{ns}$ of delay, expanding the EX step critical path to $2.462\,\text{ns}$. The single-cycle FE core requires $0.550 + 0.540 + 2.462 + 0.600 = 4.152\,\text{ns}$ ($240.8\,\text{MHz}$), while the pipelined core is bounded by the slowest stage ($\max_i T_i = 2.462\,\text{ns}$, $406.2\,\text{MHz}$). Pipelining achieves only a $4.152 / 2.462 = 1.687\times$ frequency scaling (+68.7\%). By Amdahl's Law for clock periods, the pipeline frequency is bottlenecked by the monolithic combinational multiplier, severing the advantage gained from pipelining the remaining three stages.
    \item The silicon standard cell area increases from $1,128.16\,\mu\text{m}^2$ (pure RV32I 4-stage) to $2,235.55\,\mu\text{m}^2$ (RV32I\_Zmmul 4-stage). This represents an increase of:
    \begin{equation}
    \Delta \text{Area} = 2,235.55 - 1,128.16 = 1,107.39\,\mu\text{m}^2 \quad (+98.2\% \ \text{silicon area overhead}).
    \end{equation}
    Similarly, comparing the standalone ALUs, adding multiplication increases ALU area from $103.31\,\mu\text{m}^2$ to $1,186.67\,\mu\text{m}^2$ (an $11.5\times$ increase!).
    \item Amdahl's Law for clock periods dictates that:
    \begin{equation}
    T_{\text{clk}} \ge \max_{1 \le i \le N} (T_{\text{stage}, i}) + T_{\text{reg\_overhead}}.
    \end{equation}
    The minimum clock period of a synchronous pipeline is strictly bounded by the delay of the single slowest stage. Subdividing or optimizing the remaining $N-1$ stages cannot reduce the clock period below the slowest stage's delay.
    \item Two microarchitectural techniques:
    \begin{itemize}
        \item \textbf{Multi-cycle Multiplier}: Implement the multiplier as a multi-cycle iterative unit (e.g., 3-cycle stall only on \texttt{MUL}), keeping the base processor clock at $733.7\,\text{MHz}$ for all other instructions.
        \item \textbf{Pipelined Multiplier}: Subdivide the multiplier logic array into 2 or 3 internal synchronous pipeline stages (partial product generation, tree compression, final adder), reducing each stage's delay to $<0.8\,\text{ns}$.
    \end{itemize}
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider the empirical EEMBC CoreMark 1.0 benchmark results from Table \ref{tab:riscv_all_benchmarks} executing on the pure \texttt{RV32I} single-cycle (FE) core ($T_{\text{clk}} = 3.053\,\text{ns}$) and 4-stage pipelined core ($T_{\text{clk}} = 1.363\,\text{ns}$):
\begin{enumerate}
    \item A student expects a 4-stage pipeline to achieve a $4.0\times$ speedup over the single-cycle core. Compute the actual benchmark speedup using instruction count $I = 874,891$, single-cycle cycles $C_1 = 874,891$, and pipelined cycles $C_4 = 1,643,060$.
    \item Decompose the actual speedup into its frequency multiplier factor and CPI factor. Explain why the pipelined core runs ``only a tiny bit faster'' ($1.19\times$) despite a $2.24\times$ clock frequency increase.
    \item Why cannot desktop/server benchmarks such as SPEC CPU2017 be executed directly on bare-metal \texttt{RV32I} microcontroller cores? What modern open-source benchmark suite was created to evaluate microcontroller-class RISC-V processors?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item Total execution times:
    \begin{equation}
    T_{\text{exec, FE}} = C_1 \times T_{\text{clk, FE}} = 874,891 \times 3.053\,\text{ns} = 2,671,042\,\text{ns} \quad (2.671\,\text{ms}).
    \end{equation}
    \begin{equation}
    T_{\text{exec, pipe}} = C_4 \times T_{\text{clk, pipe}} = 1,643,060 \times 1.363\,\text{ns} = 2,239,491\,\text{ns} \quad (2.239\,\text{ms}).
    \end{equation}
    \begin{equation}
    \text{Actual Speedup} = \frac{2,671,042\,\text{ns}}{2,239,491\,\text{ns}} = \mathbf{1.193\times} \quad (+19.3\% \ \text{performance gain}).
    \end{equation}
    \item Using the performance equation:
    \begin{equation}
    \text{Speedup} = \left(\frac{\text{CPI}_{\text{single}}}{\text{CPI}_{\text{pipe}}}\right) \times \left(\frac{T_{\text{clk, FE}}}{T_{\text{clk, pipe}}}\right) = \left(\frac{1.00}{1.878}\right) \times \left(\frac{3.053\,\text{ns}}{1.363\,\text{ns}}\right) = 0.532 \times 2.240 = \mathbf{1.193\times}.
    \end{equation}
    Pipelining provides a $2.240\times$ frequency multiplier by overlapping the four physical pipeline steps across clock cycles. However, in the absence of data forwarding, RAW data hazard stalls (2-cycle stalls for distance-1, 1-cycle stall for distance-2) and 2-cycle taken branch flushes inflate the CPI from 1.00 to 1.878 (+87.8\% cycle overhead). This CPI penalty factor ($1 / 1.878 = 0.532$) devours nearly three-quarters of the frequency gain, leaving only a modest $+19.3\%$ net speedup.
    \item SPEC CPU2017 cannot run on bare-metal \texttt{RV32I} microcontroller cores because SPEC benchmarks require a Memory Management Unit (MMU) with virtual memory paging, a full POSIX operating system (Linux), multi-gigabyte RAM capacity, glibc with dynamic file I/O, and commercial proprietary licenses. The modern open-source embedded alternative created by David Patterson and the FOSSi consortium is \textbf{Embench-IoT}.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider accelerating a digital signal processing Finite Impulse Response (FIR) filter or Multiply-Accumulate (MAC) inner loop on the 4-stage pipelined RISC-V processor:
\begin{lstlisting}[language=c]
mul t0, t1, t0    // t0 = sample * coeff
add a5, t0, a5    // a5 += t0 (accumulate)
\end{lstlisting}
\begin{enumerate}
    \item If the multiplier is implemented as an unpipelined combinational array inside the Execute (EX) stage, how does this affect the operating clock period of the entire core in ASAP7 7\,nm FinFET technology?
    \item Explain how partitioning the multiplier into two pipeline stages (Stage 1 in EX, Stage 2 in MEM/WB) with intermediate pipeline registers restores pipeline stage balancing. What intermediate arithmetic values are stored in the \texttt{ex\_mem} pipeline register?
    \item In the 2-stage pipelined multiplier with data bypassing, trace the cycle-by-cycle execution of \texttt{mul} followed by \texttt{add}. Explain why \texttt{add} experiences zero stall cycles despite \texttt{mul} having a 2-cycle latency.
    \item Calculate the execution time and speedup of the DSP benchmark (804 instructions, 999 cycles) running on the pipelined multiplier core ($T_{\text{clk}} = 1.363\,\text{ns}$) compared to the single-cycle core ($T_{\text{clk}} = 4.152\,\text{ns}$) and the unpipelined multiplier core ($T_{\text{clk}} = 2.462\,\text{ns}$).
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item An unpipelined combinational multiplier has a propagation delay of $2.148\,\text{ns}$ in ASAP7 7\,nm FinFET. Adding multiplexer and register setup overhead inflates the Execute stage delay to $T_{\text{execute}} = 2.462\,\text{ns}$. By Amdahl's Law for clock periods, $T_{\text{clk}} = \max(T_{\text{fetch}}, T_{\text{decode}}, T_{\text{execute}}, T_{\text{sram\_wb}}) = 2.462\,\text{ns}$, causing the operating clock frequency of the entire core to collapse from $733.7\,\text{MHz}$ down to $406.2\,\text{MHz}$ (a $-44.6\%$ penalty on all instructions).
    \item Partitioning the multiplier decouples carry-save partial product reduction from final carry-propagating vector addition. Stage 1 in EX computes Radix-4 Booth recoding and a 6-level CSA compressor tree ($\approx 0.61\,\text{ns}$, carry-free). Stage 2 in MEM/WB executes a 64-bit vector-merging adder ($\approx 0.52\,\text{ns}$). The intermediate pipeline register \texttt{ex\_mem} synchronously stores the unmerged redundant vectors: \texttt{ex\_mem.mulSum} (64 bits), \texttt{ex\_mem.mulCarry} (64 bits), \texttt{ex\_mem.mulOp} (5 bits), and \texttt{ex\_mem.isMul} (1 bit). Because both sub-stages require $\le 0.65\,\text{ns}$, the Execute stage delay drops back to the base integer ALU critical path ($1.363\,\text{ns}$), restoring the operating frequency to $733.7\,\text{MHz}$.
    \item Execution cycle trace:
    \begin{itemize}
        \item Cycle 1: \texttt{mul} in ID, \texttt{add} in IF.
        \item Cycle 2: \texttt{mul} in EX (Stage 1 computes Booth PPG and 6-level CSA tree into \texttt{mulSum} and \texttt{mulCarry}). \texttt{add} in ID. Because \texttt{mul} is not a memory load ($\texttt{memRead} == 0$), the hazard unit detects no load-use hazard and asserts 0 stalls ($\texttt{stall} == 0$).
        \item Cycle 3: \texttt{mul} enters MEM/WB (Stage 2 vector adder computes product and places \texttt{mulStage2Result} onto \texttt{exMemFwdData}). Simultaneously, \texttt{add} enters EX. The forwarding unit detects $\texttt{ex\_mem.rd} == \texttt{id\_ex.rs1}$ (\texttt{t0}) and routes \texttt{exMemFwdData} directly to ALU operand A. The ALU computes the accumulation with \textbf{0 stall cycles}.
    \end{itemize}
    Consecutive instructions enter the pipeline at \textbf{1 instruction per cycle}.
    \item Total execution times:
    \begin{itemize}
        \item Single-Cycle: $T_{\text{exec}} = 804 \times 4.152\,\text{ns} = 3,338.21\,\text{ns}$ ($3.34\,\mu\text{s}$).
        \item Unpipelined Multiplier Core with Bypassing: $T_{\text{exec}} = 999 \times 2.462\,\text{ns} = 2,459.54\,\text{ns}$ ($2.46\,\mu\text{s}$), delivering $1.36\times$ speedup.
        \item Pipelined Multiplier Core with Bypassing: $T_{\text{exec}} = 999 \times 1.363\,\text{ns} = \mathbf{1,361.64\,\text{ns}}$ ($1.36\,\mu\text{s}$).
    \end{itemize}
    Speedup vs Single-Cycle: $3,338.21 / 1,361.64 = \mathbf{2.45\times}$.
    Speedup vs Unpipelined Multiplier Core: $2,459.54 / 1,361.64 = \mathbf{1.81\times}$.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider branch prediction in the 4-stage \texttt{RiscvPipelined} processor:
\begin{enumerate}
    \item In the baseline processor without branch prediction, explain why not-taken branches execute with 0 bubbles while taken branches incur 2 bubbles.
    \item A loop executes 1,000 iterations. In each iteration, the backward loop branch is taken 999 times and not-taken 1 time upon exit. Assuming perfect data bypassing with 10 instructions in the loop body before the branch:
    \begin{enumerate}
        \item Compute the total execution cycles and loop CPI in the baseline pipeline.
        \item Compute the total execution cycles and loop CPI with Static BTFN (assuming the BTB is warm after the first iteration).
        \item Compute the total execution cycles and loop CPI with Dynamic Gshare (assuming 2-bit counter saturated to Strongly Taken).
    \end{enumerate}
    \item Explain the state transitions of a 2-bit saturating up/down counter ($00 \leftrightarrow 01 \leftrightarrow 10 \leftrightarrow 11$) when a loop terminates and restarts. Why does Gshare outperform a 1-bit predictor?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item In the 4-stage pipeline, branch condition evaluation and target address calculation occur in the Execute (EX) stage. For not-taken branches, the sequentially fetched instructions ($PC+4$) already advancing through IF and ID are on the correct execution path, incurring 0 stall cycles and 0 bubbles. For taken branches, two younger speculative instructions have entered the pipeline (one in ID, one in IF). When the branch resolves taken in EX, \texttt{exRedirect} flushes \texttt{if\_id} and \texttt{id\_ex} and redirects the PC, incurring a 2-cycle branch penalty (2 bubbles).
    \item Loop performance analysis:
    Each iteration contains 10 body instructions + 1 branch instruction = 11 instructions. Total executed instructions = $1,000 \times 11 = 11,000$ instructions.
    \begin{enumerate}
        \item \textbf{Baseline Pipeline}:
        Each taken branch incurs 2 bubbles. Total taken branches = 999. Not-taken exit branch = 1 (0 bubbles).
        Base execution cycles (assuming ideal 1 CPI with bypassing) = 11,000 cycles.
        Branch stall cycles = $999 \times 2 = 1,998$ cycles.
        Total cycles = $11,000 + 1,998 = 12,998$ cycles.
        $\text{CPI} = 12,998 / 11,000 = \mathbf{1.182}$.
        \item \textbf{Static BTFN}:
        On iteration 1 (cold miss), BTB misses, incurring 2 bubbles. On iterations 2 through 999, BTB hits and predicts backward branch taken ($Target < PC$), incurring 0 bubbles. On iteration 1,000 (loop exit), BTFN predicts taken, but the branch actually falls through (misprediction!), incurring 2 bubbles to redirect to $PC+4$.
        Total branch stall cycles = $2 \ (\text{cold miss}) + 2 \ (\text{exit mispredict}) = 4$ cycles.
        Total cycles = $11,000 + 4 = 11,004$ cycles.
        $\text{CPI} = 11,004 / 11,000 = \mathbf{1.0004} \approx \mathbf{1.00}$.
        \item \textbf{Dynamic Gshare}:
        After initial training, the 2-bit saturating counter is in state 11 (Strongly Taken). For the 999 taken branches, prediction is correct (0 bubbles). On exit, Gshare mispredicts taken (2 bubbles) and the counter decrements to 10 (Weakly Taken). Total stall cycles = 4 cycles (or 2 if BTB is pre-warmed). Total cycles $\approx 11,004$ cycles ($\text{CPI} \approx \mathbf{1.00}$).
    \end{enumerate}
    \item A 1-bit predictor immediately changes its prediction on any misprediction. On loop exit, a 1-bit predictor flips to Not-Taken. When the loop is re-entered later, the very first iteration will mispredict not-taken (paying another penalty). A 2-bit saturating counter requires \textbf{two consecutive mispredictions} to flip its MSB prediction: state 11 (Strongly Taken) decrements to 10 (Weakly Taken) on loop exit, but still predicts Taken on the next invocation! Thus, Gshare incurs only 1 misprediction per loop execution, whereas a 1-bit predictor incurs 2 mispredictions per loop execution.
\end{enumerate}
$\diamond$
\end{problem}

\begin{problem}
Consider the interaction between compiler optimization flags and processor microarchitecture evaluated in Section \ref{riscvCompilerStudy}:
\begin{enumerate}
    \item In Table \ref{tab:compiler_static_coremark}, memory instructions (Loads + Stores) account for $50.7\%$ of all static instructions at \texttt{-O0}, but drop to $28.7\%$ at \texttt{-O1}. Explain why disabling optimization causes memory instructions to proliferate so dramatically.
    \item In Table \ref{tab:compiler_dynamic_coremark}, why does the \texttt{4-Stage NoFwd} pipeline suffer an almost identical $\text{CPI} \approx 1.88\text{--}1.90$ across \texttt{-O1}, \texttt{-O2}, \texttt{-O3}, and \texttt{ridiculous}, despite vast differences in compiler optimization aggression?
    \item The \texttt{-Oz} flag minimizes static code size, while the \texttt{ridiculous} flag maximizes loop unrolling. Compare their static footprints and dynamic instruction counts on CoreMark. What fundamental architectural trade-off does this comparison illustrate?
    \item On the \texttt{4-Stage Gshare} core, CoreMark executes at $\text{CPI} = 1.09$. Explain why it is physically impossible for any software compiler technique to reduce the CPI of this processor below $1.00$. What microarchitectural modification is required to break through this limit?
\end{enumerate}

\textbf{Solution}:
\begin{enumerate}
    \item At \texttt{-O0}, the compiler disables the register allocator for local variables, mapping every local variable and compiler temporary to an offset on the activation stack frame. Consequently, every expression requires loading operands from memory into temporary registers via \texttt{lw} and immediately writing the result back to memory with \texttt{sw}. At \texttt{-O1}, the compiler constructs live ranges and allocates local variables to the 32 general-purpose registers, allowing values to persist across instructions without touching memory.
    \item In integer C code (such as CoreMark), basic blocks average only 4 to 6 instructions, and computations are tightly serialized by data dependencies. The compiler's static instruction scheduler cannot find independent instructions to separate dependent ALU operations by 2 delay slots (for distance-1 RAW hazards). Therefore, regardless of optimization level, the unforwarded pipeline continually stalls on RAW dependencies, resulting in a fixed $\text{CPI} \approx 1.88\text{--}1.90$. Hardware data bypassing is mandatory to resolve these hazards.
    \item On CoreMark, \texttt{-Oz} achieves a text footprint of only $8,812\,\text{B}$ ($1,864$ static instructions), but executes $955,942$ dynamic instructions. The \texttt{ridiculous} configuration expands text to $61,116\,\text{B}$ ($15,199$ static instructions, a $5.1\times$ expansion!), but executes only $829,488$ dynamic instructions (a $-13.2\%$ reduction compared to \texttt{-Oz}). This illustrates the classic Space-Time Trade-off in computer systems: loop unrolling eliminates loop branch overhead and enables cross-iteration scheduling at the cost of instruction cache/ROM footprint.
    \item In a synchronous single-issue processor, the datapath can fetch, decode, execute, and retire at most \textbf{one instruction per clock cycle}. Therefore, $\text{IPC} \le 1.00$, which dictates that $\text{CPI} = 1 / \text{IPC} \ge 1.00$. Even with zero stalls and zero branch mispredictions, the CPI cannot drop below $1.00$. To achieve $\text{CPI} < 1.00$ ($\text{IPC} > 1.00$), the processor microarchitecture must be redesigned as a \textbf{superscalar processor} that fetches, decodes, and executes multiple instructions concurrently in parallel execution units each clock cycle.
\end{enumerate}
$\diamond$
\end{problem}
